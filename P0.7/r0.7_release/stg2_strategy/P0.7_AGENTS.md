# Stage 2 — Sol-eid evidensretrieval og pakkestrategi

## Modell og fysisk grense

- Én manuelt startet chat per Stage 1-makroklynge, normalt omtrent 20 jobber.
- Modell: **GPT-5.6 Sol, Max**.
- Jobb bare i `stg2_strategy/`; skriv bare til den aktuelle makroklyngen i
  `output/`. Stage 2 eier retrieval, evidensvalg og strategi.

## Tillatt input

- Stage 1-output med `job_identity.json`, `vacancy.md`,
  `vacancy_analysis.md`, `_DONE.md` og ingen aktiv `BLOCKED.md`;
- `Work_experience.md`, `Education.md`, `Other_high_value_information.md`;
- `CV_BASELINE.md`, `PERSUASION_CALIBRATION.md` og relevante Stage 2-/felles
  deler av runtimekjernen.

## Én prompt, to interne faser

Bruk én chat og to arbeidsbølger på normalt 10+10 jobber: **Wave 1** er de
første omtrent ti jobbene, midpoint kommer etter Wave 1, og **Wave 2** er
resten.

1. **Phase A:** les alle vacancy-analysene før retrieval. Bygg en kompakt
   klyngebasert evidensunivers med to tydelige evidence lanes; kartlegg
   kandidatfakta til konkrete ansettelsesspørsmål, ikke bare annonseord.
2. **Midpoint/checkpoint:** lagre `CLUSTER_EVIDENCE_BASE.md` og et komplett
   `MINICLUSTER_SPLIT.json`; kontroller at alle jobber finnes én gang i A/B,
   at 10/10 er normalformen og at en 8/12–12/8-splitt er forklart.
3. **Phase B — source-first self-audit:** åpne hver valgt kilde igjen før
   blueprinten lagres. Kontroller personlig bidrag, lifecycle, kanalrolle,
   redundans og sterkeste alternative rute. Fjern uforankrede slutninger.

## Autoritative output

I `output/<macro_cluster_id>/`:

- `CLUSTER_EVIDENCE_BASE.md` med disse obligatoriske headingene:

```text
# Cluster definition
# Cluster cohesion check
# Shared employer problems
# Shared candidate routes
# Shared evidence atoms
# Evidence lane A
## Jobs
## Lane-specific employer problems
## Lane-specific candidate routes
## Lane-specific evidence priorities
## Lane-specific writing risks
# Evidence lane B
# Shared transferable capabilities
# Common objections and reframes
# Stable CV building blocks
# Cluster-specific genericity risks
# Complete cluster-job matrix
# Recommended minicluster split
# Downstream model recommendations
```

  Hvert evidensatom skal være source-first med kilde/heading, kjernefaktum,
  personlig bidrag, lifecycle, beste kanal, trygg sterk formulering og
  eksplisitt do-not-claim. Matrisen skal bruke kolonnene `Job`, `Lane`,
  `Candidate identity`, `Employer problem`, `E1`, `E2`, `Differentiator` og
  `Complexity`;
- `MINICLUSTER_SPLIT.json` med `macro_cluster_id`, `A` og `B`; hver jobbid én
  gang, A/B disjunkte;
- per jobb en kopi av kumulativ input og `package_blueprint.md` med minst:

```text
# Primary candidate identity
# Employer problem
# Shortlist thesis
# Main evidence 1
# Main evidence 2
# Optional differentiator
# Strongest alternative route and why it loses
# Objection reframes
# CV override plan
# Application plan
# Portal plan
# Do not undersell
# Borderline claims for private review
# Stage 3 complexity note
```

- per jobb `_DONE.md`:

```text
Stage: 2
Status: COMPLETED
Artifact: package_blueprint.md; job_identity.json
Job: <job_id>
Model: GPT-5.6 Sol
Effort: max
```

Oppdater makroklyngens `BATCH_STATUS.md` etter hver jobb, i fullt
Wave 1/midpoint/Wave 2-format fra `START_HERE.md`.

## Evidence lock og recovery

Etter Stage 2 er klyngebasen, splitten og blueprintene låst. Stage 3/4 kan
kontrollere ett konkret faktum, men ikke gjøre ny bred retrieval eller erstatte
strategien stille. Ved continuation gjenbrukes bare komplette jobber med
gjeldende `_DONE.md`; fortsett rundt jobber med mekanisk `BLOCKED.md`.

## Forbudt

Ingen employer-facing sluttprosa, rendering, kandidatfit-veto, API-/agentløp
eller Stage 3/4. Ikke gjør clusterbasen til én felles strategi for alle jobber.
