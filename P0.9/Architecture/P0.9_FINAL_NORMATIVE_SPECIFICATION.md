# Jobbsøk_26 P0.9 — Final Normative Specification

**Project architecture:** P0.9  
**Specification revision:** 0.9.0  
**Status:** FROZEN_NORMATIVE  
**Freeze date:** 2026-08-22

## 1. Normative scope, language and authority

### 1.1 Purpose

This specification defines the complete P0.9 architecture from a human-approved vacancy set to truthful, materially tailored, reviewable and manually submittable employer-facing packages for one candidate. It freezes product policy, authority, stage semantics, artifact roles, lifecycle, state ownership, failure behavior, validation classes, rendering semantics, human boundaries, evaluation obligations and implementation-verification requirements.

It does **not** freeze module names, class names, command spelling, library choices, volatile commercial model names, exact JSON property names where the required semantics are preserved, or internal code topology without an architectural reason.

### 1.2 Normative language

- **MUST / MUST NOT**: required for conformance.
- **SHOULD / SHOULD NOT**: strong default; deviation requires a recorded, evidence-based reason and must preserve every MUST-level invariant.
- **MAY**: genuine implementation freedom.

Descriptive examples do not create additional requirements.

### 1.3 Two independent authority axes

`INV-01` **Decision authority.** Proposition-level precedence is:

1. this final specification and its controlling process prompt;
2. the Post-Critique Authoritative Directive for every subject it addressed;
3. other unsuperseded explicit user decisions in the canonical context;
4. unsuperseded P0.8.0 normative rules;
5. mechanisms explicitly adopted into P0.9;
6. supported synthesis;
7. unresolved proposals and draft-model preference.

`INV-02` **Empirical authority.** For factual claims about implementation or the external environment, precedence is:

1. direct inspection and test evidence from the actual artifact/environment;
2. strong primary external evidence;
3. supported research synthesis;
4. inference;
5. unsupported assertion.

A policy decision may select architecture without proving an empirical generalization. An empirical fact may constrain implementation but MUST NOT silently choose product policy. Supersession is proposition-specific, never whole-document-wide.

### 1.4 Version-state facts

- P0.7 is the last real executable and mechanically test-backed release. Its implementation evidence is reusable only at the scope actually tested.
- P0.8.0 is the last formally adopted pre-P0.9 normative architecture and was never implemented.
- P0.8.1 is a non-normative hardening proposal unless this specification explicitly adopts a mechanism informed by it.
- P0.9 revision 0.9.0 is the controlling architecture for Step 2.

No P0.8.1 mechanism is described as historically adopted merely because P0.9 now adopts a similar mechanism.

### 1.5 Interpretation rule

Where this specification identifies an empirical uncertainty as `GATE-*`, the frozen architecture already has a safe default and does not depend on guessing the result. Where it identifies a causal uncertainty as `EXP-*`, baseline correctness is independent of the outcome. A gate or experiment result MUST NOT silently broaden or contradict a user-locked rule.

## 2. Product objective and hard constraints

### 2.1 Product

Jobbsøk_26 is a private, local-first, manually operated production system for one candidate. The product is the employer-facing package, not the analysis, state, provenance, validation or reporting machinery used to protect it.

`DEC-01` **Invariant core deliverables.** Every `CORE` job MUST produce:

1. one materially tailored CV; and
2. one materially tailored application letter.

Both documents MUST be written in Norwegian Bokmål and MUST be complete semantic deliverables regardless of whether a particular employer ultimately consumes both. Core schemas and prompts MUST NOT contain a `letter_required`, CV-only or output-mode branch.

`DEC-04` **Bokmål-only core.** The P0.9 core language is `nb-NO`. Non-Bokmål jobs are exceptions handled outside the core. The core MUST NOT contain normal language branching.

`DEC-02` **Portal/forms outside core.** Portal questions, structured form answers, platform-specific text fields, question IDs, field limits, portal status and portal answer generation are outside the core. They MAY be handled downstream in a separate, manually initiated activity after an approved package exists. That activity is not a prerequisite for core completion and writes no authoritative core state.

### 2.2 Narrow happy-path architecture

P0.9 MUST optimize the invariant CV-plus-letter path rather than generalize around irregular channels, languages or submission modes. The core MUST NOT contain generalized platform, channel, `portal_required`, `required_components`, upload-mode or submission-mode machinery solely to adapt package production.

Operational notes MAY identify unusual facts for the human. Such notes MUST NOT become a generalized branch engine.

`DEC-03` **Minimal exception isolation.** Every approved opportunity MUST be represented exactly once as `CORE` or `EXCEPTION`. An exception MUST remain visible, MUST NOT block a core job, and MUST be handled separately or manually. The exception representation MUST remain small: classification plus a human-readable reason is sufficient. It MUST NOT grow into a second workflow or a machine-actionable channel taxonomy.

`DEC-32` **Operational inventory, human redesign judgment.** A vacancy inventory is useful for prioritization, exception visibility and later human decisions, but it is not authority over the invariant product boundary. No percentage, count or repeated exception reason automatically reopens the architecture. Only an explicit human amendment may do so.

### 2.3 Selective-quality objective

The optimization target is:

```text
Q_happy = (median(package_quality)
           + mean(top_80_percent(package_quality))) / 2
```

`Q_happy` applies only to `CORE` packages that were produced by the automated core and received a human quality score. Any core job without an evaluable/scored final MUST be reported separately and MUST NOT disappear from batch counts. For a finite set, the evaluation MUST state its rounding convention; the default is the highest `floor(0.8 × n)` scores, with at least one score. At small `n`, raw ordered scores and sensitivity views MUST accompany the aggregate.

The practical target remains approximately 30 strong packages from an opportunity set around 40, assessed only among `CORE` automated jobs. Exception jobs and core jobs lacking an evaluable final remain visible in the companion counts. The system SHOULD surface and selectively handle the weak tail rather than weaken strong packages to increase uniformity.

Baseline planning and evaluation MUST acknowledge the current operating envelope: roughly 5–10 human hours per week, approximately 10–20 total human minutes per submitted package, an urgent first-batch window of roughly 1–4 weeks, and a normal semantic-chat envelope around 20–25 chats for approximately 40 jobs. These are workload and expected-value constraints, not automatic rejection thresholds. Additional chats MAY be used when demonstrated package-quality value justifies them; routine extensive human rewriting is a product failure signal.

Every report containing `Q_happy` MUST also report, at minimum:

- total approved opportunities;
- core-job count;
- exception-job count;
- submitted-known count;
- human-scored core-package count and core jobs lacking an evaluable final.

It MUST NOT present core-only quality as coverage of the entire approved opportunity set.

### 2.4 Optimization hierarchy

Among alternatives satisfying the hard constraints, optimize in this order:

1. final package quality / expected interview value;
2. low human effort;
3. fast and simple implementation;
4. model cost;
5. reversibility / optionality.

A mechanism whose only current benefit is future optionality SHOULD NOT exist.

### 2.5 Hard constraints

The following are non-tradeable:

- every material candidate claim MUST be truthful, correctly attributed and interview-defensible;
- candidate identity, employer identity and job identity MUST remain exact;
- final deliverables MUST remain employer-usable;
- human approval MUST precede submission or any irreversible external action;
- no deterministic runtime component may autonomously contact an employer, submit an application, alter a profile or publish material;
- no runtime numeric package-quality or fit judge may gate or route production.

`DEC-31` **No runtime quality score; role-based models.** Model responsibilities are frozen as capability roles, not volatile product names. Human pilot scores MAY be stored in a separate evaluation log, but runtime components MUST NOT compute, store or act on a model-generated package-quality or confidence score.

## 3. Regression firewall and explicit non-goals

`DEC-17` **No auxiliary preparation model in baseline.** Stage 1 begins from the vacancy, factual authorities and lean deterministic index; no Luna-class or other preparatory semantic pass is a baseline dependency. Any such pass belongs only to `EXP-03` until explicitly amended.

The baseline MUST NOT include any of the following unless a later explicit amendment identifies a recurrent observed failure and demonstrates material expected value:

- API/model-call orchestration as the normal workflow;
- automatic semantic execution or hidden multi-stage retries;
- multi-agent debate, generalized agent frameworks or a fourth judge stage;
- automatic job search, employer research as a default pipeline, employer contact or submission;
- portal/form generation, channel matrices or language branches in core;
- model-generated cluster plans, Priority A/B predictions or differentiated writing treatment;
- event sourcing, mutable-manifest version engines, database abstractions or runtime dependency graphs;
- vector databases, embeddings, GraphRAG, semantic caches or manually maintained claim graphs;
- cross-job role/archetype/personality memory or persistent semantic memory;
- model-generated global source summaries, cheap-model relevance filters or any preparation artifact that becomes a factual carrier or source-exclusion boundary;
- model-generated settings compilers, prompt caches or configuration surfaces with no current consumer;
- per-job duplicated copies of candidate authorities as separately maintained state;
- automatic model routing, best-of-N package generation or LLM-as-judge gates;
- a baseline convergence detector, n-gram gate, headline-similarity gate or semantic similarity gate;
- typography auto-fit, persistent LibreOffice daemon or multi-converter failover infrastructure;
- semantic truth validation by Python;
- hard semantic-density/cardinality limits inherited merely from P0.7;
- `_DONE` markers, heading/sub-string completion signals, mutable progress files or duplicate authoritative status objects;
- optionality-only serialization seams, advisory-artifact slots or other unused hooks;
- backward compatibility with P0.7/P0.8 repository topology.

A deleted mechanism MUST NOT return under a more abstract name without a surviving requirement that consumes it.

## 4. Factual, strategic and interpretive authority

### 4.1 Candidate factual authorities

`INV-03` During a frozen run, the only candidate factual authorities are:

- `Work_experience.md`;
- `Education.md`;
- `Other_high_value_information.md`.

They MUST be preserved and hash-bound to the run. No model artifact, prior package, personality profile, generated index, research report or baseline may create facts or raise claim ceilings.

Known source-maintenance uncertainty does not make the authorities unusable. Where a source does not establish exact scale, lifecycle, result, ownership or formal mandate, the package MUST use the documented lower claim ceiling or omit the precision. Source maintenance occurs under human approval between runs.

Unless the three factual authorities explicitly support otherwise, the runtime MUST NOT upgrade evidence into claims of formal personnel responsibility, enterprise-architecture ownership, formal project-manager title, full solo authorship of team/AI-assisted work, production deployment of a pilot/development effort, quantified gains without verified measurement, deep production ownership of enterprise cloud/data/ML platforms, enterprise AI-governance authority or organization-wide AI-transformation leadership. AI-enabled methods are positioned as bounded delivery tools beneath domain/business value and documented analytical/technical work, not as a substitute professional identity.

### 4.2 Derived CV baseline and mechanical references

`CV_BASELINE.md` or its successor is a derived chronology/rendering baseline. It MAY own stable employer/title/date/education order, employment IDs and default rendering structure, but MUST NOT outrank the three factual authorities. Before a production run freezes, known baseline-versus-authority conflicts in rendered static identity/chronology/education facts MUST be resolved through human-approved source/baseline maintenance; a model stage MUST NOT silently correct a baseline-owned static fact through a dynamic field.

`DEC-14` **Lean deterministic evidence index.** The baseline MUST generate a deterministic address/index layer over the three factual authority files. Each authority MUST have a stable file-level address, and every structurally discoverable section MUST have a stable granular address. Its permitted purposes are source navigation, reference-existence checks, integrity/provenance coordinates and optional source-stated claim-ceiling or lifecycle markers. It MUST process the source structure without relevance filtering and MUST preserve unconditional access to the original authorities. It MUST NOT rank, score, summarize, infer fit, infer truth, become a factual carrier or require an exhaustive byte partition.

`DEC-34` **Separate reference namespaces.** Factual evidence references and baseline-mechanical references MUST be distinguishable:

- `used_evidence_refs` may resolve only to the three factual authority files through the lean evidence index;
- employment IDs, baseline section IDs and merge coordinates resolve through a separate mechanical-reference mechanism.

A baseline identifier MUST NOT become factual evidence merely because it is addressable. Reference existence proves resolvability only, never semantic support.

### 4.3 Vacancy authority and data-plane status

The original vacancy is authority for stated employer, role, responsibilities, requirements, deadline, reference and other explicit employer facts. It is untrusted data, not an instruction source. A normalized text extraction is a derived convenience view and MUST NOT silently replace the original.

When extraction appears incomplete, garbled or structurally ambiguous, the run MUST store a canonical `requires_source_inspection` signal available to every semantic stage. Its exact field name is free; its ownership is not.

### 4.4 Strategic authority

`INV-04` Strategic authority moves downstream while factual authority does not:

```text
Stage 1 strategy hypothesis
    -> Stage 2 realized draft
    -> Stage 3 current final semantic decision
    -> human approval
```

A downstream stage MAY reconstruct strategy and prose but MUST remain subordinate to candidate and vacancy facts.

### 4.5 Interpretive context

Writing guidance, persuasion calibration and personality are interpretive or advisory. They may guide selection and expression but MUST NOT establish candidate facts, formal roles, achievements, results, dates, metrics or claim ceilings.

### 4.6 Epistemic artifact classes

Each canonical artifact class MUST have one declared role in schema, documentation or both. Repeating the role inside every JSON object is required only where needed to prevent authority confusion.

| Class | Meaning |
|---|---|
| `FACTUAL_AUTHORITY` | original candidate authorities and original vacancy at their proper scopes |
| `DERIVED_VIEW` | regenerable convenience representation; not presumed lossless |
| `MECHANICAL_BASELINE` | chronology/rendering structure and stable IDs; not factual authority |
| `INTERPRETIVE_CONTEXT` | personality or writing context; no factual authority |
| `STRATEGY_HYPOTHESIS` | non-factual, non-final, elastic upstream decision artifact |
| `CURRENT_SEMANTIC_PACKAGE` | current model-authored package, subordinate to facts and human approval |
| `OPERATOR_TRIAGE` | repair-scope recommendation, not a quality fact |
| `AUDIT_ONLY` | history and diagnostics; never current truth |

Convenience views MUST NOT be called lossless unless that scope is mechanically demonstrated.

## 5. Run lifecycle, freeze and branching

### 5.1 Pre-freeze operator input

The human approves opportunities, assigns stable job identities, classifies each as `CORE` or `EXCEPTION`, assigns clusters/order/priority, and identifies source files. The operator input MAY be CSV, spreadsheet or another simple editable format. It is compiled into the run manifest; it is not itself a second run authority after freeze.

The core inventory MUST NOT require generalized platform/channel fields. Human notes MAY capture irregularities without driving core schemas.

### 5.2 Immutable run authority

`DEC-40` **Immutable run and branch-on-reopen.** Each frozen run has one canonical manifest and one immutable `run_id`. After freeze, no operation may mutate in place:

- the expected approved jobs or their `CORE`/`EXCEPTION` classification;
- candidate-authority or vacancy hashes;
- policy, schema, stage-instruction or personality-setting snapshot;
- template/master or evidence-index hashes;
- other canonical run-level authority.

There is no same-run `amend`, manifest-version lineage engine or history replay.

### 5.3 Manifest semantics

`DEC-08` **Expected sets from one manifest.** Every approved opportunity MUST appear in the immutable manifest, and the current core and exception expected sets MUST derive from its job entries. Directory discovery or a separately maintained expected-set object MUST NOT define completeness.

`CTR-01` The run manifest MUST contain, directly or by unambiguous derivation:

- `run_id` and optional `parent_run_id`;
- specification and schema revisions;
- freeze timestamp;
- hashes/versions for the three candidate authorities, CV baseline, stage instructions, settings, schemas, templates and deterministic evidence index;
- one entry for every approved opportunity with stable job identity, employer/title identity, source location/hash, class, cluster, sequence, human priority and any `requires_source_inspection` signal;
- enough information to derive the expected core set and exception set without directory discovery.

The manifest MUST store facts and frozen configuration, not semantic conclusions, quality scores or progress.

### 5.4 Reopen as a child run

To change any frozen-run element, the system MUST create a new run with a new `run_id` and `parent_run_id` referencing the prior run. The original MUST remain untouched.

The implementation MAY copy, link or reference prior files efficiently. Prior semantic artifacts MAY be offered as context or reused only after explicit validation against the child manifest. A deterministic branch operation MAY create a child-local copy and rebind identity/hash metadata without changing the semantic payload only when every content-governing input is proven identical; otherwise the owning semantic stage must regenerate/adopt it. No artifact becomes current in the child solely because it existed in the parent.

Branching SHOULD be a simple operator action; the human SHOULD NOT manually reconstruct the run.

### 5.5 Job transaction

`DEC-06` **Fresh job-centric runtime.** Current semantic artifacts and deterministic outcomes MUST be organized and operated job-centrically rather than moved through a stage-conveyor topology. Exact directories remain implementation freedom.

`INV-05` A job is the unit of persistence, validation, failure containment, semantic restart and rendering. A job MUST persist its current artifact before processing moves to the next job. Failure in one job MUST NOT mutate, erase, block or demote another valid job.

### 5.6 Idempotency and atomicity

Deterministic operations MUST be safely rerunnable. Writes that could leave misleading partial files MUST use temporary output and atomic promotion where the target filesystem supports it. A failed replacement MUST preserve prior valid outputs. No command may silently fall back to stale output.

Target filesystem behavior is verified by `GATE-08`.

## 6. Stage topology, clustering and human initiation

### 6.1 Three-stage topology

`DEC-19` The core semantic route is:

1. **Stage 1 — Decision Architecture:** strongest available reasoning role (`SOL_CLASS`).
2. **Stage 2 — Native Package Writer:** strongest cost-effective native-writing role (`TERRA_CLASS`).
3. **Stage 3 — Elastic Final Writer / Review:** strongest available reasoning/final-writing role (`SOL_CLASS`).

No fourth standard semantic stage exists.

### 6.2 Manual execution boundary

Each semantic stage is a manually initiated model chat. Deterministic code MAY prepare context, validate artifacts, render documents and derive status, but MUST NOT call models or autonomously advance semantic stages.

A model MAY invoke local validators and repair its artifact in-session when the chosen surface supports it. The runtime does not depend on that capability; `GATE-01` verifies the operator flow.

### 6.3 Human clusters and order

`DEC-12` Clusters, sequence and priority are human-assigned and frozen in the manifest. For an approximately 40-job batch, roughly five clusters of about eight jobs, with a normal range around 6–10, is an implementation starting default rather than a normative constant.

`DEC-13` The baseline has no model-generated cluster plan, Priority A/B fit prediction or differentiated writing treatment. Human priority and deadlines MAY affect order only.

Each cluster-stage chat processes jobs sequentially without routine between-job confirmation. The chat MUST reset to the current job identity and inputs before producing that job’s artifact.

### 6.4 Cross-job isolation

Hard controls are:

- job-local write roots;
- exact run/job/employer/title identity validation;
- explicit current-job reset/reload protocol;
- persistence before moving on.

These controls prevent state/file contamination. They do not prove zero semantic carryover inside a shared chat. Semantic convergence and position effects are observed in the pilot and `EXP-01`/`EXP-07`; no baseline detector is built.

### 6.5 Continuation

If a cluster-stage chat is interrupted or context-exhausted, the operator MUST:

1. start a fresh chat with the same stage instruction and frozen policy;
2. identify the run and cluster;
3. use current derived status to find the next unfinished or blocked job;
4. load only that job’s required inputs;
5. continue from current disk state.

Completed jobs’ full artifacts MUST NOT be reloaded merely to reconstruct chat history. Remembered chat position is never authoritative.

## 7. Canonical artifacts and current-state model

### 7.1 Artifact inventory

`CTR-02` A conforming implementation MUST provide the following semantic roles, though exact filenames and directories are free:

| Artifact | Role | Owner | Authority/current-state use |
|---|---|---|---|
| operator batch input | pre-freeze human input | human | compiled, then subordinate to manifest |
| run manifest | frozen run authority | deterministic freeze operation | canonical expected set, hashes and identities |
| original vacancy | employer factual source | human/freeze | authoritative data-plane input |
| normalized vacancy / job context | derived convenience view | deterministic code | optional; never factual replacement |
| evidence index | deterministic factual address map | generator | reference resolution/navigation; no semantic authority |
| strategy | Stage-1 hypothesis | Stage 1 | current if mechanically valid and not stale |
| draft package | realized draft | Stage 2 | current if mechanically valid and not stale |
| final package | current semantic package | Stage 3 or later normal stage restart | rendering source, subordinate to facts/human |
| review | operator triage | Stage 3 | current triage only when paired with current final |
| current failure/blocking record | current mechanical failure state | validator/operator tooling | status derivation; not history replay |
| rendered DOCX/PDF | employer-facing artifacts | deterministic finalizer | derived from current final + masters |
| render report | deterministic render evidence | finalizer | current render-state source |
| status/queue | derived view | status tooling | disposable, never authoritative |
| human pilot log | persistent evaluation record | human | not regenerated or consumed as production authority |
| history | audit-only superseded artifacts/diagnostics | runtime | never replayed as current state |

`INV-09` **Stage-scoped write ownership.** Stage 1 may write/replace only the current strategy; Stage 2 only the current draft; Stage 3 only the current final package and review. No stage may mutate an upstream artifact in place. Replacing an upstream artifact requires a separately initiated execution of its owning standard stage, followed by normal staleness rules. Deterministic tooling alone owns manifest, indexes, current failure records, render reports, derived views and employer-document generation. A deterministic branch operation may copy/rebind an unchanged validated semantic payload under §5.4 but may not author or alter that payload. This model-stage restriction does not remove the human's right to make an explicit validated semantic correction to the final package.

### 7.2 Artifact lineage

Every current stage artifact MUST bind to the immutable run identity/manifest hash and the fixed upstream hashes relevant to that stage. The implementation need not build a dependency engine; fixed comparisons are sufficient.

At minimum:

- strategy binds to manifest, vacancy, factual-authority/index and Stage-1 policy hashes;
- draft binds to current strategy and Stage-2 policy hashes;
- final binds to current draft and Stage-3 policy hashes, while remaining semantically free to reconstruct it;
- review binds to the current final;
- render report binds to the current final, final document date, baseline, template and render configuration.

### 7.3 Static staleness

`DEC-26` Staleness is derived through a small fixed invalidation table, not a runtime graph:

| Current change | Minimum downstream stale scope |
|---|---|
| strategy replaced | draft, final, review, render |
| draft replaced | final, review, render |
| final replaced | review and render |
| review replaced | derived queue only |
| final document date assigned/changed through semantic finalization | render |
| frozen authority, vacancy, policy, setting, schema or template must change | new child run, not in-run mutation |

A stale artifact MAY remain in history/audit but MUST NOT count as current completion. A mismatch in a manifest-frozen authority, vacancy, policy, schema, setting, index or template is a run-integrity failure: tooling MUST fail loudly and require restoration of the frozen bytes or creation of a child run; it MUST NOT normalize that mutation as ordinary in-run staleness.

### 7.4 Current failure representation

`DEC-07` **Current-state derivation, not history replay.** Current production status MUST derive from the immutable manifest, current artifacts and their fixed input hashes, the current failure/blocking record and the current render report. Audit history and human-readable markers MUST have no status authority.

`CTR-03` The system MUST maintain one minimal current failure/blocking representation that status derivation can read without consulting history. It MUST identify:

- run and job;
- affected stage or deterministic operation;
- current classification (`FAILED` or `BLOCKED_MANUAL`);
- diagnostic summary and machine-readable violations where available;
- attempts used and last successful stage where relevant;
- recommended next action;
- the artifact/input hashes to which the failure applies.

A successful current replacement clears or supersedes this current record and MAY move the old record to audit history. Exact schema shape is implementation freedom.

### 7.5 Three orthogonal state axes

`DEC-42` Status MUST preserve three independent axes. They MUST NOT be collapsed into one enum.

#### A. Semantic/operator triage

Valid values, once a current final/review exists:

- `READY` — no known material repair remains beyond normal human skim/approval;
- `CHECK` — bounded local confirmation or edit; no strategic reconstruction;
- `RERUN` — broader model reconstruction is more efficient than local editing.

Triage is based on remaining repair scope, never reason count. It is absent before a current final/review exists.

#### B. Production/mechanical state

The derived state MUST distinguish:

- `NOT_STARTED`;
- `VALID`, with highest current valid stage (`STRATEGY`, `DRAFT` or `FINAL`);
- `FAILED`, where a current attempt/artifact is mechanically invalid and recovery remains available;
- `STALE`, where an otherwise valid artifact no longer matches an allowed-to-change current semantic upstream artifact (strategy, draft, final/review/date relation);
- `BLOCKED_MANUAL`, where configured/simple recovery is unavailable or exhausted;
- `EXCEPTION`.

The presence of a current valid final is reported explicitly as `semantic_final_available`; it is not inferred from a render file.

#### C. Render state

The render axis MUST distinguish at least:

- not rendered;
- DOCX valid / PDF valid;
- DOCX valid / PDF degraded or absent;
- render failed.

The implementation MAY represent CV and letter components separately. A PDF problem MUST NOT be encoded as a semantic status such as `READY_DOCX_ONLY`.

### 7.6 Axis interaction

- `EXCEPTION` removes the job from core production expectations but not from approved-opportunity reporting.
- `STALE` or `BLOCKED_MANUAL` prevents an artifact from being treated as current completion.
- `READY`, `CHECK` or `RERUN` may coexist with PDF degradation.
- render failure does not invalidate a current semantic final package.
- a `RERUN` label does not itself mutate artifacts or start a workflow.
- history never decides current status.

Derived queue ordering SHOULD place `BLOCKED_MANUAL`/failed, `RERUN`, `CHECK`, `READY`, and exceptions in actionable groups, with human deadline/priority inside groups. Exact display order is implementation freedom.

## 8. Stage 1 — Decision Architecture

### 8.1 Role

Stage 1 answers:

> Which truthful candidate identity, evidence architecture, employer-decision argument and writing direction create the strongest expected interview case for this vacancy?

It is not a miniature letter writer, fit scorer or rejection gate.

### 8.2 Read order

Stage 1 SHOULD:

1. load exact run/job identity and inspect the vacancy first;
2. form a provisional employer problem, selection logic and requirement structure;
3. inspect the deterministic evidence index and open original candidate authorities as needed;
4. observe any `requires_source_inspection` signal and inspect the original source;
5. only after factual grounding, consult the personality profile;
6. select zero to three evidence-bound facets if useful;
7. write and validate the strategy.

This is a debiasing protocol, not a mechanically provable cognition guarantee.

### 8.3 Obligations

Stage 1 MUST:

- preserve every material minimum and important desired requirement without an arbitrary count cap;
- map each material requirement to supported, adjacent, gap or unknown status;
- choose one primary truthful candidate identity and explicit headline hypothesis;
- identify strongest evidence bridges, caveats and claim ceilings;
- identify material objections/gaps and truthful reframes;
- define CV versus letter allocation and dynamic CV emphasis;
- provide a specific motivation bridge;
- keep a materially different counterfactual route when genuinely useful, not as mandatory filler;
- state concise writer guidance and one consolidated avoid-guidance surface;
- preserve Stage-3 elasticity and source escape;
- never veto a human-approved core job, invent facts or assign a numeric fit probability.

## 9. Strategy contract

### 9.1 Canonical representation

`DEC-09` `strategy.json` is the sole canonical strategy representation. A deterministic human-readable view MAY be generated but MUST be marked derived/read-only and MUST NOT be independently authored or consumed as a second truth.

### 9.2 Epistemic contract

`DEC-10` The strategy MUST communicate, in schema or unambiguous metadata:

```text
artifact_role = STRATEGY_HYPOTHESIS
authority = NON_FACTUAL_NON_FINAL
elasticity = ELASTIC
final_writer_may_reconstruct = true
```

No downstream instruction may require semantic compliance with the strategy or justification for deviation.

### 9.3 Minimum semantic surfaces

`CTR-04` The strategy schema MUST be able to represent:

- run/job/employer/title identity and input hashes;
- employer decision problem and likely selection logic;
- primary candidate identity and headline hypothesis;
- shortlist thesis / dominant backbone;
- all material requirements and candidate relation;
- evidence plan with factual refs, roles and claim ceilings;
- objections, gaps and truthful reframes;
- motivation bridge;
- CV direction and application direction;
- consolidated avoid guidance;
- optional counterfactual route and risk notes;
- zero to three selected personality facets with evidence-bound expression guidance;
- explicit source-escape permission.

Optional surfaces MUST be omitted when not useful rather than populated with boilerplate.

### 9.4 Validation boundary

`DEC-33` Hard validation of strategy is limited to mechanical properties:

- parse/schema validity;
- exact identity and manifest binding;
- required epistemic constants where used;
- allowed enums and known IDs;
- factual evidence-reference existence and namespace;
- baseline-mechanical reference existence;
- duplicate/unknown fields where the schema intentionally closes them;
- true technical limits of the generated document/runtime or another explicitly adopted non-channel constraint. Portal/form/channel limits remain outside core validation.

Word counts, requirement counts, evidence-bridge counts, paragraph counts, objection counts and similar semantic-density choices MUST NOT be hard failures merely for exceeding historical defaults. The system MAY provide soft guidance or warnings. No hard cap may truncate a material employer requirement.

The locked zero-to-three personality facet bound is mechanically enforceable because it defines the interface, not semantic density.

## 10. Personality interface

### 10.1 Default and role

`DEC-35` Personality is ON by default from the first P0.9 baseline and MUST be implemented as a real semantic-quality feature, not a dormant stub.

The rich personality source is `INTERPRETIVE_CONTEXT`. It MUST NOT create candidate facts, raise claim ceilings, override vacancy/candidate evidence or appear as typology jargon in employer-facing text.

### 10.2 Stage handoff

Stage 1 MAY select zero to three facets after factual grounding. Zero is valid. Each selected facet MUST identify a stable/plain-language facet, supporting factual evidence refs and an expression ceiling. It SHOULD also state vacancy relevance, intended employer interpretation and any material misread risk or expression guardrail.

Stage 2 MUST receive only the distilled selected guidance needed for writing, not the full profile when the distilled handoff is sufficient. Stage 3 MAY suppress, reinterpret, replace or ignore every personality-conditioned element.

### 10.3 Mechanical and semantic checks

Mechanical validation MAY enforce the zero-to-three bound, reference existence and absence of closed-set typology/private tokens. It MUST NOT decide whether a trait is authentic, persuasive or relevant.

Professional text MUST use ordinary work language. Generic style phrases such as `brenner for` are semantic guidance issues and MUST NOT fail deterministic validation merely because the literal string appears.

## 11. Stage 2 — Native Package Writer

### 11.1 Role and inputs

Stage 2 turns the strategy into a complete native Bokmål package. It receives the vacancy, current strategy, writing/persuasion policy, targeted factual evidence/source access, CV baseline/merge contract and distilled personality guidance.

Stage 2 MAY reopen original authorities. It SHOULD follow the strategy strongly but MAY make a bounded correction when the strategy is contradictory, unwriteable or clearly weak. Any writer note is diagnostic, not a competing strategy.

### 11.2 Draft package

`CTR-05` The draft package MUST contain only current dynamic semantic content and private provenance, conceptually:

- exact run/job identity and input hashes;
- a non-empty factual `used_evidence_refs` array;
- CV headline;
- CV profile;
- competency selection/order/wording;
- employment bullet replacements keyed by known employment ID;
- complete application letter content;
- optional bounded writer note.

It MUST NOT duplicate static chronology as model-owned truth, contain portal fields, contain language/output-mode branches, or expose private references in employer-facing text.

### 11.3 Completion

Stage 2 is complete only when the current draft passes deterministic validation. A filename, heading, chat message or marker is never completion.

---

## 12. CV and application contracts

### 12.1 Dynamic CV ownership

`DEC-23` The baseline owns stable chronology, formal employer/title/date/education identity and order. Model-authored dynamic zones are:

- headline;
- profile;
- competencies;
- employment bullet sets.

The model MUST NOT add/delete employment identities or mutate formal title, date, degree, institution or other baseline-owned identity through dynamic output.

### 12.2 Employment replacement semantics

An employment override is keyed by a known baseline employment ID. When present, its bullet array fully replaces the rendered default bullet array for that employment. There is no append, positional merge or hidden mixture.

Absence of an override means use the baseline default for that employment. A present empty replacement has the explicit meaning “render no bullets for this employment” and SHOULD trigger a quality warning, not an automatic fallback. This removes ambiguity without making a historical minimum count normative.

### 12.3 CV quality doctrine

The CV MUST be materially vacancy-specific, preserve chronology, foreground the strongest decision-relevant evidence, distinguish personal and team contribution, preserve lifecycle/claim ceilings and avoid unsupported seniority or authority inflation.

Competency and bullet counts are soft editorial choices. No historical P0.7 count is a hard P0.9 rule unless a verified generated-document/runtime constraint requires it.

### 12.4 Application letter

The letter MUST be a complete, coherent Bokmål employer-decision argument that complements rather than repeats the CV. It SHOULD:

- establish one dominant candidate backbone;
- focus disproportionate attention on the top employer problems and strongest evidence;
- connect prior work to future employer value;
- express motivation through problem/work fit;
- handle material gaps honestly when useful;
- remain natural, precise and restrained rather than translated or hype-driven.

Opening/body/closing structure, paragraph count and one-page convention are guidance, not schema limits. Explicit employer technical limits, when separately known to the human, remain hard for the human submission activity but do not create core channel machinery.

### 12.5 Page behavior

`DEC-24` Sparse CVs MAY be one page; normal/dense CVs will often be two. Page count, paragraph count and typography are normally review/editorial signals. A document fails mechanically only when unusable, corrupted, clipped beyond acceptable use or subject to a true explicit external constraint. P0.9 MUST NOT delete decision-relevant content merely to satisfy an inherited proxy page rule.

## 13. Stage 3 — Elastic Final Writer and review

### 13.1 Fresh view and inputs

Stage 3 SHOULD inspect vacancy and relevant factual evidence before strategy and draft, then read upstream artifacts. It MAY source-escape at any time. It SHOULD receive the distilled selected personality guidance, not the full profile by default, and MAY suppress, replace or ignore that guidance entirely.

### 13.2 Elastic authority

`INV-06` Stage 3 is `ELASTIC` within immutable truth ceilings. It MAY:

- change headline and primary identity;
- replace evidence selection;
- choose a counterfactual strategy;
- alter CV profile, competencies and employment bullets;
- rewrite the entire application;
- change argument order, emphasis and personality-conditioned expression;
- recover evidence omitted upstream.

It MUST NOT invent support, exceed claim ceilings, mutate factual authorities or treat validator success as proof of truth.

A known unsupported or inflated upstream claim MUST be repaired before final save. It MUST NOT be shipped under `CHECK`.

### 13.3 Final package

`CTR-06` The final package uses the same employer-facing semantic shape as the draft, plus final-stage metadata and the eventual canonical document date. It is the sole semantic source for rendering and is subordinate to factual authorities and human approval.

`DEC-25` Final `used_evidence_refs` MUST be non-empty and synchronized to the evidence actually used after Stage-3 reconstruction. The array is a flat private audit surface. Stage 3 and the human own semantic support/coverage; code proves only allowed-source resolvability and hash consistency.

### 13.4 Review

`CTR-07` The review artifact MUST contain:

- exact run/job binding and final-package hash;
- one triage value: `READY`, `CHECK` or `RERUN`;
- concise reasons and recommended actions;
- known limitations relevant to human approval;
- optional diagnostic notes such as material strategy change or repaired upstream claim.

Reason count MUST NOT determine triage. Implementations SHOULD display no more than the few highest-priority reasons, ordinarily about three, while preserving enough diagnostic detail to act.

### 13.5 RERUN meaning

`DEC-37` `RERUN` is an operator triage judgment only: broader model reconstruction is preferable to local human editing. It does not create a fourth stage, special schema, state machine, strategy-mutation lifecycle or automatic action. The human chooses a normal restart point and initiates the corresponding standard stage(s).

## 14. Validation and diagnostics

### 14.1 Validation classes

`INV-07` Three classes remain separate:

| Class | Owner | Effect |
|---|---|---|
| mechanical boundary | deterministic code | artifact invalid / render or state failure |
| semantic truth and attribution | models + human | repair before approval; known material defect cannot ship |
| soft quality | models + human | edit, `CHECK`, `RERUN` or later calibration |

No mechanical check may be represented as proof of factual truth, relevance, naturalness, persuasive quality or correct semantic support.

### 14.2 Complete mechanical scope

Deterministic code MAY enforce only genuinely mechanical properties, including:

- schema and parse validity;
- exact run/job/employer/title identity;
- expected-set membership;
- immutable source/input hashes;
- known factual evidence IDs and allowed source namespace;
- known mechanical employment/baseline IDs;
- allowed roots, path traversal/symlink/reparse handling, file type and size;
- duplicate IDs and intentionally forbidden unknown fields;
- template-map/control/placeholder mechanics;
- no known private/control tokens or internal paths/IDs in employer-facing fields;
- DOCX/PDF existence, openability, nonzero size and extractability where applicable;
- static input-hash/staleness relations;
- true technical limits of the generated document/runtime or another explicitly adopted non-channel constraint. Portal/form/channel limits remain outside core validation.

Lexical checks MUST be narrow and high precision. A stock phrase or ordinary employer word MUST NOT fail merely because it appears in a style-warning list.

### 14.3 Diagnostics

Validators SHOULD report all independently detectable violations in one run where practical. Diagnostics MUST identify the file/artifact, field or location, violated contract, expected condition and observed value. Failures MUST be visible and nonzero at the command level.

### 14.4 Reference semantics

Mechanical reference validation proves only:

- the ID exists;
- it belongs to an allowed authority namespace;
- source/index hashes match the run.

It does not prove that every factual implication is covered or that the evidence supports the wording. Stage 3 MUST update final refs; the human MUST verify material claims before approval.

## 15. Repair, retry, blocking and partial success

### 15.1 Mechanical correction

When a selected model surface supports local validation, a model MAY perform a visible same-session correction and revalidation. One correction attempt is the initial implementation default. The exact count is tunable and not architecture. The validator MUST NOT call the model.

### 15.2 Semantic retry setting

`DEC-36` If `GATE-11` confirms a clean implementation within the manual-chat model, settings SHOULD expose:

```text
retry_start_stages = [3]
```

Each array entry identifies the earliest standard stage to restart for that attempt, proceeding through Stage 3. Examples:

- `[3]`: one Stage-3-only retry;
- `[3, 2, 1]`: Stage 3; then Stage 2→3; then Stage 1→2→3;
- `[]`: no configured semantic retry.

The initial default is `[3]`. This is an implementation setting and may be tuned for future/child runs without a specification amendment; the value frozen into an existing run MUST NOT change in place.

The setting MUST NOT trigger model calls or create an orchestration engine. It may at most scaffold/operator-route the next manually initiated standard stage.

### 15.3 Exhaustion and manual block

If the configured/simple path is unavailable or exhausted, the job MUST become `BLOCKED_MANUAL`, expose run/job, issue, attempts, last successful stage, deterministic diagnostics and recommended next step, then allow independent jobs to continue.

No recovery state machine is required.

### 15.4 Partial success

A run MAY finish with a mixture of valid, degraded-render, stale, blocked, failed and exception jobs. Valid jobs remain usable. Run-level nonzero exit/status MUST NOT delete, hide or demote valid job outputs.

### 15.5 Targeted operation

The implementation MUST support job-targeted validation, semantic context preparation, finalization and rerendering without modifying unrelated job outputs. Exact command spelling is free.

## 16. Rendering, dates, templates and human edits

### 16.1 Normal target and semantic/render separation

Normal target deliverables per core job are:

- CV DOCX;
- CV PDF;
- application-letter DOCX;
- application-letter PDF.

`DEC-41` Valid CV and letter DOCX outputs are the minimum conforming employer-document result. Automated PDF is a target, not a semantic precondition. If both DOCX outputs are valid and automated PDF conversion fails for either document, the semantic package MAY remain `READY` or `CHECK`; render state MUST show PDF degradation and the human MAY export PDF manually.

A PDF conversion failure MUST NOT demote a valid semantic package or create a semantic status variant.

### 16.2 Render transaction

`DEC-21` One job is the render transaction and each document result is independently verified. The finalizer MUST:

1. validate current final package/review and document date;
2. merge baseline plus dynamic CV zones with full replacement semantics;
3. fill the CV and application masters from one canonical template map;
4. unwrap/remove transient controls and assert no unresolved control/placeholder remains;
5. validate DOCX structure;
6. write to a temporary job path;
7. attempt PDF conversion under isolated converter state;
8. verify each produced document independently;
9. atomically promote successful outputs without destroying prior valid outputs;
10. write a render report and continue other jobs on failure.

The default converter invocation granularity is one isolated invocation per document until `GATE-04` proves a simpler per-job invocation preserves observability and isolation. No persistent daemon is permitted.

### 16.3 Template and OOXML posture

`DEC-30` P0.7 assets are implementation capital, not mandatory architecture. The Step-2 builder MUST inspect the actual masters and may reuse the proven non-data-bound SDT fill→unwrap→assert-no-SDT technique only if `GATE-02` confirms fit.

Delivered documents MUST contain no unresolved data-bound/transient control or placeholder. Unknown, duplicate or missing required template controls MUST fail preflight rather than be ignored.

### 16.4 Document date

`DEC-38` The employer-facing document date becomes canonical when the final semantic package is explicitly finalized/approved for first rendering. It MUST be stored with the current final semantic package or co-owned metadata, not the initial run manifest. A pure rerender MUST preserve it. A semantic edit requiring a new date is an explicit re-finalization, not an incidental render side effect.

### 16.5 Parseability

`DEC-39` Critical identity/contact and logical reading order MUST be successfully extractable from representative DOCX/PDF outputs. Body-flow duplication is not intrinsically required. Step 2 MUST inspect and test the actual masters; content is moved or duplicated only if `GATE-06` shows the outcome is not achieved.

Generic ATS folklore MUST NOT override actual master/parser evidence.

### 16.6 Human edits and overwrite protection

The canonical semantic source remains the structured final package. Semantic edits SHOULD be made there and rerendered. A human MAY explicitly edit that final package, but it MUST pass the same mechanical validation, preserve/update factual references, and undergo explicit semantic re-finalization before its outputs are treated as current.

A human-edited DOCX is a post-pipeline submission artifact. Deterministic rerender MUST NOT silently overwrite it. The implementation MUST provide a simple no-clobber/force or alternate-destination behavior; it MUST NOT build document version management.

### 16.7 Render verification

Verification is document-specific, not a single universal string list. At minimum:

- CV checks candidate identity, headline, expected chronology anchors and absence of private/control material;
- letter checks candidate identity/contact as appropriate, employer/title addressing and absence of private/control material;
- every produced file is nonempty and openable;
- no unresolved placeholders/SDTs remain;
- text is extractable/selectable where expected;
- representative sparse/normal/dense fixtures receive visual QA for clipping, substitution, glyphs, page balance and blank pages.

## 17. Security, privacy and external-action boundary

### 17.1 Control plane and data plane

`DEC-27` Control-plane material comprises this specification, frozen settings/manifest, stage instructions, schemas/validator policy, authority definitions, write permissions and the submission boundary. Data-plane material comprises vacancies, extracts, candidate content, personality, model artifacts and operator notes.

Data-plane content may inform reasoning but MUST NOT change permissions, authority, expected jobs, validation rules, run identity or external-action policy.

### 17.2 Local deterministic tooling

Deterministic tooling MUST:

- make no network requests;
- make no model calls;
- write only under approved generated/run roots;
- protect authority and policy inputs from stage writes;
- reject traversal and deliberately handle symlinks/reparse points;
- avoid executing macros, embedded objects or vacancy-supplied code;
- minimize personal data in logs and diagnostics.

### 17.3 Prompt-injection posture

Vacancy text is employer content, not operating instruction. Instruction/data separation, least privilege, no autonomous external action and human approval are the controls. No artifact may claim prompt injection is solved or prevented.

### 17.4 Privacy and selected model surface

Before production, `GATE-10` MUST verify current account/surface retention, training, file access, context and privacy behavior. These volatile facts belong in settings/runbook, not this architecture.

### 17.5 Human irreversible authority

Only the human may approve final truth/semantics, choose whether to submit, enter portal data, attach credentials, contact employers or perform any irreversible external action. The human also owns opportunity selection, source maintenance between runs, cluster/order/priority, exception/drop/restart choices and product-quality scoring.

Deterministic tooling MUST own state reconciliation, missing-expected-job detection, hash checks, rendering diagnostics and queue derivation. The operator MUST NOT be required to synchronize state files, reconstruct chat position, repeatedly re-enter candidate facts or confirm every job between sequential generations.

## 18. Evaluation architecture and pilot

### 18.1 Three distinct loops

`INV-08` Evidence loops MUST remain separate:

1. **A — Engineering conformance:** deterministic contracts, state, isolation, merge, rendering, security and environment behavior.
2. **B — Real product baseline:** actual package quality, truth, effort and tail behavior on real jobs and intended model roles.
3. **C — Causal experiments:** uncertain enhancements or tunings after a trustworthy baseline exists.

Engineering test success MUST NOT be cited as semantic quality evidence. A causal experiment MUST NOT be required merely to prove baseline correctness.

### 18.2 Pre-production sequence

Before broad production:

1. freeze this architecture;
2. complete Step-2 target-environment gates;
3. pass a one-job deterministic vertical slice with valid and adversarial fixtures;
4. run two real jobs through all three semantic stages and rendering;
5. run one representative cluster pilot;
6. only then process the remaining batch.

The vacancy inventory may identify operational exceptions but does not reopen product policy automatically.

### 18.3 Persistent pilot log

Human measurements MUST live in a separate persistent human-owned log, not in regenerable status or queue files. Per job, record as useful:

- human overall quality score;
- submit-ready yes/no;
- known factual corrections;
- total human minutes through submission;
- Stage-3 triage and actual repair scope;
- cluster position;
- retry/rerun action and result;
- notable convergence/context/render failure;
- submitted/dropped outcome.

Runtime production logic MUST NOT consume the human quality score.

### 18.4 Product reporting

For a representative cluster and later batch, report:

- raw ordered human scores, median, mean and `Q_happy` with rounding stated;
- total approved, core, exception, human-scored core, core-without-evaluable-final and submitted-known counts;
- `READY`/`CHECK`/`RERUN` and mechanical/blocking counts;
- median/distribution of human minutes per submitted package;
- truth/attribution defects;
- review-load and weak-tail capture together;
- descriptive cluster-position effects;
- cost at the stage-chat/run level where it actually arises.

Historical applications or conversion rates are not a calibrated baseline.

### 18.5 Truth guardrail and Stage-3 observation

Approved/submitted final packages MUST have zero known material truth or attribution defects. Caught-and-repaired upstream defects are process diagnostics, not final failures.

The pilot MUST NOT require Stage 3 to perform a dramatic reconstruction. If a genuine opportunity occurs, observe whether Stage 3 repairs it; otherwise record `N/A`. Synthetic tests prove permission/contract, not product frequency.

### 18.6 Human-evaluated quality

Employer specificity, backbone coherence, evidence strength, CV/letter complementarity, natural Bokmål, persuasion and handling burden require human/model judgment. They are not Python acceptance checks.

Human scores are noisy calibration signals. At small `n`, raw scores, qualitative notes and material differences outrank fine-grained averages or claims of statistical precision. Blinding is not a baseline requirement; it MAY be used in a specific low-friction experiment when it improves attribution.

## 19. `STEP2_VERIFY` gates

Every gate below has a safe frozen posture. Passing or failing a gate may change implementation details named in the gate without a specification amendment; it may not change user-locked product policy.

### `GATE-01` — Stage surface and same-session validation

- **Empirical question:** Can the selected Work/Desktop/Codex surface read the run, edit only permitted job artifacts, execute local validators and revalidate in-session reliably?
- **Why architecture need not guess:** Manual stage initiation and validator-before-completion remain valid with either in-session or operator-mediated execution.
- **Method:** Run one deliberately invalid strategy and one invalid package through validate→diagnose→repair→revalidate; test continuation after interruption.
- **Safe posture:** Assume operator-mediated validation and continuation status handoff.
- **Pass consequence:** Document the in-session workflow and use it for bounded correction.
- **Fail consequence:** Human runs the validator and supplies the full diagnostic; continuation starts from derived status. No model orchestrator is added.
- **May change without amendment:** Operator instructions and surface-specific commands.
- **Re-adjudication trigger:** No available manual flow can preserve job-local persistence and the human-effort envelope without materially changing the execution boundary.

### `GATE-02` — Actual P0.7 masters and OOXML technique

- **Empirical question:** Do the supplied masters match the audited non-data-bound control structure, and does fill→unwrap→assert-no-SDT work on the actual files?
- **Why architecture need not guess:** The contract requires usable DOCX and verified templates, not a particular master or tag implementation.
- **Method:** Inventory controls/tags, data bindings, tables/text boxes, duplicates/missing tags; fill representative content; unwrap; inspect OOXML and open in Word/LibreOffice.
- **Safe posture:** Reuse only after inspection; unknown/duplicate/missing required controls fail preflight.
- **Pass consequence:** Adapt the masters and proven primitives.
- **Fail consequence:** Build minimal replacement masters satisfying the same document contract.
- **May change without amendment:** Master files, tag map and fill library.
- **Re-adjudication trigger:** No practical master can produce both required documents with the frozen semantic contract.

### `GATE-03` — Automated PDF conversion on target Windows

- **Empirical question:** Does the chosen converter work headlessly/reliably with isolated profile, quoted absolute paths, captured diagnostics and independently verifiable outputs?
- **Why architecture need not guess:** Both DOCX outputs are conforming; PDF automation may degrade gracefully.
- **Method:** Convert sparse/normal/dense CV and letter fixtures; force partial/failure cases; verify exit/stderr, file integrity and prior-output preservation.
- **Safe posture:** Both DOCX outputs are required; automated PDFs are attempted but untrusted until proven; manual export is the fallback.
- **Pass consequence:** Mark PDF OK when independently verified.
- **Fail consequence:** Mark PDF degraded, surface manual export action, and continue semantic delivery.
- **May change without amendment:** Converter, invocation command and manual-export runbook.
- **Re-adjudication trigger:** The environment cannot produce usable DOCX or any practical PDF path when PDF is operationally necessary for the batch.

### `GATE-04` — Converter invocation granularity

- **Empirical question:** Can one isolated invocation for both documents expose partial failures and preserve independent output verification as reliably as per-document invocation?
- **Why architecture need not guess:** Job transaction and per-document verification are invariant; process grouping is not.
- **Method:** Inject a one-document failure in combined and separate modes and compare observability/containment.
- **Safe posture:** One isolated invocation per document.
- **Pass consequence:** Combined per-job conversion MAY be used.
- **Fail consequence:** Retain per-document invocation.
- **May change without amendment:** Invocation grouping.
- **Re-adjudication trigger:** Neither grouping can isolate failures and protect prior valid output.

### `GATE-05` — Fonts, glyphs and representative layout

- **Empirical question:** Are target fonts present/substituted safely, Norwegian glyphs correct, and sparse/normal/dense outputs visually usable?
- **Why architecture need not guess:** Font and layout are template/environment facts, not product policy.
- **Method:** Render representative fixtures; inspect `æ/ø/å`, punctuation, wrapping, clipping, blank pages, balance and PDF text selection.
- **Safe posture:** Use a target-installed standard font and soft page guidance.
- **Pass consequence:** Freeze the verified template/font set for a run.
- **Fail consequence:** Change font/layout and rerun fixtures.
- **May change without amendment:** Font and template styling within semantic/parseability contracts.
- **Re-adjudication trigger:** Required content cannot be made readable without changing the semantic document contract.

### `GATE-06` — Parseability and identity/contact placement

- **Empirical question:** Do representative DOCX/PDF outputs expose critical identity/contact, headline, chronology and logical reading order to ordinary extraction/parser tests?
- **Why architecture need not guess:** The frozen requirement is outcome-based; header versus body placement is implementation.
- **Method:** Extract text from both formats, inspect order and test any real target-channel preview available.
- **Safe posture:** Keep actual master layout until evidence shows failure.
- **Pass consequence:** No duplication is required.
- **Fail consequence:** Move or duplicate only the failing critical content into normal flow and retest.
- **May change without amendment:** Placement/layout of critical identity/contact.
- **Re-adjudication trigger:** No reasonable document layout can satisfy both usability and extractability.

### `GATE-07` — Python, dependencies, Unicode and path behavior

- **Empirical question:** Do selected libraries and Python version support schemas, OOXML, PDF inspection, Norwegian filenames/glyphs and long Windows paths reproducibly?
- **Why architecture need not guess:** Libraries and versions are implementation choices.
- **Method:** Reproducible environment install plus valid/adversarial fixtures with Unicode and long paths; verify nonzero failures and diagnostics.
- **Safe posture:** Assume no library capability until the vertical slice proves it.
- **Pass consequence:** Record the locked implementation environment.
- **Fail consequence:** Replace the library or shorten/move the run root without changing contracts.
- **May change without amendment:** Dependencies, versions and internal APIs.
- **Re-adjudication trigger:** The target environment cannot implement required deterministic boundaries with permitted tooling.

### `GATE-08` — Filesystem atomicity and human-edit protection

- **Empirical question:** Do temp-write/rename, synced-path behavior, hash checks and no-clobber protection work on the actual run root?
- **Why architecture need not guess:** The contract fixes atomic/no-silent-overwrite outcomes, not the filesystem location.
- **Method:** Interrupt writes, simulate locked/synced files, directly edit a rendered DOCX, attempt rerender and verify prior-output preservation/explicit force behavior.
- **Safe posture:** Prefer a local non-synced run root; never overwrite in place.
- **Pass consequence:** The tested root MAY be used.
- **Fail consequence:** Move active runs to a local safe root and copy final deliverables outward after completion.
- **May change without amendment:** Run-root location and atomic-write implementation.
- **Re-adjudication trigger:** No available local path can preserve current-state integrity.

### `GATE-09` — Complete deterministic vertical slice

- **Empirical question:** Does inventory→freeze→index→valid/invalid artifacts→validate→merge→DOCX/PDF attempt→render report→derived status/queue work end to end on the target machine?
- **Why architecture need not guess:** This is conformance evidence, not an architecture choice.
- **Method:** One synthetic core job plus adversarial variants, actual authorities/baseline/masters, and output inspection.
- **Safe posture:** No semantic pilot before pass.
- **Pass consequence:** Proceed to two real-job live smoke.
- **Fail consequence:** Fix the implementation; architecture remains frozen unless a true invariant is impossible.
- **May change without amendment:** Internal implementation and libraries.
- **Re-adjudication trigger:** A frozen requirement is mutually impossible on the target environment after substantively different implementation attempts.

### `GATE-10` — Model-role mapping, surface limits and privacy

- **Empirical question:** Which current models/surfaces satisfy `SOL_CLASS`/`TERRA_CLASS`, file/context behavior, effort controls and acceptable retention/privacy posture?
- **Why architecture need not guess:** Roles are stable while commercial names and limits are volatile.
- **Method:** Verify official/current surface facts, run one real-job smoke per role, and document account privacy/retention settings.
- **Safe posture:** No hard-coded product names; Stage 2 MAY use `SOL_CLASS` if no distinct suitable `TERRA_CLASS` exists.
- **Pass consequence:** Record role mapping in settings for the run.
- **Fail consequence:** Remap roles or change the human-selected surface; no stage is removed silently.
- **May change without amendment:** Commercial model names, effort settings and surface-specific limits.
- **Re-adjudication trigger:** No available model surface can perform a required role within truth/privacy/human-control constraints.

### `GATE-11` — KISS feasibility of `retry_start_stages`

- **Empirical question:** Can the retry-stage array be implemented as simple operator scaffolding in the manual-chat workflow without autonomous orchestration or new persistent state machinery?
- **Why architecture need not guess:** Baseline recovery already has manual restart plus `BLOCKED_MANUAL`.
- **Method:** Prototype `[3]` on one failed fixture/job; inspect code/state surface and operator steps.
- **Safe posture:** Default intent is `[3]`, but no large subsystem is built; manual restart remains available.
- **Pass consequence:** Ship the setting and record attempts in the minimal current failure record.
- **Fail consequence:** Omit automated scaffolding, document manual stage restart, and use `BLOCKED_MANUAL` after the bounded path.
- **May change without amendment:** Presence of the convenience setting and its configured array.
- **Re-adjudication trigger:** Recovery burden materially breaks the human-effort envelope and cannot be reduced without changing the manual-execution boundary.

## 20. `STEP3_EXPERIMENT` queue

No experiment below is required for baseline correctness. Results may tune defaults or motivate a later explicit amendment; they never silently override this specification.

### `EXP-01` — Cluster size and position effects

- **Hypothesis:** Smaller or reset clusters reduce late-position quality degradation without excessive human/chat overhead.
- **Control:** Frozen starting default, approximately 6–10 jobs per cluster.
- **Treatment:** Smaller clusters or a mid-cluster fresh chat with otherwise identical roles/policy.
- **Metrics:** human quality, human minutes, triage, material omissions, position trend and prompt burden.
- **Decision rule:** Change the implementation default only if degradation is recurrent/material and the treatment improves net value.
- **Pre-evidence default:** human clusters around eight jobs.
- **Baseline independence:** every job remains an independent transaction at any cluster size.

### `EXP-02` — Personality contribution and facet tuning

- **Hypothesis:** The active 0–3-facet interface improves specificity/authenticity without unsupported inference or overexpression.
- **Control:** Same feature available but Stage 1 intentionally selects zero facets for matched jobs.
- **Treatment:** Normal evidence-bound 0–3 selection.
- **Metrics:** package quality, candidate specificity, employer relevance, unsupported inference, cringe/typology leakage and human edit time.
- **Decision rule:** Tune facet guidance/vocabulary when treatment creates recurrent costs; changing the ON-by-default policy requires explicit user re-adjudication.
- **Pre-evidence default:** personality ON, zero to three facets chosen by relevance.
- **Baseline independence:** zero facets is already valid; factual correctness never depends on personality.

### `EXP-03` — Advisory preparation model

- **Hypothesis:** A bounded job-local advisory preparation pass improves evidence selection or human/model effort beyond deterministic index plus direct source access.
- **Control:** evidence index + direct source → Stage 1.
- **Treatment:** identical control plus source-linked advisory preparation.
- **Metrics:** final package quality, decisive evidence recall, omissions, anchoring, source escape and total effort.
- **Decision rule:** Add no preparation layer unless gains are material and omissions/anchoring are acceptably bounded.
- **Pre-evidence default:** absent.
- **Baseline independence:** Stage 1 always has index and direct sources.

### `EXP-04` — Structured strategy serialization

- **Hypothesis:** Canonical JSON improves mechanical reliability without reducing final quality through field-filling or authority inflation.
- **Control:** current JSON strategy.
- **Treatment:** stable-label Markdown representation of the same semantic contract in a matched test.
- **Metrics:** final quality, malformed artifacts, writer coherence, human inspectability, repair burden and appropriate Stage-3 reconstruction.
- **Decision rule:** A material, repeatable net advantage may justify a later serialization amendment; schema validity alone is insufficient.
- **Pre-evidence default:** canonical JSON plus generated view.
- **Baseline independence:** final-writer elasticity and source authority do not depend on serialization.

### `EXP-05` — Evidence index as navigation aid

- **Hypothesis:** The index improves evidence selection beyond its required address/provenance role.
- **Control:** direct source navigation with valid IDs available for final recording.
- **Treatment:** index-guided navigation plus direct source escape.
- **Metrics:** strongest-evidence selection, omissions, source-open effort and final quality.
- **Decision rule:** Promote/demote navigation guidance only; the lean address layer remains unless an explicit amendment replaces factual reference resolution.
- **Pre-evidence default:** index available, non-ranking and optional as a navigation aid.
- **Baseline independence:** direct source escape is unconditional.

### `EXP-06` — Triage calibration

- **Hypothesis:** `READY/CHECK/RERUN` predicts actual remaining human repair scope well enough to route effort.
- **Control:** Stage-3 triage as frozen.
- **Treatment:** revised triage instructions derived from pilot errors, not a new score.
- **Metrics:** actual repair minutes/type by status, weak-tail capture and review load.
- **Decision rule:** Clarify/tune triage instructions only when misclassification is recurrent and materially costly; any change to the frozen repair-scope meanings requires an explicit normative amendment.
- **Pre-evidence default:** repair-scope definitions in §7.5.
- **Baseline independence:** human approval remains mandatory regardless of status.

### `EXP-07` — Cross-job convergence

- **Hypothesis:** Shared sequential cluster chats create material phrase/identity convergence beyond acceptable professional consistency.
- **Control:** current reset protocol and human spot-check.
- **Treatment:** fresh-chat reset or changed cluster composition; no automatic detector.
- **Metrics:** human-identified genericity, repeated backbone/headline patterns, employer specificity and effort.
- **Decision rule:** Build no detector unless recurrent failure first establishes a precise low-cost consumer; any automation remains advisory unless separately amended.
- **Pre-evidence default:** protocol + observation only.
- **Baseline independence:** hard file/state isolation is already enforced.

### `EXP-08` — Model/effort routing

- **Hypothesis:** Alternative current role-to-model or effort mappings improve net quality/effort.
- **Control:** frozen run mapping.
- **Treatment:** one role mapping or effort variable changed at a time.
- **Metrics:** package quality, truth defects, human minutes, malformed artifacts and cost at the stage-chat level.
- **Decision rule:** Change settings only on material repeatable net gain; stage semantics remain fixed.
- **Pre-evidence default:** strongest reasoning role for Stages 1/3; strongest cost-effective native-writing role for Stage 2.
- **Baseline independence:** roles remain satisfiable by substitutions recorded in settings.

- trigger and evidence;
- old and new rule;
- affected runs/artifacts;
- migration or child-run consequences.

Existing frozen runs remain governed by their frozen specification and manifest. Gate results and implementation-default tuning do not require a normative amendment unless they change a frozen rule. Experiment results may motivate, but never enact, an amendment.
