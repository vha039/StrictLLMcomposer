# Jobbsøk_26 P0.9 — Final Implementation and Verification Contract

**Project architecture:** P0.9  
**Specification revision:** 0.9.0  
**Status:** FROZEN_NORMATIVE  
**Authority:** Subordinate to `P0.9_FINAL_NORMATIVE_SPECIFICATION.md`. This contract introduces no architecture. If any wording differs, the specification governs.

## 1. Step-2 objective

Build a fresh, local-first repository that turns a human-approved opportunity set into validated, reviewable Bokmål CV-plus-letter packages for `CORE` jobs while preserving immutable truth, job-local failure containment, manual semantic execution and manual submission.

The build is complete only when it produces actual evidence on the target Windows machine that the frozen contracts work. A code path that exists but has not been exercised at its trust boundary is `IMPLEMENTED`, not `MECHANICALLY_TESTED`. A deterministic vertical slice is not product-quality evidence; real vacancy/model output and human review are separate.

Step 2 MUST NOT choose or reopen product policy. It MUST implement the frozen baseline, execute `GATE-01`…`GATE-11`, and leave `EXP-01`…`EXP-08` outside baseline correctness.

---

## 2. Required runtime capabilities

The implementation MUST support, through any small task-oriented command surface:

1. validate human batch input and freeze a new immutable run;
2. create a child run from a parent without mutating the parent;
3. generate and validate the lean evidence index;
4. validate each current semantic artifact independently or by job/run;
5. derive current status and an operator queue from current state;
6. merge the CV baseline with dynamic zones deterministically;
7. fill and validate both Word masters;
8. attempt PDF conversion and record per-document render outcomes;
9. finalize or rerender one selected job without touching unrelated jobs;
10. preserve prior valid output on any failed replacement;
11. represent current failure/blocking without reading audit history;
12. protect post-pipeline human edits from silent overwrite;
13. emit dense actionable diagnostics and nonzero exit status on failure;
14. repeat deterministic operations safely without duplicate authoritative state or silent fallback;
15. run with no deterministic model calls, network requests or external actions.

The exact number and spelling of commands are free. A likely operator surface is freeze/branch, validate, status, finalize/rerender and preflight, but Step 2 MUST NOT preserve a command merely because the draft named it.

## 3. Minimum repository roles

Exact paths are free. The active repository MUST make these roles obvious and permission-separable:

```text
authorities/     three factual authority files + derived CV baseline (protected data plane)
context/         rich personality profile (protected interpretive data plane)
policy/          settings, writing/persuasion rules and stage instructions (control plane)
templates/       CV and letter masters + one canonical template map
schemas/         canonical artifact schemas
runtime/         deterministic code and tests
generated/       regenerable evidence index/views
runs/<run_id>/   immutable manifest, per-job current artifacts, renders, audit history
```

Only the current run/job output area is model-writable. Policy, schemas, templates, manifest and deterministic code are control plane. Candidate authorities, vacancy sources, CV baseline and personality are protected read-only data-plane inputs: authoritative or interpretive at their declared scopes, but never instructions or permissions. Every protected input MUST be inaccessible to stage writes.

Historical P0.7/P0.8 material MUST NOT reside in active runtime paths unless an explicit current reference consumes it.

### 4.2 One current artifact rule

There MUST be at most one current artifact for each semantic role per job. Replacements MUST be atomic. Superseded versions MAY move to bounded audit history, but history MUST NOT be required for validation or status.

Stage write permissions MUST be role-scoped: Stage 1 may replace strategy only; Stage 2 draft only; Stage 3 final and review only. A later standard-stage restart may replace that stage's artifact atomically, but downstream stages MUST NOT edit upstream artifacts. Deterministic tooling owns manifest, indexes, failure/render records, derived views and document generation. It MAY copy/rebind a validated unchanged semantic payload into a child run under §6.3, but MUST NOT author or alter the payload.

### 4.3 Epistemic labels

Schema/documentation MUST make the artifact role unambiguous. The strategy MUST explicitly carry hypothesis/non-final/elastic semantics. The implementation SHOULD avoid repeating labels in every object when file class and schema already make the role unambiguous.

Derived vacancy text, job context and CV baseline MUST be labeled `DERIVED_VIEW` or `MECHANICAL_BASELINE`, not lossless unless a defined scope is mechanically proven.

## 5. Minimal schema contracts

The following are semantic minima. Property names and nesting MAY differ, but a builder MUST NOT remove the represented meaning or add unused optionality hooks.

### 5.1 Run manifest

The manifest MUST represent:

```text
run identity
  run_id
  optional parent_run_id
  specification/schema revisions
  frozen timestamp
frozen inputs
  hashes/versions for three authorities, CV baseline, settings, stage instructions,
  personality source/configuration, schemas, evidence index, templates/template map
jobs[]
  stable job identity
  employer/title identity
  original vacancy path/hash
  CORE or EXCEPTION
  cluster, sequence, human priority
  optional inert exception note
  requires_source_inspection signal
```

The expected core and exception sets MUST be derived from `jobs[]`; do not store a second independently maintained expected-set list. The manifest MUST NOT contain semantic progress, quality scores, portal/form state, platform/channel branching, `letter_required`, language branching or mutable status.

### 5.2 Evidence index

The index MUST provide one stable file-level address for each factual authority and stable entries for structurally discoverable sections. Each factual entry MUST include enough to resolve its address to one of the three factual authority files:

```text
evidence_id
source_file
heading/path or stable anchor
section/content hash or other deterministic integrity coordinate
optional source-stated lifecycle/claim-ceiling marker
```

The generator MUST process the full source structure without relevance filtering. It MUST NOT rank, score, summarize, infer fit, infer truth, require manual curation or assert an exact byte partition. Direct source access remains available even when a passage lacks a convenient granular entry.

`CV_BASELINE` employment/section IDs MUST be validated through a separate mechanical map or schema namespace.

### 5.3 Strategy

The strategy schema MUST represent:

```text
exact run/job/employer/title identity and fixed input hashes
artifact role = strategy hypothesis
non-factual/non-final authority statement
elastic final-writer permission
employer decision problem / selection logic
primary candidate identity and headline hypothesis
dominant shortlist thesis
all material requirements with supported/adjacent/gap/unknown relation
factual evidence plan and claim ceilings
objections/gaps/reframes
motivation bridge
CV direction
application direction
one consolidated avoid-guidance surface
optional counterfactual/risk notes
personality facets[0..3] with evidence-bound distilled guidance
source-escape permission
```

Hard validation MUST NOT impose a maximum number of material requirements or historical word/cardinality limits. Soft warnings MAY be emitted.

### 5.4 Draft and final package

Draft and final SHOULD share one employer-facing semantic schema. It MUST represent:

```text
exact run/job identity and upstream input hashes
source stage / current semantic role
factual used_evidence_refs[] (three-authority namespace only)
CV dynamic content
  headline
  profile
  competencies
  employment overrides keyed by known employment_id
complete application-letter content
optional bounded diagnostic/writer note not rendered to employer
final-only/co-owned metadata
  semantic finalization/approval state
  canonical employer-facing document date once assigned
```

It MUST NOT contain portal answers, platform/channel fields, `letter_required`, language switches, static model-owned chronology, numeric quality/confidence or private evidence refs inside employer-facing text.

The final package is the sole semantic rendering source.

### 5.5 Review

The review MUST represent:

```text
run/job identity and final_package hash
triage = READY | CHECK | RERUN
concise reasons with recommended actions
known limitations
optional material_strategy_change diagnostic
optional upstream_claim_repaired diagnostic
```

No numeric quality/confidence field is permitted. Reason count MUST NOT route status. A human view MAY show only the highest-priority few reasons.

### 5.6 Current failure/blocking record

A minimal current record MUST represent:

```text
run_id, job_id
operation/stage
classification = FAILED | BLOCKED_MANUAL
input/artifact hashes to which failure applies
all detected mechanical violations or render diagnostics
attempts used / configured retry position where relevant
last successful stage where relevant
recommended next action
timestamp for audit display
```

On successful current replacement, this record is cleared/superseded and MAY be archived. Status MUST NOT replay archived events.

### 5.7 Render report

The render report MUST bind to the current final-package hash, document date, baseline/template hashes and render configuration. For each CV/letter format attempted, it MUST record:

- output path/hash;
- command/tool/version where relevant;
- exit code and relevant diagnostics;
- existence/nonzero/openability checks;
- placeholder/SDT/private-token checks;
- document-specific identity/extraction checks;
- final state: OK, DEGRADED or FAILED with limitation/action.

A missing/failed PDF whose corresponding DOCX is valid is `DEGRADED`, not a semantic failure.

### 5.8 Derived status

Derived status MUST expose three axes separately:

```text
semantic_triage: null | READY | CHECK | RERUN
production_state: NOT_STARTED | VALID | FAILED | STALE | BLOCKED_MANUAL | EXCEPTION
highest_valid_stage: null | STRATEGY | DRAFT | FINAL
semantic_final_available: boolean
render_state: component-level DOCX/PDF state or an equivalent orthogonal structure
```

Exact enums/field names MAY differ; the distinctions and interaction rules may not.

### 5.9 Pilot log

The human pilot log MAY be CSV, spreadsheet or another durable file. It MUST be stored outside regenerated views and SHOULD include job ID, human score, submit-ready, corrections, minutes, actual repair scope, submitted/dropped outcome and notes. Runtime production logic MUST NOT consume the human score.

## 6. Authority, hashes and immutable-run behavior

### 6.1 Freeze

Freeze MUST:

- reject duplicate/unsafe job identities and path collisions;
- preserve and hash original vacancy files;
- if a normalized/extracted vacancy view is generated, run deterministic extraction sanity checks, set `requires_source_inspection` when content is missing/garbled/structurally ambiguous, and retain the original as the only employer-fact authority;
- validate that each approved opportunity appears exactly once as core or exception;
- require a recorded human-reviewed baseline-to-authorities reconciliation for rendered static identity/chronology/education facts and fail on a known conflict;
- record all frozen authority/policy/schema/template/index hashes;
- generate the evidence index deterministically;
- create job scaffolding without semantic completion markers;
- fail atomically: no partial frozen run may masquerade as valid.

### 6.2 Every-command checks

Every deterministic operation MUST verify the manifest and relevant frozen hashes before acting. A mismatch MUST fail loudly and recommend creating a child run; it MUST NOT update the current manifest.

### 6.3 Child branch

Branching MUST:

1. create a new run ID and immutable child manifest;
2. record the parent run ID;
3. leave every parent byte untouched;
4. copy/link/reference frozen inputs efficiently where safe;
5. treat parent artifacts as prior context until validated under the child;
6. permit deterministic child-local copy/rebinding only when all content-governing hashes are identical and the semantic payload is unchanged; otherwise require the owning standard stage;
7. clearly report which child artifacts are current, reused, stale or absent.

The rebind operation may update child identity/hash metadata but MUST NOT edit semantic payload. Do not implement same-run manifest versions, event sourcing or an artifact-lineage graph.

### 6.4 Static input binding

Each semantic artifact MUST record or be paired with enough fixed hashes to detect the normative stale relations:

- strategy → manifest/vacancy/authority-index/Stage-1 policy;
- draft → current strategy/Stage-2 policy;
- final → current draft/Stage-3 policy;
- review → current final;
- render → current final/date/baseline/template/render configuration.

A small comparison table/function is sufficient. No general dependency engine.

## 7. State derivation and failure precedence

Status derivation MUST use only current manifest, current artifacts, current failure record and current render report. Before job-state precedence, the command MUST verify all manifest-frozen files/hashes. A mismatch is a run-integrity error requiring restoration or child branching, not ordinary `STALE` state under a silently changed run.

Recommended precedence for a core job:

1. if manifest class is exception → production `EXCEPTION`;
2. if current terminal blocking record applies → `BLOCKED_MANUAL`;
3. if required current artifact input hashes mismatch → `STALE`;
4. if a present current artifact fails validation or current nonterminal failure applies → `FAILED`;
5. otherwise report `VALID` and highest valid stage;
6. expose triage only when current final and review both validate and bind to each other;
7. derive render independently from render report/output verification.

A stale or blocked final MUST NOT be presented as current ready output. A current semantic final remains available even when PDF is degraded. Planting `_DONE`, status prose or a history entry MUST have no effect.

## 8. Validator obligations

### 8.1 Contract

Every validator MUST:

- accept a clearly identified artifact/job/run target;
- return nonzero on mechanical failure;
- report all practical independent violations in one pass;
- identify file, location/field, contract ID, expected and observed condition;
- avoid modifying the artifact unless a separate explicit repair operation is invoked;
- be deterministic for identical inputs;
- make no network or model calls.

### 8.2 Mechanical-only inventory

Implement only checks traceable to the specification:

- schema/parse and intentionally closed fields;
- exact run/job/employer/title identity;
- manifest membership and fixed input hashes;
- factual evidence ID existence and allowed source namespace;
- mechanical employment/baseline ID existence;
- path/root/type/size/symlink/reparse safety;
- template-map and content-control mechanics;
- placeholder/private/control-token/path/ID leakage in employer-facing fields;
- output existence, nonzero size, openability and extraction where applicable;
- document-specific identity checks;
- staleness/static lineage;
- true generated-document/runtime constraints or another explicitly adopted non-channel constraint; never portal/form/channel limits.

Do not implement prose truth, motivation, persuasion, native-language quality, evidence strength or semantic support checks. Do not convert stock/cliché phrase guidance into a regex failure. Typology/private control tokens may be narrowly rejected only when a legitimate employer-facing use is effectively absent and false-positive fixtures pass.

### 8.3 Manual-chat output

Never assume a JSON request guarantees valid JSON. Every model artifact counts only after local validator success.

### 8.4 Reference checks

The reference validator MUST verify only existence, allowed factual source and hash consistency. Tests and documentation MUST state that it does not prove semantic support or exhaustive claim coverage.

## 9. Repair, retry and `BLOCKED_MANUAL`

### 9.1 Mechanical correction

The initial same-session mechanical correction default is one visible attempt. The validator SHOULD surface all violations before that attempt. This default MAY be tuned without architecture revision.

### 9.2 `retry_start_stages`

Execute `GATE-11`. If the feature remains KISS, implement a simple setting with conceptual semantics:

```text
retry_start_stages = [3]
```

It MUST only tell/scaffold the operator which normal manually initiated stage sequence to run next. It MUST NOT call a model, advance automatically, create a retry engine or add a general workflow-state object.

If omitted after a failed gate, the runbook MUST state the manual restart procedure. The current failure record still tracks the current block and recommended action. Any configured array is frozen into the run settings; later tuning applies only to a new/child run.

### 9.3 Exhaustion

When available/simple recovery is exhausted, write/update current `BLOCKED_MANUAL`, keep other jobs processing and surface:

- run/job ID;
- issue and full deterministic diagnostic;
- last valid stage;
- attempts used;
- recommended normal restart or human action.

### 9.4 RERUN

There is no RERUN command contract beyond convenience. A `RERUN` review means the human should initiate one or more ordinary stages at the chosen restart point. Existing artifacts may be supplied as historical context, but no RERUN-specific schema, strategy mutation, invalidation or state machine may exist.

## 10. Partial success, continuation and targeted work

### 10.1 Job isolation

Every finalization/validation operation MUST contain errors at the job boundary. In a multi-job invocation, one poisoned job yields a nonzero overall result while preserving valid outputs and continuing independent jobs where safe.

### 10.2 Continuation artifact

Status MUST expose the next unfinished/failed/blocked job for a selected run/cluster/stage. A fresh chat receives:

- stage instruction and frozen policy;
- run/cluster identity;
- current job identity;
- required current inputs only.

No completed-job transcript or full artifact set is required. The disk state, not chat memory, controls continuation.

### 10.3 Targeted operation

Validation, finalization and rerender MUST accept a job selector or equivalent. Tests MUST prove unrelated output hashes remain unchanged.

### 10.4 Human queue

The queue is a disposable view. It MUST show enough current data to act: identity, production state/highest stage, semantic triage if available, render limitation, concise action/reasons, deadline/priority and output paths. Human measurements MUST NOT be stored in it.

## 11. Evidence-index implementation

### 11.1 Generator

The generator MUST:

- read only the three factual authority files for factual entries;
- use deterministic source-stable or heading/explicit-ID-derived addresses;
- include one file-level root entry per authority and all structurally discoverable sections without relevance filtering;
- preserve source/anchor/hash navigation;
- avoid summaries, rankings, inferred lifecycle/claim ceilings and manual edits;
- regenerate identically for identical inputs;
- keep direct source access available.

It MUST NOT assert that every byte belongs to exactly one entry. It MUST include the file-level root entry; it MAY add a distinct preamble entry as a convenience, but no partition theorem/test is required.

### 11.2 Mechanical baseline map

Implement a separate map/schema for known employment IDs and baseline section identities. A validator MUST reject a factual `used_evidence_ref` that targets this mechanical namespace.

### 11.3 Final refs

Draft/final schemas MUST require a nonempty factual ref array because every package contains factual candidate content. Stage 3 MUST update it after reconstruction. A mechanical nonempty/resolvable check does not replace human claim review.

## 12. Personality implementation

Step 2 MUST ship the personality feature active by default:

1. store the rich profile as protected read-only interpretive data-plane context;
2. make it available to Stage 1 only after vacancy and factual evidence grounding in the stage instruction;
3. validate zero to three selected facets;
4. require factual refs for any facet intended to influence employer-facing expression;
5. generate/pass only distilled guidance to Stage 2;
6. pass only distilled selected guidance to Stage 3 by default and tell it explicitly that it may suppress/ignore every facet;
7. test that zero facets is valid;
8. test that typology/private labels do not leak while ordinary style phrases do not falsely fail.

The implementation MUST NOT add a personality score, candidate ranking, trait memory across jobs or full-profile injection into every stage by default.

### 13.1 CV merge

Implement and test:

- baseline-owned stable identity/chronology/order;
- model-owned headline, profile, competencies and employment bullets only;
- unique known employment IDs;
- absent override = baseline bullets;
- present override = full replacement, including explicit empty replacement;

### 13.2 Application

### 13.3 Single template map

There MUST be one canonical package-to-template map. Code, documentation and tests MUST consume the same map. Duplicate/missing/unknown controls fail preflight.

### 13.4 OOXML

```text
fill expected non-data-bound SDTs
-> unwrap controls
-> assert no w:sdt/transient placeholder remains
-> validate/open DOCX
```

Do not blindly copy P0.7 code. Extract and independently test the minimal primitives.

## 14. Render transaction, degradation and human edits

### 14.1 Transaction

For each selected valid final job:

1. verify manifest/current artifact hashes;
2. assign/verify canonical document date at semantic finalization/approval;
3. merge and generate CV/letter DOCX in a temporary job transaction;
4. verify each DOCX independently;
5. attempt PDF conversion per `GATE-03`/`GATE-04` posture;
6. verify each PDF independently if produced;
7. write render report;
8. atomically promote successful outputs;
9. preserve prior valid files on any failure.

### 14.2 Render-state rules

- Both valid DOCX files are required for a conforming rendered package.
- PDFs are normal targets.
- Both DOCX outputs valid + either automated PDF failed/missing = render degraded, not semantic failed.
- A manual PDF export MAY later update render state after verification.
- Do not add `DOCX_ONLY` product mode or semantic status variants.

### 14.3 Document-specific verification

Do not require every string in every document. Verify:

- CV: candidate identity, headline, representative chronology anchors, no private/control material;
- letter: candidate identity/contact as designed, employer/title addressing, no private/control material;
- both: nonzero/openable, no unresolved placeholder/SDT, expected text extraction and no corruption.

### 14.4 Date

Store the canonical document date in/with the final semantic package when explicitly finalized/approved. A pure rerender reads it and MUST NOT replace it with current date. A semantic re-finalization may explicitly choose a new date.

### 14.5 Human-edit protection

An explicit human edit to the structured final package MUST use the normal final-package validator and semantic re-finalization path; material edits require corresponding factual-reference review. This is not a separate artifact/version subsystem.

Before replacing an existing rendered document, compare expected ownership/hash or use an equivalent safe mechanism. If a human-edited/post-pipeline file would be overwritten, require explicit force or write to a new destination. Do not infer complex document versions from modification time alone; keep the behavior simple and documented.

## 15. Security implementation

The deterministic package MUST have no HTTP/model-client dependency needed by production commands and no employer-contact/submission capability. Tests MUST cover:

- traversal and path-collision attempts;
- symlink/reparse-point escape;
- unsupported/oversized inputs;
- write outside current job/generated roots;
- authority/policy/template mutation;
- vacancy text containing instruction-like content;
- private paths/evidence IDs/control tokens in employer-facing fields;
- macro/embedded-object non-execution;
- logs free of unnecessary personal content/secrets.

A dependency audit MAY permit libraries that themselves have optional networking capability only if production code never invokes it and tests/architecture remain no-network; the simplest implementation SHOULD avoid such dependencies.

## 17. Deterministic test obligations

### 17.1 Tier 1 — before any semantic pilot

1. **Freeze/immutability:** manifest hashes actual sources; mutation makes commands fail; no same-run amend path exists.
2. **Branch:** child run gets new ID/parent link; parent tree hashes remain unchanged; unchanged payload may be rebound only when governing hashes match; changed-input artifacts remain prior context/non-current.
3. **Idempotency:** repeating validation/status/finalization or rerender with unchanged current inputs creates no duplicate authority/progress state, preserves the canonical date and yields the same logical content/state; any unavoidable container metadata variation is documented rather than treated as semantic change.
4. **Identity/path:** duplicate IDs, sanitization collisions, traversal, symlink/reparse, unsupported/oversized files fail loudly.
5. **Stage ownership:** Stage 2/3 attempts to mutate upstream artifacts fail; a normal owning-stage replacement succeeds and produces the fixed stale scope.
6. **Approved set/baseline:** deleted/missing job directory is reported from manifest expectations; exceptions remain countable; a known baseline-versus-authority static identity/chronology/education conflict blocks freeze.
7. **Schema:** valid and adversarial strategy/draft/final/review/failure/render fixtures; diagnostics identify all practical violations.
8. **Current failure:** failed attempt differs from never-started without reading history; success clears current failure.
9. **State axes:** fixtures cover every required production state and PDF-degraded `READY`/`CHECK` combination.
10. **Static staleness:** replacing strategy/draft/final produces exactly the frozen downstream stale scope; no automatic execution.
11. **Evidence namespace:** fabricated factual ID fails; baseline mechanical ID fails in factual refs; valid refs resolve; tampered/frozen index hash mismatch fails the run command and recommends a child run rather than updating in place.
12. **No byte partition dependency:** sources with preamble/unusual headings still index usable sections and direct-source escape remains valid.
13. **CV merge:** exact arrays prove full replacement, explicit empty replacement, absence/default behavior, unknown ID rejection and static chronology preservation.
14. **Leakage:** private paths/evidence IDs/control tokens fail; ordinary phrases including `brenner for` pass mechanical validation.
15. **Personality:** 0 and 3 facets pass; 4 fails; unsupported/missing factual ref fails; typology leakage fails; Stage 2 fixture receives distilled guidance only.
16. **Partial success:** one poisoned job; other outputs and hashes remain unchanged; run result remains visibly nonzero/partial.
17. **Continuation:** fresh-chat context derives next job from current state and excludes completed-job artifact history.
18. **Template preflight:** actual master tag/control map; fill/unwrap; no residual `w:sdt`/placeholder.
19. **Target render:** actual machine produces both DOCX; PDF success or explicit degradation; per-document checks and prior-output protection.
20. **Date/rerender:** first finalization fixes date; pure rerender preserves it.
21. **Human edit:** edited DOCX is not silently overwritten; force/alternate destination works.
22. **Security:** instruction-like vacancy text changes no control state; writes outside roots and network/model calls are absent.
23. **Source inspection:** a deliberately truncated/garbled extraction sets the canonical inspection signal, surfaces the original source to every stage and cannot be mistaken for a clean normalized authority.

### 17.2 Tier 2 — before first full batch

- two real jobs through all semantic stages and rendering;
- malformed model outputs through visible correction/failure;
- sparse/normal/dense visual QA;
- Unicode and long Windows paths;
- interrupted writes and target filesystem atomicity;
- queue grouping and persistent pilot-log separation;
- `retry_start_stages` gate outcome and fallback;
- cluster start/middle/end position logging;
- target privacy/model-role runbook.

### 17.3 Tier 3 — measured polish only

- richer reporting;
- performance improvements against observed bottlenecks;
- optional experiment support only when an experiment is actually approved;
- no historical compatibility work without explicit authority.

Tests MUST create and inspect actual outputs. Silent or expensive failure modes require adversarial fixtures.
