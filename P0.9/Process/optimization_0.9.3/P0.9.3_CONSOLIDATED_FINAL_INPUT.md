## 1. Stage 2 — the critical analysis

The user asked whether Stage 2 is necessary, and if not whether to change or cut it. This is the highest-leverage question in the pass, so it is answered first and with measurement rather than reasoning alone.

### 1.1 What Stage 2 was for

`settings.toml` assigns Stage 2 `TERRA_CLASS` (GPT-5.6 Terra) while Stages 1 and 3 use `SOL_CLASS` (GPT-5.6 Sol). The intent, as the user states it: *"a lower quality model generating a draft… hope being that it would absorb some of stage 3's output token expenditure."*

### 1.2 Measurement: how much of the draft survives

Word-level sequence similarity, draft → final, across every completed run:

| Run | Job | Letter retained | CV retained |
|---|---|---:|---:|
| r20260828-213932 | Avinor | 20.4% | 47.7% |
| r20260828-213932 | Huseierne | 24.2% | 49.1% |
| r20260902-210926 | Avinor | 14.3% | 31.6% |
| r20260902-210926 | Huseierne | 24.8% | 69.1% |
| **r20260905-005939 (treatment)** | Avinor | **92.4%** | **95.1%** |
| **r20260905-005939 (treatment)** | Huseierne | **77.0%** | **95.7%** |
| r20260905-115243 | Avinor | 18.6% | 45.6% |
| r20260905-115243 | Huseierne | 33.0% | 54.6% |
| r20260905-195443 | Avinor | 9.3% | 19.6% |
| r20260905-195443 | Huseierne | 13.7% | 27.2% |

**Excluding the treatment run, Stage 3 discards 67–91% of the letter, median ≈ 79%.**

The treatment run must be excluded, and the reason matters: I authored Stages 2 and 3 as the same model in the same session. That is precisely the configuration the architecture forbids in production (`Spec 313`: each semantic stage is a separately initiated chat). Its 77–92% retention measures self-consistency, not the value of a handoff between two different models. **The outlier is my run, not the others.**

### 1.3 The cost rationale is not merely unmet — it is structurally unachievable

`final_package.json` must be a **complete** package: `cv` and `letter` are both required, and every field must be present regardless of how much was reused. Stage 3 therefore emits the same output volume whether it inherits a perfect draft or none at all.

**A draft cannot absorb any of Stage 3's output tokens, because the artifact contract requires Stage 3 to write the whole thing either way.** The hypothesis was falsified by the schema before any model ran.

What Stage 2 actually costs, per job:

| Item | ≈ Tokens |
|---|---:|
| Stage 2 input (authorities, policies, instruction, prompt, strategy, baseline map) | 86,400 |
| Stage 2 output (`draft_package.json`) | 6,000 |
| Stage 3 reading the draft | 2,500 |
| **Total** | **≈ 94,900** |

Return: roughly a fifth of a letter that Stage 3 would have written anyway, plus one additional human-operated chat session per job.

### 1.4 Stage 2 is the traced defect-injection point

Every fabrication located in this project originated in a Stage-2 draft:

- **D1**, the unsupported PRJ-04 workshops, entered at draft `:46` and Stage 3 *strengthened* the personal attachment rather than removing it.
- **D2**, the unsupported "mest" comparative, entered at the draft and the final retained it.
- In `r20260905-115243`, both drafts invented an "avstemmingsledd" removal and converted "about 50 involved people" into "50 controllere og ledere". Stage 3 repaired those two — but only in the later branch.

So Stage 2 injects fabrications, and Stage 3 catches them inconsistently. A fluent, complete draft is a powerful anchor: it is far easier to lightly edit a confident sentence than to notice that its verb has no source.

### 1.5 Adjudication

**Cut Stage 2.** Not repurpose. The reasoning, in order of weight:

1. **Its purpose is unachievable by construction** (§1.3), so no amount of instruction repair recovers it.
2. **It is the only traced defect-injection point** (§1.4), and removing it removes the anchor that let two fabrications survive into a delivered package.
3. **It costs ~95,000 tokens and one chat per job** for ~21% of a letter.
4. **Repurposing costs more than cutting.** The two credible repurposings both require a schema change, which is forbidden and which cutting does not:
   - *Stage 2 owns the CV, Stage 3 owns the letter* — `package.schema.json` holds `cv` and `letter` in one object, so split ownership inside one artifact collides with `INV-09`'s prohibition on mutating an upstream artifact in place. It would need two artifacts.
   - *Stage 2 produces an evidence dossier* — a different artifact shape, hence a new schema. And once `fetch.py` exists (§3.1), most of the dossier's mechanical work is code, leaving only a support judgment that Stage 3 must make anyway.
5. **Cutting is a deletion**, which is the safest class of change. Every mechanical edit it requires removes a branch rather than adding one.

**The counter-argument, stated fairly.** Two models produce two independent takes, and 21% retention could be read as "Stage 3 mined a fifth of a useful alternative" rather than "79% waste". Model diversity is real and cheap here. I reject it on the evidence: a *draft* is the wrong instrument for diversity because it anchors rather than offers. Where diversity has value it belongs in Stage 1's option set — `counterfactual_route` already exists for exactly this and is currently underused. If the finalizing model wants to preserve diversity, strengthening `counterfactual_route` is the cheaper and safer route.

## 2. Item-by-item response to every user comment

### 2.1 On the evidence index (comment at §2.1)

The user proposed: a CSV ID-list per file plus a path so the model can construct `[core_path]/[filename]` and search for `[ID]`; or better, context files as Python libraries with `fetch.py --ids [...]` returning full text.

**On the ID-list: the user's version is better than mine, and I withdraw my proposal.** The EV ids are self-describing slugs — `EV:WORK#023-4-4-prj-04-sykehusdekkende-rammeverk-for` already encodes its heading path. A bare newline-delimited id list is ~55 characters per entry: **7,920 characters ≈ 2,400 tokens, against my 90-character proposal at 3,900 and the current file at 22,900.** Adopt the user's.

**On "context files as Python libraries": reject the literal form, adopt the function.** Converting the `.md` authorities into `.py` modules breaks four things at once — `evidence_index.py` derives the index by parsing ATX headings; the freeze/hash mechanism records `.md` paths; every `EV:` id encodes a heading slug, so historical references break; and the files stop being human-editable, which matters because the user owns the factual nuggets.

**The function is free, and I under-specified it.** `evidence_index.json` already stores `line_start` and `line_end` for every entry (verified: `EV:WORK#023…` → lines 470–515). So a reader is roughly thirty lines:

~~~text
fetch.py --run <run_id> --ids EV:WORK#023-…,EV:WORK#025-…
→ prints the exact frozen source lines for each id, with its heading path
~~~

Reading the **frozen** copy for that run, not the live file, so a fetch is reproducible against the run it belongs to.

**This corrects my own FE-01, which was wrong in an instructive way.** I called `line_start`/`line_end` noise. They are noise *to a model that has already loaded the whole file* and precisely the payload *to a tool that slices it*. Strip them from what the model reads; keep them for the tool.

**On "strategy writes 'use [ID] as [purpose]'": right direction, calibrated down.** Output tokens cost roughly 4–5× input, and I had optimised almost entirely for input. Measured: `strategy.json` is ~31,700 characters ≈ 9,600 output tokens per job, of which `evidence_plan[].role` is 4,802 characters and `claim_ceiling` 1,863 — **about 21% of the most expensive token class in five entries.**

But `use [ID] as [purpose]` is too thin: `role` must still carry which employer decision the evidence serves and which boundary is live, or Stage 3 loses the reasoning and re-derives it worse. Target **200–400 characters per `role`** instead of ~960 average.

This converges with my own earlier finding F1, that long `role` prose becomes a substitute source for the downstream writer. **The same edit wins on both axes — it cuts the expensive token class and removes a defect pathway.** That is the strongest single instruction change available.

### 2.2 On authorities and stage consumption (comment at §2.2)

The user: *"once the evidence index is built, stage 2 should not be allowed to consume any of the full context files even, and stage 3 should do so only for specific inquiries… that is the primary function of step 1."*

Agreed, and with Stage 2 cut it simplifies: **Stage 1 reads the digests and ranks; Stage 3 fetches by id and verifies.** Neither loads all 45,200 tokens of authority text as a matter of course.

One caution the finalizing model must weigh: Stage 3's duty is to verify propositions against source, and a fetch-only stage can only verify what it thinks to fetch. Mitigation: Stage 3 fetches **every id in `used_evidence_refs`** before fixing content — that is a complete, mechanical rule, and it is stronger verification than today, where the source is present but diluted across 27,900 tokens.

### 2.3 On `FORFATTERSTEMME.md` routing (comment at §2.3)

The user: voice should be **Stage 3 only**. With Stage 2 cut this is automatic — voice goes to the only stage that writes employer-facing prose. Stage 1 never receives it, which is what its own front matter has always said.

### 2.4 On the retrieval indexes (comment at §3, and FLAG-01)

The user: *"if you still want this cut, that is A-ok by me, alternatively these could be extracted into a separate file and only read by stage 3 when searching."*

**The user is right and I reverse my recommendation.** I proposed cutting `W-01`, `O-01`, `E-01` because "the model is handed the entire file." Under fetch-based retrieval that premise dies: a keyword → section map stops being redundant and becomes **the search index the fetch tool needs**. Repurpose, do not delete: fold the three indexes into `fetch.py --search <term>`, returning candidate ids.

Same logic answers FLAG-01: a short `Education_map.md` fed to Stage 1, with the 43 course rows fetched only against a strict formal criterion, is exactly right. Generalise it — one map per authority, detail behind fetch.

### 2.5 On the AI differentiator (FLAG-03)

The user wants AI competence promoted from subordinate to differentiator, especially for private-sector, less-regulated or technically oriented vacancies, on the grounds that it is both true and under-used.

**I agree, and the user's own new facts make it better-supported than when `Other §4` was written.** Two of the ENH answers change the evidentiary basis:

- registered **"SuperBruker – Kunstig intelligens"** at OUS for nearly three years — a formal designation, not a self-description;
- currently building a **self-developed Python repository for patient bed-occupancy forecasting combining statistical and ML models** — delivery evidence, not method description.

The current rule (`Other §4.1`: `IDENTITY-AI` is subordinate unless AI is decisive) was calibrated when the only evidence was a workflow description. It is now under-calibrated.

**Recommended rule**, for the finalizing model to place: AI-enabled delivery may be named as a differentiator when the vacancy is private-sector, lightly regulated, or technically/innovation-oriented, **even where the advertisement does not mention AI** — provided it is anchored to a concrete artifact (the superuser designation or the forecasting repository) and every ceiling in `Other §4.5` holds unchanged: no production LLM applications, no RAG or fine-tuning or model serving, no enterprise AI governance, no quantified productivity gain, no sole authorship.

The honest risk: AI evidence is still mostly *method*, and method claims inflate more easily than delivery claims. The anchor requirement is what keeps this safe, and it should be non-negotiable.

## 3. New and changed mechanics

### 3.1 `fetch.py` — replaces FE-01

`runtime/tools/fetch.py`, read-only, no writes, no new schema, no new frozen input.

~~~text
fetch.py --run <run_id> --ids <EV:…>[,<EV:…>]   → verbatim frozen source for each id
fetch.py --run <run_id> --search <term>          → candidate ids from the repurposed keyword indexes
~~~

Resolves ids against that run's frozen `evidence_index.json` and reads the run's frozen authority copies using the stored line ranges. Roughly thirty lines. Sits alongside `make_fixtures.py` and `prepare_masters.py` in the existing tools directory.

The context bundle then carries the **id list only** (~2,400 tokens) plus the fetch invocation, and points at the full frozen index for validation as it does today.

### 3.2 Authority digests — FE-06, now load-bearing

With fetch in place, each authority needs a compact decision surface at its head, replacing the retrieval index that moves into the tool:

~~~text
| Record | Lifecycle | What it can prove | Hardest ceiling | EV id |
~~~

Ten rows for `Work`, fewer elsewhere, plus `Education_map.md` per §2.4. Stage 1 ranks from these; nothing else is loaded by default.

### 3.3 Output-token discipline in Stage 1

`evidence_plan[].role` target 200–400 characters, stating the supported proposition and the employer decision it serves. `claim_ceiling` states only the boundaries live for this vacancy, not the authority's full ceiling text. Justification in §2.1; this is simultaneously the F1 quality fix.

### 3.4 Still recommended, unchanged

FE-04 (deterministic page rendering for scanned vacancy sources) and FE-05 (slim baseline-map view) stand as written. FE-03 (stage-filtered policy and governing-hash scope) is **simplified** by cutting Stage 2: with two stages, Stage 1 takes doctrine + persuasion, Stage 3 takes all three.

FE-07, FE-08, FE-09 remain rejected, with FE-07's reasoning strengthened: `fetch.py` is the legitimate form of "code handles the nugget", because it retrieves verbatim source for a model to judge, rather than authoring a judgment.

## 5. Higher-order and multivariate effects

The individually-sound changes interact, and several compound in ways that change what should be implemented and in what order.

### 5.1 Cutting Stage 2 relocates the semantic fix

The base plan's Cluster 1 places a substantial share of the complete-proposition correction in `stage2_package_writer.md` — the routing table, the composition order, the `## Truth` replacement. **If Stage 2 is cut, those edits are addressed to a file that will not exist.**

This does not weaken the fix; it relocates it. The failure mode migrates to whichever stage authors prose, so the correction belongs in `S1` (encoding: what `role` may assert) and `S3` (authoring and pre-lock repair). The finalizing model must make this call **before** scheduling Cluster 1, or the cluster will be written twice.

**This is the single most important sequencing consequence in this document.**

### 5.2 Fetch-based retrieval structurally attacks the D1 defect class

D1 attached PRJ-08's workshops to PRJ-04. Both records sat in the same 27,900-token context window, and the workshop language bled across a record boundary that exists only in the text.

Under fetch, an author working on PRJ-04 retrieves PRJ-04 and sees only PRJ-04. **The bleed surface is removed structurally, which no instruction can achieve.** This is the strongest quality argument in the whole analysis, and it is a side effect of a change proposed for token reasons.

The corresponding new risk — a stage verifying only what it thinks to fetch — is bounded by the rule in §2.2: fetch every id in `used_evidence_refs` before fixing content.

### 5.3 Cut Stage 2 × fetch × digests compound super-additively

Individually: cutting Stage 2 removes one stage's authority reads; fetch makes remaining reads selective; digests make selective reads sufficient for ranking. Together they remove not just Stage 2's 86,400 tokens but most of Stage 1's and Stage 3's bulk reading as well, because after the cut only two stages read authorities at all and both read them through the same narrow interface.

| State | Static input per two-job run |
|---|---:|
| Today | ≈ 556,000 |
| Stage 2 cut only | ≈ 383,000 |
| Cut + fetch + digests + slim index + context cuts | **≈ 180,000–210,000** |

A roughly 62–68% reduction, with output-token savings from §3.3 on top of it and — the part that matters more — a defect pathway closed.

### 5.4 Interaction with `User required optimizations.md`

- `branch --from-stage N` collapses to `--from-stage 1|3`. The option remains valuable: *"redo Stage 3 for all vacancies"* is unaffected and becomes the dominant use.
- The §A goal prompts lose the Stage-2 variant. The Stage-1 and Stage-3 prompts stand unchanged.
- The one-instance-per-stage invariant is **strengthened**, not weakened: two stages, two chats, and my treatment run demonstrated exactly why merging them produces misleading evidence.

### 5.5 ENH-05 changes the Avinor argument, not just the authority

The 2027 budgeting tool being in hospital-wide use converts the carrying case from a single constrained delivery into a two-act arc: accept an imposed narrow frame and buy safety with parity controls → deliver → be given freedom → deliver again at scale. For a unit whose stated purpose is *"styrke gjennomføringskraften"*, that arc is materially stronger than what the current letter carries, and it is now true.

The finalizing model should expect the next Avinor package to differ substantially from the treatment package for this reason alone — which is a further argument for updating the authorities **before** the comparison run, not after.

### 5.6 The sequencing question resolves differently than I first advised

I originally recommended holding the authorities fixed to keep the treatment comparison clean. Three things now override that:

1. `W-04`'s maturity ladder actively fights the lifecycle rule being tested.
2. `ENH-02`, `ENH-04` and `ENH-05` change what is *true*, and running a comparison on stale facts tests the wrong package.
3. The user's own answer: *"quite a bit will be handled BY the P0.9.3 semantic implementation itself, the rest AFTER."*

**Revised recommendation: apply the factual updates and the retired-prescription removals before the comparison run; defer cosmetic consolidation until after.** The comparison then measures the treatment against current truth, which is the only comparison worth having. Accept explicitly that it is a multi-variable change and stop describing it as an A/B — it never was one, since all writing policies fold into every stage's hash.

### 5.7 Compression interacts with the cut

Roughly 2,500 tokens of instruction disappear with `stage2_package_writer.md`, and `STAGE2_PROMPT.md` plus its mirror remove ~2,100 more. Compression work should be scheduled **after** the cut so it is not spent on files that will be deleted.
