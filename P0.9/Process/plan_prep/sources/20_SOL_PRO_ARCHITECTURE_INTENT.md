# Jobbsøk_26 P0.9 — Implementation Intent Adjudication

## Verdict

**NO-GO for the two-real-job smoke until a bounded trust-boundary repair pass is complete. No architecture rewrite is warranted.**

The core design remains strong: narrow product scope, three semantic stages, elastic Stage 3, job-local persistence, immutable child branching, deterministic mechanics, personality as bounded interpretive context, Word-based rendering, and orthogonal semantic/render state. The employer-facing package—not internal machinery—is the product, and verified implementation evidence should override design assumptions at its proper empirical scope.  

The release blocker is narrower: **the build does not yet reliably distinguish “present and schema-valid” from “current, correctly bound and eligible.”** That weakness affects stage handoffs, branching, rendering, render provenance and failure observability. These defects can produce misleading green state, stale employer-facing output or wasted semantic work. They violate the architecture’s original currentness intent, not merely its wording. The frozen design explicitly requires fixed artifact lineage, current-state derivation and orthogonal render state.  

### Independent implementation controls

Direct inspection and execution against `Build.zip` confirmed and sharpened the forensic audit:

* The included vertical-slice run reports `VALID` / `CHECK` / render `OK`, although its render report binds to a different final-package hash and contains obsolete absolute output paths. Current status trusts the report without verifying its binding or output bytes.
* An unchanged branch can label strategy, draft, final and review as `REUSED`, yet the child immediately derives only Strategy as current because the semantic chain is not rebound transitively.
* Stage-3 context generation can return success and hand the model a stale draft.
* A malformed frozen evidence index can make `status` terminate with a raw traceback rather than returning an integrity diagnosis.
* The CV master’s unconditional page break visibly creates poor sparse-fixture balance; this is product-quality contamination, not cosmetic compliance work.
* The audit’s reproduced parent-tampering, vacancy-tampering, interrupted-Stage-3 and compromised-`next` cases remain valid.

## Where the forensic audit is materially wrong or incomplete

1. **`SOL-A005`: the proposed remedy is too broad.** Render or PDF-conversion failure must not become production failure state. The failure record should capture failed semantic submissions and exhausted production recovery; the render report owns DOCX/PDF failure. Otherwise the repair collapses the three frozen axes.

2. **`SOL-A015`: arbitrary `--dest` is not inherently a security defect.** An explicit human export outside the run tree is useful no-clobber behavior. The defect is allowing such an external export to masquerade as authoritative current render state.

3. **`SOL-A016`: severity is understated.** The forced page break should be fixed before quality smoke, not treated as optional polish. Otherwise the pilot measures a known template defect rather than the semantic system.

4. **`SOL-A019`: exact-PID cleanup is not automatically the right fix.** A complex ownership-discovery mechanism could kill unrelated Word sessions or create more operational risk than an occasional orphan. Truthful diagnostics are mandatory; exact cleanup is conditional on a safe target-Windows implementation.

5. **`SOL-A021`: `KEEP` is too confident.** The closed PF catalogue has not been shown to improve or harm real packages. It should remain unchanged through the first smoke, but its long-term retention is a pilot question: `DEFER`.

6. **`SOL-A023`: missing OS read-only bits are not presently a demonstrated defect.** Their value depends on the selected semantic-model surface and actual filesystem permissions.

7. **`SOL-A026`: the Linux backslash test failure is a portability artifact, not a Windows-target product defect.** Altering Windows path semantics to green the Linux suite would be a regression.

8. **`SOL-A032`: a multi-file transaction system would be worse than the current implementation.** Exact report/output validation makes a crash between output promotion and report writing safely detectable and rerunnable.

9. **`SOL-A033`: validating every generated view is unnecessary.** Current failure and render records need validation because status trusts them. Disposable `status.json` need not become a second authoritative contract merely because a schema exists.

10. **The audit’s “no amendment” conclusion is too conservative.** Four narrow clarifications are justified by implementation evidence: explicit-human export, deterministic binding-envelope ownership, render-receipt semantics and failure-record axis ownership. None changes the product or stage architecture.

The audit correctly warns that the repair pass should centralize a few strong boundaries rather than add event sourcing, dependency graphs, workflow engines or document-version management.

# Frozen-rule assessment

## Shown too strong

### 1. “Deterministic tooling writes only under run/generated roots”

Applied literally, this forbids useful, explicitly human-directed export. The actual invariant should be:

> **Canonical pipeline state and model-controlled writes remain inside approved roots. An explicit human export may target another location, but that copy does not become authoritative current render state without an explicit verified adoption path.**

This preserves security, no-clobber usability and human authority simultaneously.

## Shown too weak or underspecified

### 2. Artifact binding ownership

The freeze specifies which hashes artifacts bind to but not who must author mechanical binding metadata. Asking semantic models to copy deterministic hashes is low-value work and a recurrent malformed/stale-at-birth source. The architecture should explicitly assign the **binding envelope to deterministic tooling** and the semantic payload to the model.

### 3. Render report transaction semantics

The specification and implementation contract imply different report/promotion orderings. Neither ordering can atomically commit several DOCX/PDF files plus JSON on a normal filesystem. The invariant should instead be:

> **A render report is a receipt whose currentness is derived from exact input and output hashes. Unreceipted or mismatched files may exist after interruption but are never current.**

### 4. Current failure-record scope

“Deterministic operation” is too broad. The architecture must state that the failure record is not a general command-error log and does not own render state.

## Not shown empirically wrong

Implementation evidence does **not** justify reopening:

* invariant CV plus letter;
* Bokmål-only core;
* portal/channel exclusion;
* three semantic stages;
* Stage-3 elasticity;
* personality ON with zero-to-three selection;
* job-as-transaction;
* immutable parent plus child branch;
* PDF degradation orthogonal to semantics;
* lean deterministic evidence indexing;
* no semantic judge, workflow engine, event sourcing or dependency graph.

The audit’s conclusion that no wholesale re-adjudication is needed remains correct; its conclusion that **no clarification amendment** is needed does not.
