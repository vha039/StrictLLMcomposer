# Evolution, deltas and rationale

## 1. Causal evolution

Jobbsøk_26 did not evolve through clean whole-document replacement. It accumulated four layers with different authority:

```text
P0.7 executable release
    -> concrete audit and product-quality correction
P0.8.0 final normative Selective Quality redesign
    -> interface and pilot review
P0.8.1 non-normative contract hardening
    -> product/context/personality/state reopening
P0.9 pre-lock decision basis
    -> current derived candidate, still awaiting formal adoption
```

The current state must therefore be reconstructed per proposition. P0.7 remains strongest on what was actually implemented and tested; P0.8 remains strongest on adopted architecture; P0.8.1 supplies unadopted but often valuable interface repairs; later P0.9 user decisions override specific policy points; research corrects empirical assumptions; derived files 19–20 supply hypotheses and cross-source insights rather than self-authorizing decisions.

### 1.1 P0.7 — executable engineering baseline

P0.7 was a real 52-file local release with four physically separated model stages, three scripts, schemas, source authorities, CV baseline, Word masters, fixtures and test evidence. Its normal route was:

```text
Stage 1 Terra Max — candidate-blind vacancy analysis
Stage 2 Sol Max   — evidence/strategy + macro→mini split
Stage 3 Terra     — draft package
Stage 4 Sol       — final writer/recruiter mirror
```

About 40 jobs were organized as two macroclusters and four miniclusters, requiring 12 standard chats. `advance.ps1` moved controlled artifacts between physical stage areas. The finalizer enforced identity, baseline, portal, page, leakage and render contracts.

The release was mechanically credible but not product-validated: 32 tests passed, two PowerShell-dependent tests were skipped, controlled synthetic E2E/rendering passed, but no real Terra/Sol vacancy batch was run. [SRC-00: Part II; SRC-02: §§0.2–2; SRC-19: §§2–3]

### 1.2 P0.7 → P0.8 — objective correction, not merely stage compression

The P0.7 audit found real defects:

- mutable Stage-4 draft/evidence reference could undermine integrity checks;
- `_DONE.md` and review heading checks could validate substrings rather than meaningful state;
- duplicate portal question IDs were not fully protected;
- target-scale 20/10 stress behavior was unproved;
- PowerShell runtime path remained unverified;
- sparse CVs were forced toward weak two-page output;
- no explicit headline/candidate identity field existed;
- no real model/vacancy pilot existed.

The initial instinct was stronger immutability and reliability gates. The user then made the decisive correction: the framework should optimize the best possible normal output for the majority, not spend disproportionate complexity making the weakest tail uniform. Approximately 75–85% excellent output could be highly valuable if the remainder were cheaply identified and separately rerun. This created `Q_happy` and the Selective Quality doctrine. [SRC-02: §§0.2, 3–6; SRC-04: §§3–6; SRC-19: §4]

### 1.3 P0.8.0 — adopted three-stage Selective Quality architecture

P0.8 transformed the product and semantic route:

```text
Stage 1 — Sol Max — Decision Architecture
Stage 2 — Terra Max — Native Package Writer
Stage 3 — Sol Max — Final Writer & Selective Review
```

The macro/minicluster split disappeared. About five clusters × eight jobs, 6–10 normal range, produced 15 standard chats. `advance.ps1` disappeared; two deterministic scripts were targeted. P0.8 added explicit headline, stronger dynamic CV, full final-writer reconstruction authority, `READY/CHECK/RERUN`, partial success, per-job rerender and soft page handling. P0.8’s final specification was formally normative but was never implemented. [SRC-05: §§0–8; SRC-06: Parts I–VII]

The apparent increase from 12 to 15 chats was not architectural bloat. Complexity fell because there was one cluster type, no physical macro→mini transfer, fewer status/handoff surfaces and clearer model roles.

### 1.4 P0.8 → P0.8.1 — interface hardening, not adopted redesign

Independent reviews agreed that P0.8’s product/topology were largely correct and concentrated risk at interfaces. P0.8.1 consolidated 25 change recommendations:

- canonical job/deliverable input;
- nonredundant channel/output representation;
- operational freeze and context snapshot;
- schema/set equality for cluster plan;
- expected-job reconciliation;
- mechanical versus semantic validation classes;
- exact package→template mapping;
- full employment bullet-array replacement;
- final evidence-ref synchronization;
- repair-scope READY/CHECK/RERUN;
- explicit RERUN route;
- validator success before completion;
- run-level cost and total human-time measurement;
- small-n Top-80 sensitivity;
- vertical-slice-first build sequence.

It also rejected YAML dual truth, typography auto-fit, 5-gram collision gates, portal tolerance, LibreOffice daemon, judge stage, automatic retry, database/event sourcing and vector/RAG machinery.

The status remained explicit: `NON_NORMATIVE_UNTIL_ADOPTED`. Later models may use a repair only if Step 1 selects it or if it is implemented and verified; they must not call P0.8.1 a historical release. [SRC-07: technical summary and §§1–8; SRC-08: front matter, §§0–22]

### 1.5 P0.8.1 → P0.9 — controlled reopening

P0.9 brainstorming did not claim the three-stage topology had failed. It reopened whether several P0.8 surfaces should exist:

- core portal/channel branching;
- Priority A/B prediction, order and differentiated treatment;
- stage-centric state and duplicated manifests/progress;
- Markdown versus structured strategy;
- evidence retrieval/context preparation;
- personality/authenticity context;
- Luna as a cheap preparation model;
- fresh runtime and legacy compatibility;
- how many experiments were worth running before build.

The broad Brainstorm Brief intentionally preserved many options; the bounded review normalized them into decision clusters `DC-1..DC-7`, mechanisms `N-01..N-06`, bundles and experiments. Both remained non-normative. [SRC-10: §§0–1 and decision registers; SRC-11: §§0–8]

### 1.6 Research, personality and latest user policy

The pre-architecture work then reduced uncertainty:

- external evidence challenged naive assumptions about context windows, JSON guarantees in manual chat, long-context Luna quality, portal uniformity, LibreOffice behavior and prompt-injection controls;
- a rich canonical personality source made authenticity a concrete, testable input rather than an abstract “me-nizer” idea;
- the latest user answers set the reuse horizon, workload, deadlines, prompt envelope, fresh-runtime permission, immutable/current authorities, optional personality toggle and final Sol elasticity;
- those answers did **not** select final portal, strategy, tree, evidence-index, personality-default or Luna architecture.

The terminal historical state was therefore “decision-ready but not selected.” [SRC-12: §§0–4; SRC-15: §§1–10; SRC-16; SRC-17; SRC-18: §§3–5, 12, 15]

## 3. Mechanisms retained and why

### 3.1 Three factual authorities and derived CV baseline

Retained because they provide a clear claim ceiling, support stable chronology and prevent model-generated package text from becoming self-referential truth. Later candidate-source research remains a maintenance input, not a fourth runtime authority.

### 3.2 Human-approved jobs and no semantic GO/NO-GO router

Retained because the human selects the opportunity set. Model-side fit scoring or automatic rejection would add false precision and could suppress useful packages. Tail handling happens after production evidence, not as hidden pre-veto.

### 3.3 One-job persistence before the next

Retained because it limits blast radius, makes continuation auditable, supports per-job rerun/render and prevents one broken job from invalidating the batch.

### 3.4 Models for semantics, code for mechanics

Retained because the best division of labor is stable across versions. Models decide identity, evidence, motivation and prose; code handles deterministic identity, structure, expected sets, limits, merge and rendering.

### 3.5 Manual separate semantic stages

Retained because the project explicitly rejects an API/model orchestrator and values clear human initiation, stage contracts and local files. Local validators may run inside a capable session without becoming an orchestrator.

### 3.6 Sol→Terra→Sol role split

Retained because it aligns non-linear decision architecture and final reconstruction with the strongest reasoning/writing model while assigning output-heavy native writing to Terra. No corpus evidence shows a general fourth stage or judge would improve net value.

### 3.7 Explicit headline and dynamic CV zones

Retained because P0.7’s missing headline was a concrete quality defect and full model-owned chronology would create factual risk. Headline/profile/competencies/bullets give high relevance leverage.

### 3.8 Final-writer elasticity

Retained and strengthened by explicit user decision. Upstream artifacts must reduce cognitive work without limiting stronger downstream evidence or strategy correction.

### 3.9 `READY/CHECK/RERUN` and partial success

Retained because the system needs cheap tail surfacing and bounded human action, not an opaque score. Per-job delivery preserves the strong majority.

### 3.10 Professional Word masters and deterministic rendering

Retained as capital, not dogma. P0.7 supplied direct evidence that the actual non-data-bound SDT fill/unwrap method worked in controlled tests. Reuse is conditional on target-machine verification and adaptation.

### 3.11 No-submit human boundary

Retained as hard safety, accountability and scope boundary throughout every version.

## 4. Deleted, superseded or conditionally obsolete mechanisms

The distinctions below are important because a future builder may otherwise re-import old machinery on the assumption that “more mature” means “still applicable.” A mechanism should survive only when its product/state surface survives.

### 4.1 P0.7 mechanisms that should not return as default architecture

| Mechanism | Current treatment | Why it was superseded |
|---|---|---|
| Four standard semantic stages | `RETIRE` | P0.8 replaced this with a simpler three-stage topology after the objective shifted from uniform process control to strong-majority package quality. No later evidence restores a fourth mandatory stage. |
| Macrocluster → minicluster split | `RETIRE` | It increases operator and context handoff complexity. P0.8’s single clustering layer is the last adopted design and remains the cleaner control. |
| `advance.ps1` as semantic stage conveyor | `RETIRE/REBUILD` | Physical movement and sentinel-driven progression create status theatre. A fresh P0.9 runtime should derive progression from validated canonical artifacts, not directory movement. |
| `_DONE.md` and review-heading completion signals | `RETIRE` | The audited P0.7 parser could accept substring theatre rather than proving valid semantic output. Completion must follow schema/contract validation. |
| Strong Stage-4 lock to prior blueprint/evidence | `RETIRE` | It protects stale strategy at the expense of final quality and conflicts directly with the user-locked `ELASTIC` final-Sol requirement. |
| Shared mutable draft reference used as integrity anchor | `RETIRE` | A malicious or accidental Stage-4 edit could change both reference and final output. Immutable upstream truth and final synchronized evidence refs are the correct controls. |
| Hard CV/application page count as semantic success proxy | `REPLACE` | Page bounds matter for usability, but a package should not fail because a mechanically counted page limit substitutes for editorial judgment. Use template budgets, warnings and human review; hard-fail only on unusable output or explicit external limit. |
| Competency-derived headline | `RETIRE` | P0.7 had no explicit candidate identity/headline field. P0.8 correctly made it a first-class strategy and package element. |
| Full-batch all-or-nothing completion posture | `RETIRE` | Selective-quality economics require partial success and per-job delivery/rerun. |
| Model-generated package content as future source material | `PROHIBIT` | Generated package text is output, not candidate truth. Allowing it to feed later runs would create self-amplifying claim drift. |

### 4.2 P0.8/P0.8.1 surfaces that may become contract zombies

P0.8.1 often repaired real interfaces. The repair should be adopted only if Step 1 retains the interface.

| Earlier surface | Hardening attached to it | Current P0.9 treatment |
|---|---|---|
| Portal answers inside the core package | Canonical channel matrix, exact portal limits, portal-state coherence, portal validation and delivery contract | `STEP1_FREEZE`. If portal is detached, delete these core contracts and keep only a downstream request/handoff boundary. Do not implement them and then bypass them. |
| Model-generated `cluster_plan.json` with Priority A/B treatment | Schema, freeze, priority semantics and execution reconciliation | `STEP1_FREEZE`. Human cluster/order may remain useful while model-generated priority treatment is deleted. Preserve only state with a unique consumer. |
| Separate `context_snapshot.json`, `progress.json`, expected set and status files | Hashing, coherence and completion checks | Reconcile against the candidate run/job manifest. Do not preserve multiple authoritative objects that represent the same freeze or completion state. |
| Stage-centric directory progression | Stage readiness and transition rules | Re-evaluate if a job-centric runtime is adopted. Stage artifacts remain distinct; the directory tree need not make the stage the transaction boundary. |
| Mandatory support for English and rare channels | Language/channel validation branches | Delete from v1 if the real inventory supports Bokmål-only invariant output and exceptions are handled separately. This is not yet frozen. |
| Priority A/B writing treatment | Microvariation and selective extra effort | Decompose prediction, ordering and treatment. Human priority may survive while differentiated model treatment is removed unless it proves value. |
| Elaborate strategy Markdown formatting | Stable labels, section presence and handoff parser | Preserve the semantic contract, but let the selected serialization determine the minimal validation surface. |

### 4.3 Mechanisms whose problem disappeared rather than being “solved”

Several earlier debates become unnecessary under a narrower candidate:

- A sophisticated portal-schema engine is unnecessary if portal content is downstream and low-volume.
- A batch-wide semantic similarity detector is unnecessary if the observed problem can be handled by human sampling and final-writer instructions.
- Per-job copies of all static context are unnecessary if a single frozen run authority plus immutable source paths provides the same protection.
- A separate cluster-strategy model is unnecessary if clustering is a human mechanical operation and Stage 1 begins at the job level.
- A strategy “approval” gate is unnecessary if strategy is explicitly a revisable hypothesis and Final Sol owns correction.
- A universal retrieval layer is unnecessary if deterministic navigation plus direct-source escape performs adequately at this corpus scale.

The governing rule is:

> **Do not harden or optimize an interface before confirming that the final product still needs the interface.**

## 5. Rejected alternatives worth remembering

These alternatives are retained only because their rejection rationale prevents regression. They are not a general prohibition on future change; each has an activation condition.

| Alternative | Why rejected/deferred now | Re-open only when |
|---|---|---|
| API/SDK model orchestrator | Conflicts with manual Work/Codex operation, adds code-owned semantic routing and repeats the rejected P0.5.3 direction | Manual initiation is proven to be the dominant bottleneck and an API path can preserve quality, authority and auditability |
| Database, vector store, GraphRAG or semantic cache | Adds ingestion, indexing, invalidation, observability and retrieval failure surfaces without evidence of marginal package-quality gain at one-candidate scale | Direct source + deterministic index repeatedly fails recall or human maintenance becomes unmanageable |
| Multi-agent debate/subagents | More model activity is not equivalent to better decision architecture; adds conflicting authority and synthesis burden | Controlled tests show a stable, material gain over one strong strategy/final writer |
| Automatic retries or hidden repair loops | Hide failure, inflate cost/latency and can repeatedly mutate semantics | A narrowly defined deterministic failure class has a safe, observable and idempotent retry |
| LLM-as-judge standard stage | Creates a score proxy, not guaranteed semantic truth; can encourage optimization to the judge | A calibrated evaluator is validated against human package judgments and changes decisions enough to justify another stage |
| Full-package best-of-N | High prompt and human comparison cost; conflicts with selective-quality simplicity | A specific high-value job class shows repeatable gain that exceeds selection burden |
| Automated employer research | Expands factual and freshness risks and can displace vacancy/candidate evidence | A bounded, cited research protocol proves value for selected high-priority jobs |
| Automatic submission/contact/profile changes | Irreversible external action outside scope and human authority | Not a P0.9 activation path; would require a separately governed product |
| YAML/frontmatter duplicating strategy JSON/Markdown | Two representations of the same decisions create drift and unclear authority | One is generated mechanically as a disposable view from the canonical form |
| Typographic auto-fit engine | Hidden per-document variation, difficult QA and premature document-engine complexity | Repeated real render failures remain after template tuning and a bounded deterministic adjustment solves them |
| N-gram/phrase-collision hard gate | False positives and code-owned prose judgment; no evidence it improves packages | Batch-wide phrase reuse is measured as a material employer-facing defect and a lightweight advisory check proves precise |
| Persistent LibreOffice daemon/service | Profile locks, state leakage and operational complexity | Per-job/document conversion is measured as an unacceptable bottleneck and a supervised service is locally proven reliable |
| Regex “AI firewall” as primary injection defense | Prompt injection is not fully solvable by lexical scanning; creates false confidence | Never as sole control; lexical checks may remain one defense-in-depth signal |
| Semantic truth validator in code | Code cannot prove interview-defensible meaning or attribution | No activation; semantic truth remains human/model-source reasoning, supported by mechanical references |
| Global Luna preparation/filter over the full corpus | Long-context weakness, anchoring and false-exclusion risk; no direct quality proof | A bounded paired test shows incremental value over deterministic index/direct sources without recall loss |
| Full personality profile to every writer | Risks stereotype, anchoring, voice performance and factual leakage | No activation as default; only selected evidence-bound facets should ever pass downstream |
| Role-archetype memory/library | Encodes stale abstractions and can force new vacancies into inherited frames | Repeated batches show stable, source-linked archetypes save work without reducing job-specific reasoning |
| Backward-compatible P0.7/P0.8 runtime | Fresh P0.9 is explicitly allowed; compatibility would preserve obsolete contracts | A specific verified asset is cheaper and safer to adapt than rebuild |

## 6. Cross-source insights that no single source fully establishes

### 6.1 Two authority axes, not one

The corpus becomes coherent when factual authority and strategic authority are separated:

```text
Candidate/vacancy sources
  → decide what is true and what may be claimed

Strategy artifacts
  → propose what matters and how to frame it

Final writer
  → may revise strategy but may not revise truth
```

A more structured strategy can be easier to validate while remaining non-authoritative. Conversely, free prose can still be dangerously authoritative if later stages are instructed to obey it. Serialization and authority must therefore be designed independently.

### 6.2 Structural strictness can increase semantic freedom

Exact job IDs, expected sets, evidence addresses, source hashes and render checks do not make writing more formulaic. They remove ambiguity from mechanics, allowing Final Sol to reconstruct the argument aggressively without risking cross-job leakage or untraceable claims.

### 6.3 Delete first, then harden

P0.8.1 is strongest where it distinguishes mechanical from semantic contracts. P0.9 adds the prior question: should this contract surface exist? The combined rule is:

1. define the smallest employer-facing product;
2. delete product/state branches that no longer serve it;
3. harden the remaining boundaries;
4. leave semantic judgment with the strongest appropriate stage.

### 6.4 Upstream formalization creates a compensating-freedom requirement

The more precise Stage 1 becomes, the more likely later stages are to mistake its output for truth. Formalization must therefore be paired with explicit downstream permissions:

- evidence selection is revisable;
- headline and backbone are hypotheses;
- omitted evidence may be recovered from sources;
- final evidence refs must reflect the final package;
- correction is not a deviation requiring apology.

### 6.5 False exclusion is the dominant context-preparation risk

A missed source atom can remove the best argument before the strongest model sees it. A false inclusion merely costs attention. Context mechanisms should therefore optimize asymmetric loss:

- advisory ranking, not destructive filtering;
- direct-source escape always available;
- stable evidence addresses;
- record when decisive evidence came from outside preparation;
- compare preparation against a direct-source/index control.

### 6.6 Minimal authoritative core; rich disposable views

A robust runtime should minimize authoritative mutable state. Derived summaries, human reports, navigation views and dashboards may be rich, but should be regenerable from a smaller canonical core. This reduces reconciliation and invalidation complexity without reducing operator visibility.

### 6.7 Job is the natural failure and delivery transaction

Across partial success, targeted rerender, source changes, human review, portal exceptions and RERUN, the job is the smallest object that should complete or fail independently. Clusters are semantic execution aids; they should not become the unit of durable success.

### 6.8 Status is a repair prediction, not a quality score

`READY/CHECK/RERUN` works because it predicts action:

- no material repair;
- bounded human confirmation/edit;
- coherent semantic reconstruction.

This avoids pretending that a scalar score has calibrated meaning while still routing scarce human effort.

### 6.9 Static invalidation beats dynamic dependency machinery

The source and artifact families are few and stable. A documented invalidation matrix can specify which downstream products become stale after a candidate-source, vacancy, strategy, package or template change. This gives most of the value of a dependency graph without runtime graph infrastructure.

### 6.10 Three evidence loops must remain distinct

1. **Engineering proof:** contracts, validation, isolation, deterministic rendering.
2. **Product observation:** quality and effort on real jobs.
3. **Causal comparison:** whether optional personality, Luna, serialization or routing improves outcomes.

P0.7 has substantial loop 1 evidence but no real semantic loop 2. P0.9 should not use engineering test counts as evidence that optional quality mechanisms work.

### 6.11 Control plane versus data plane is the smallest useful security model

Vacancies, personality context, model outputs and context-prep artifacts may influence reasoning but may not change instructions, permissions, authority, manifests, validation policy or external-action boundaries. This compact distinction captures the relevant threat model without an elaborate security platform.

## 8. Regression guardrails for Step 1 and Step 2

A future model should treat the following as warning signs that the project is regressing:

1. **State count grows faster than unique decisions.** Two files encode the same freeze, status or source set.
2. **A validator starts judging persuasion.** Mechanical code is becoming a semantic authority.
3. **Final Sol must defend Stage 1 instead of improve the package.** Strategy has become an unauthorized lock.
4. **A weak job blocks strong jobs.** Partial success has been lost.
5. **A model-generated summary becomes the only path to source evidence.** False-exclusion risk is unbounded.
6. **Optional personality or Luna becomes required for baseline correctness.** Experimental quality levers have contaminated the core.
7. **Portal/channel exceptions dominate core schema complexity before inventory evidence exists.** The product boundary has not been simplified first.
8. **Generic ATS/LibreOffice folklore overrides actual master inspection—or the reverse.** Both direct artifact evidence and target-environment tests are required at their correct scope.
9. **The repository preserves P0.7/P0.8 shapes solely for compatibility.** Fresh P0.9 was explicitly permitted.
10. **Prompt count, test count or schema count is presented as package-quality evidence.** The wrong evidence loop is being used.
11. **The system silently submits, contacts, updates profiles or rejects jobs.** Human irreversible authority has been breached.
12. **An OPEN item disappears without a decision record or experiment.** Cosmetic closure has replaced resolution.

The correct stopping rule for architecture is not “every interesting possibility has been modeled.” It is:

> The smallest truth-safe candidate has explicit owners for every remaining uncertainty, no duplicated authority, and enough contractual precision that the builder can proceed without inventing product policy.
