# P0.9 Draft Architecture — Extra-KISS Interaction Critique

Red-team pass on `P0.9_DRAFT_NORMATIVE_SPECIFICATION.md` + its two companion drafts, against the seven canonical context files. Governing test throughout: *if this mechanism disappeared, what expected-value loss results, weighed against its package-quality/effort/state/failure/context/maintenance cost?*

---

## 1. Structural verdict

The draft is disciplined where it matters most: one frozen manifest, fully derived status, no second authoritative state object, an honest gate/experiment split, and a real instinct for deleting risk classes instead of detecting them (DEC-29 moving identity into body flow is the clean exemplar — one template edit permanently retires a whole verification dependency). The classic P0.7 failure mode — several objects encoding the same freeze/completion fact and disagreeing — has been genuinely engineered out, not just relocated.

The residual problems are second-order, not foundational, and cluster in three places: (1) one enforcement mechanism (the evidence index's lossless-coverage requirement) is sized for a guarantee it never actually cashes downstream; (2) one product decision (the invariant letter) deletes proven P0.7 capital to avoid a strawman (P0.8.1's heavy portal-in-core hardening) rather than the actual small thing it was attached to; (3) several `PROTOCOL`-typed claims (cross-job leakage, the four-reasons-escalation rule) are stated with `BOUNDARY`-level confidence but tested at a materially narrower scope than the claim. No finding below rises to P0 — nothing here corrupts state or invalidates the architecture's soundness. This is a tuning pass, not a redesign, and the register in §10 should be read that way.

## 2. Top architecture-interaction risks

### OPUS-001 — Invariant letter × portal-heavy channel reality
**Severity:** P1 · **Confidence:** High
**Location:** `DRAFT_NORMATIVE` §3.1 (`DEC-01`), `CTR-01`; cf. `04_IMPLEMENTATION_BASELINE` §1.4 (P0.7's actual `application: null` contract); `05_EVIDENCE` §2.2 (Webcruiter free-text/question-module behavior); `Decision Record` `DEC-01` ("estimated portal prevalence ~20%, uncertain").
**Mechanism:** Every core job unconditionally produces a letter in DOCX+PDF. `DEC-01`'s rationale attacks P0.8.1's heavy portal-in-core hardening (channel matrix, question IDs, limit validation) and then, in the same move, also deletes the far smaller `letter_required` boolean + `application: null` pattern P0.7 already implemented and tested — a mechanism that was never part of the portal-hardening surface being rejected.
**Delete-test:** Removing the invariant and reintroducing one boolean field breaks nothing: `CTR-06`'s `application` field already accepts a shape that can be `null`; the finalizer's step 3 already branches per job on class.
**Cost/risk:** For every job whose channel is a free-text/question-module portal (plausibly a large share, since Webcruiter — the evidence base's dominant example — routinely works this way), the system pays Stage-2 writing effort, Stage-3 finalization, two renders and the full 8-point per-document verification (§18.3) for a document nobody will submit as a file — then hands the human an unlabeled per-job judgment call ("do I need this?") that the old boolean answered for free. This works directly against optimization-order priority #2 (human effort), and `GATE-07`'s re-adjudication trigger does not catch it: that gate counts `EXCEPTION` jobs, and a Webcruiter free-text job is still `CORE` (the CV is fine, only the letter-as-document is wasted).
**Smallest better design:** Restore `letter_required` as a human-populated intake field (the human already knows the channel when filling the batch table) and `application: null` when false — exactly P0.7's proven contract. Keep every P0.8.1 portal-hardening deletion (`DEC-02`) as-is.
**Second-order effect:** Shrinks the render/verify surface from a fixed 4 documents/job to a variable 2–4, and removes an unrecorded per-job human decision at submission time, replacing it with one explicit intake-time field.

### OPUS-002 — Cross-job leakage claimed as hard defect, tested only as string leakage
**Severity:** P1 · **Confidence:** Medium-high
**Location:** `DRAFT_NORMATIVE` §8.4 (`INV-22`), §26 test 6; cf. candidate architecture §5.2 ("avoid placing one identity archetype so early that it anchors the whole cluster"), `EXP-07`.
**Mechanism:** `INV-22` states cross-job leakage is "a hard defect," but the only Tier-1 evidence for it (§26 item 6) is a fixture where job B's *employer string* appears verbatim in job A's package. The actual risk this invariant is meant to guard against — one continuous cluster chat producing convergent identities/headlines/phrasing across the 6–10 jobs it processes sequentially — leaves no literal string trace and is explicitly deferred to a human spot-check (`EXP-07`), not tested at all pre-pilot.
**Delete-test:** Removing `INV-22`'s "hard defect" framing and leaving only the string-leakage test changes nothing observable before the pilot — which is itself the finding: the claim currently exceeds its enforcement.
**Cost/risk:** This is the one place where a locked, unchanged-from-P0.8 design choice (one chat per cluster-stage, `D-023`) directly creates the failure mode (`Q_happy` convergence) that a currently-untested invariant claims to prevent. Unlike most findings here, this isn't self-correcting — `EXP-07` only runs after a real batch, i.e., after the risk has already had a chance to depress `Q_happy` on the first production run.
**Smallest better design:** Add one cheap, `ADVISORY` (never a hard gate — consistent with the standing non-goal against similarity hard gates) check: flag when two jobs in the same cluster share a headline or `primary_identity` string above a trivial similarity threshold, surfaced in `status`/`queue.md`. This is data the manifest already has (cluster/sequence) plus a string compare on already-produced artifacts — no new state object.
**Second-order effect:** Makes `EXP-07` partly answerable from Tier-1/Tier-2 engineering data already logged via `EXP-01`'s position hook, reducing the need for a dedicated future experiment pass.

### OPUS-003 — Strategy density budget × mandatory cardinalities → anchoring baked in before it's tested
**Severity:** P2 · **Confidence:** Medium
**Location:** `DRAFT_NORMATIVE` §10.3 (surface table, non-omittable 1–N arrays), §10.4 (`DEC-11`, 450–900 soft/1200 warn/1600 hard).
**Mechanism:** The requirement map (1–12 entries) and evidence plan (1–10 entries) both have a hard *minimum* of 1, and both require sub-fields (`class`, `relation`, `evidence_refs`, `why`) per entry. Combined with roughly a dozen other required prose surfaces (employer decision problem, primary identity + avoid identity, motivation bridge, CV direction, application direction…) inside a 450–900-word soft budget, the average surface gets on the order of 50–60 words. `DEC-09`'s own risk list (Decision Record Part D, item 1) names exactly this failure mode — "a schema makes an upstream hypothesis feel contractual" — as the strongest counter-argument, but the specific mechanism that would *produce* it (tight budget × non-zero minimums across many surfaces) is never examined as a conjunction.
**Delete-test:** Loosening either constraint alone (looser budget, or 0-minimums) removes the forcing function; nothing downstream depends on the current tightness.
**Cost/risk:** Pressure toward generic, schema-satisfying boilerplate per field — the specific failure `EXP-04` (JSON vs. Markdown falsification) is designed to detect — is partly self-inflicted by the budget/cardinality interaction rather than by JSON serialization itself, which will confound `EXP-04`'s result when it eventually runs.
**Smallest better design:** Raise the soft target modestly (e.g. 600–1100) or drop the hard minimum on requirement-map/evidence-plan entries to 0 for genuinely thin vacancies, consistent with the table's own "omitted when not applicable — never filled with placeholder prose" rule, which currently contradicts the ≥1 minimum for these two arrays.
**Second-order effect:** Decouples "was quality lost to JSON-format anchoring" from "was quality lost to a too-tight budget" for `EXP-04`, making that eventual experiment cheaper and cleaner to interpret.

### OPUS-004 — GATE-01 safe default leaves continuation reconciliation as unspecified human procedure
**Severity:** P2 · **Confidence:** Medium
**Location:** `Implementation Contract` §10 (`GATE-01` row); `DRAFT_NORMATIVE` §8.3 (continuation chat), §24.3 ("the human must not have to… synchronize state files"), `ACC-12`.
**Mechanism:** `GATE-01`'s safe default assumes the execution surface does *not* support in-session validation, making the two-attempt repair loop operator-mediated. Under that same default, §8.3's "a continuation chat begins by reconciling against the manifest and current artifacts on disk" has no mechanical support either — reconciliation becomes the human manually reading `status` output and relaying which jobs to skip into a fresh chat, every time a cluster-stage chat is interrupted.
**Delete-test:** Nothing currently breaks, because `status` already exposes the needed information — but `ACC-12` ("continuation reconciles… never a remembered pointer") is stated as a system guarantee while, under the safe default, it is entirely human-executed.
**Cost/risk:** Silent tension with §24.3's explicit promise that the human never synchronizes state — relaying a per-job skip list into a resumed chat is state synchronization in substance if not in name, and it recurs on every interruption across up to 15 cluster-stage chats.
**Smallest better design:** One explicit sentence: on continuation, run `status --cluster <id>`, paste the non-`_OK` job list as the resumed chat's first message. Turns an implicit expectation into a two-step, teachable procedure.
**Second-order effect:** Makes `ACC-12` actually verifiable as written — currently there is no artifact to check the claim against under the GATE-01 safe default.

## 3. State/authority surface audit

Authoritative: `run_manifest.json` (facts/identities/hashes only, `INV-20`), the three candidate authority files, the vacancy artifact per job. Derived and explicitly regenerable: `status.json`, `queue.md`, `job_context.json`, the evidence index's human view. Current-per-stage, single-owner: `strategy.json` → `draft_package.json` → `final_package.json`/`review.json`, sharing one semantic shape (`CTR-09`) specifically to avoid a draft-vs-final schema disagreement class. This is clean; P0.7's multi-object drift problem does not reappear here. Two exceptions:

### OPUS-005 — `exception_reason` smuggles channel facts back into core state
**Severity:** P2 · **Confidence:** High
**Location:** `DRAFT_NORMATIVE` §3.4 (`DEC-03`, enum values `LANGUAGE_NON_NB | NO_DOCUMENT_UPLOAD | STRUCTURED_CV_ONLY | SOURCE_UNREADABLE | OTHER`), §19.1 ("no core schema… mentions portals, channels, platforms… a reviewer can verify this by grepping the schemas"), §6.3 (manifest `jobs[].exception_reason`).
**Mechanism:** `NO_DOCUMENT_UPLOAD` is parenthetically defined as "portal-only structured entry" — a channel fact. It lives in the frozen `run_manifest.json`, a core schema. §19.1's claim that a reviewer can verify the absence of channel state "by grepping the schemas" is falsified by this single enum, which is a different field name for the same category of fact `DEC-02` claims to have fully deleted.
**Delete-test:** Removing the two channel-shaped values doesn't break the exception mechanism (`OTHER` + free text still covers the case) — it only removes the contradiction.
**Cost/risk:** Low real-world harm (the enum is small, low-cardinality, never validated against employer limits), but it is exactly the kind of self-verification claim a later reviewer will trust and be wrong to trust — a clean, checkable internal-consistency defect.
**Smallest better design:** Either (a) narrow `exception_reason` to `LANGUAGE_NON_NB | SOURCE_UNREADABLE | OTHER` and push channel detail into `notes` (never read by any validator), or (b) reword §19.1's claim to acknowledge that exception classification is a bounded, honest exception to the no-channel-state rule.
**Second-order effect:** Option (a) also simplifies `GATE-07`'s reason-counting: free-text `notes` aren't compared for the "more than two share a reason" trigger, so the trigger's behavior stops depending on how finely channel sub-reasons happen to be enumerated.

### OPUS-006 — RERUN strategy revision: history archival unstated
**Severity:** P3 · **Confidence:** Medium
**Location:** `DRAFT_NORMATIVE` §17.3 (`DEC-20`); cf. §7.3 (general current→history rule).
**Mechanism:** §17.3's "required to move the superseded versions into `history/`" grammatically attaches to `final_package.json`/`review.json` (the preceding sentence's subject). The next paragraph — "a RERUN may also revise the strategy in place" — never restates that the prior strategy is archived, though §7.3's general rule presumably should cover it.
**Delete-test:** If §7.3's general rule is meant to apply universally (plausible reading), nothing is actually broken — but the text doesn't say so at the one place a builder is most likely to special-case it.
**Cost/risk:** Audit-trail gap only, narrow blast radius (RERUN + explicit strategy revision is already a rare, human-initiated path).
**Smallest better design:** One clause: "a revised strategy follows the same current→history rule as §7.3."
**Second-order effect:** None material beyond closing the audit trail — flagged for completeness, not urgency.

## 4. Contract-zombie and deletion candidates

### OPUS-007 — Evidence index's lossless-coverage requirement is built and tested for a guarantee nothing downstream cashes
**Severity:** P1 · **Confidence:** High
**Location:** `DRAFT_NORMATIVE` §20.2–20.3 (`DEC-14`, `DEC-15`, `INV-28`); `Implementation Contract` §5 (`INV-28` row: "Coverage assertion failure fixture"); §14.6 (the actual proof the reference validator provides).
**Mechanism:** `DEC-14`'s justification is explicitly *enforcement*, not retrieval: "without stable addresses, reference validation degrades to substring matching." That need is fully served by *any* stable, resolvable address per evidence unit. `INV-28` goes further and requires the generator to prove **every byte** of every authority file belongs to exactly one leaf entry — an exhaustive, non-overlapping segmentation of hand-authored markdown (headings, prose, lists, code blocks, text before the first heading) that must be maintained correctly forever as the candidate edits those files between runs. Nothing downstream uses the completeness property mechanically: §14.6 states plainly that the reference validator "proves only that each reference resolves… whether the evidence supports the wording is a semantic judgment," and nothing checks that a used claim's supporting text was actually inside its cited leaf entry.
**Delete-test:** Replace the index with a stable-heading-ID address list (the source files already carry usable IDs — `PRJ-01`…`PRJ-10`, `EMP_OUS_ANALYSE`, `EDU_NTNU_ECON`, etc., per the candidate architecture's own §4.5 snapshot) and drop the full-partition proof. `DEC-25`'s synchronization requirement, the resolvability check, and every consumer named in §20.2 ("Stage-1 planning, Stage-2/3 source escape, final provenance, audit") keep working unchanged — none of them consume the coverage guarantee specifically, only the addressing.
**Cost/risk:** This is the single most expensive piece of net-new deterministic machinery in the whole build (a boundary-complete parser plus a coverage-assertion test suite) relative to its cashed value — larger, by the specification's own text, than the entire render-verification pipeline it sits beside.
**Smallest better design:** Heading/ID-keyed address list, hashed per entry, no exhaustiveness proof; keep everything else in §20.3 (hash, regeneration, `STALE_INDEX`) unchanged.
**Second-order effect:** Removes the `INDEX` invalidation class's most fragile trigger (a regeneration hash mismatch on *unchanged* source content caused by generator nondeterminism at document edges) — a failure mode that only exists because exhaustiveness was required in the first place.

*(Cross-reference: the two speculative hooks in Implementation Contract §11 are a smaller instance of the same forward-zombie pattern — pre-built surface for a consumer that doesn't yet exist. Full write-up at OPUS-012, §7, since their defect is specifically the optionality-only justification, not build cost.)*

## 5. Semantic overconstraint

The strategy's enum vocabulary (`class: MINIMUM|DESIRED|TASK|CONTEXT`, `relation: SUPPORTED|ADJACENT|GAP|NOT_MATERIAL|UNKNOWN`, `role: BRIDGE_PRIMARY|BRIDGE_SECONDARY|SUPPORT`) was examined as a candidate for trimming and largely earns its keep — see §9. The real overconstraint risk in this draft is the budget/cardinality interaction already covered as **OPUS-003**; it belongs here as much as in §2, since its effect is specifically to squeeze Stage 1's semantic freedom through a mechanical channel (word count) rather than a stated content rule. One smaller instance:

### OPUS-008 — Duplicated "avoid list" micro-structure
**Severity:** P3 · **Confidence:** Medium
**Location:** `DRAFT_NORMATIVE` §10.3 ("CV direction: emphasis, employment IDs to foreground, avoid list" / "application direction: backbone, 2–3 proof arcs, one interview hook, avoid list").
**Mechanism:** Two independent `avoid list` fields, one per surface, where a single strategy-level avoid list would serve the same writer-guardrail purpose for both CV and letter (Stage 2 receives the whole strategy either way).
**Delete-test:** Merging into one field loses only the (unused) ability to say "avoid X in the CV but not the letter" — a distinction never invoked elsewhere in the spec.
**Cost/risk:** Trivial — a few words of schema, not a real burden. Included for completeness per the mission's instruction to name overconstraint, not because it materially matters.
**Smallest better design:** One `avoid` list at the top level of the strategy surface table.
**Second-order effect:** None material.

## 6. Mechanical underconstraint

### OPUS-009 — "Four reasons ⇒ RERUN" is prose, not a boundary, and the boundary it does have can reward concealment
**Severity:** P2 · **Confidence:** High
**Location:** `DRAFT_NORMATIVE` `CTR-10` (`reasons[0..3]`), §14.5/§16 ("a triage note that needs four reasons is a `RERUN`").
**Mechanism:** The schema hard-caps `reasons` at 3 (a genuine `BOUNDARY`). The rule that a fourth real issue should force `status = RERUN` is stated only as prose guidance to the model. Nothing cross-validates status against reason count, so a model that wants to stay in the easier `CHECK` lane can simply not report a fourth defect rather than escalate — the cap constrains the *symptom* (list length) without constraining the *claim* (escalation).
**Delete-test:** Today, removing the "four reasons" sentence changes nothing mechanically enforced — which is exactly the gap.
**Cost/risk:** Perverse incentive under time pressure (15 cluster chats to get through the batch); directly degrades `EXP-06`'s calibration data (`ReviewLoad`/`TailRecall20`) since under-escalation is invisible to both.
**Smallest better design:** A real cross-field `BOUNDARY`: `reasons.length > 3` at the point of writing the artifact is itself a schema violation unless `status = RERUN`. This is mechanically checkable (it's cardinality-vs-enum, not content judgment) and doesn't violate `INV-06`.
**Second-order effect:** Closes the concealment incentive without a new artifact, and strengthens `EXP-06`'s eventual calibration signal for free.

### OPUS-010 — DEC-18's "two attempts" rationale assumes exhaustive validator reporting, never stated
**Severity:** P2 · **Confidence:** Medium
**Location:** `DRAFT_NORMATIVE` §17.1 (`DEC-18`); §10.5/§15.2 (validator check lists, no stated fail-fast/exhaustive policy).
**Mechanism:** `DEC-18`'s own reasoning — "two, because the second attempt covers a fix that exposes a second, now-visible error" — only holds cleanly if a single validator run reports *every* violation in one pass. If validation is fail-fast (stops at the first failure), an artifact with three independent, pre-existing defects could exhaust the two-attempt budget on the third one appearing only after the first two are individually fixed, contradicting the stated rationale.
**Delete-test:** Nothing observable breaks today because the policy is simply unstated — which is the point: the load-bearing assumption behind a locked count (`DEC-18`) is currently implicit.
**Cost/risk:** Could silently make the two-attempt bound too tight for compound-defect artifacts, producing more `FAILED` states than intended by design, with the cause misattributed to "the model is bad at this" rather than "the validator under-reports."
**Smallest better design:** One line in the Implementation Contract: validators report all violations for an artifact in a single pass.
**Second-order effect:** Likely improves effective repair success without touching the attempt count — a free quality gain from a clarification, not new machinery.

### OPUS-011 — Amendment + job reclassification leaves prior artifacts' disposition unspecified
**Severity:** P3 · **Confidence:** Low-medium
**Location:** `DRAFT_NORMATIVE` §7.6 ("existing valid job artifacts survive an amendment unless their own inputs changed").
**Mechanism:** If a `freeze --amend` reclassifies a job from `CORE` to `EXCEPTION` (or the reverse) after that job already has valid strategy/draft/final/rendered artifacts, §7.6 doesn't say whether those artifacts are archived, left in place-but-orphaned from the core queue, or flagged.
**Delete-test:** Low-frequency edge case (the human triggers the amendment deliberately and is presumably aware of what they're reclassifying); nothing catastrophic follows either way.
**Cost/risk:** A `CORE→EXCEPTION` reclassification would leave fully rendered, verified documents sitting in the job directory but invisible to the core queue/metrics — plausible confusion during a real batch, not a correctness defect.
**Smallest better design:** One sentence: reclassified jobs retain prior artifacts unreferenced by the core queue; disposition is a human decision, not automatic deletion.
**Second-order effect:** None material — edge-case closure only.

## 7. Optionality/experiment tax

Personality (§21), the absent Luna/preparation layer (§22), `EXP-01`'s position logging, and the review schema's diagnostic fields are all appropriately cheap or already-free (the data or schema slot exists for other reasons). One exception:

### OPUS-012 — Two Step-3 hooks are justified by the exact rationale the spec itself forbids
**Severity:** P2 · **Confidence:** High
**Location:** `Implementation Contract` §11 ("strategy serialization seam… so a Markdown variant can be added without touching Stage-2/3 code paths"; "optional advisory artifact slot… nothing in the baseline reads it"); `DRAFT_NORMATIVE` §2.4 ("a mechanism whose only benefit is future optionality is rejected — reversibility ranks last").
**Mechanism:** Both hooks are explicitly justified by making a *future, unscheduled* change easier — precisely the justification §2.4 names and rejects. Neither hook unlocks anything not already possible without it: a future builder can refactor a JSON-read call site into a shared function whenever `EXP-04` actually needs it, and can drop an unreferenced file into a job directory at any time — `INV-21`'s structural invariants don't forbid extra files, so there is no "slot" to reserve.
**Delete-test:** Removing both paragraphs changes zero present behavior and blocks zero future option.
**Cost/risk:** Small in isolation (a few sentences of spec, no runtime cost), but it's a direct textual self-contradiction inside a document whose main discipline *is* refusing optionality-only justifications elsewhere (portal, priority, Luna). Worth naming on principle as much as on cost.
**Smallest better design:** Delete both paragraphs from §11. Keep the two genuinely free hooks (position logging, diagnostic fields) as-is since they cost nothing beyond what already exists.
**Second-order effect:** Reinforces §2.4 as an actually-enforced rule rather than one with a standing exception, which matters for how the next amendment (§31) gets argued.

## 8. Build-surface burden

Quantified Step-2 surface: 6 schemas, 5 task-oriented commands, 11 `STEP2_VERIFY` gates (6 blocking), 15 Tier-1 tests plus Tier-2/3, 6 named adversarial security fixtures, 2 lexical scanners (leakage/placeholder, typology-vocabulary), one template-map validator, an 8-point per-document render verification run across up to 4 documents × ~40 jobs, and one evidence-index generator. Against the objective hierarchy's own ranking (quality, human effort, then implementation speed), most of this is proportionate — `GATE-11`'s decision to bundle nearly all empirical risk into one blocking end-to-end gate rather than scattering it is good practice, worth calling out as the positive counterpart to the findings above.

The evidence-index generator (**OPUS-007**) is the one component whose build cost is disproportionate on its own terms: a boundary-complete segmentation parser plus a coverage-assertion test fixture is materially harder to build and keep correct than the entire finalizer's render-verification logic, for three hand-maintained markdown files that already carry usable heading-level IDs. It is also the only major piece of core-path machinery in this draft that is unconditionally built (not gated behind a `GATE-xx`) despite its distinguishing feature — full coverage, not mere addressing — being something no `ACC` criterion or downstream validator actually consumes. Everything else of comparable size (rendering, security) is either gated on empirical verification or serves a mechanically-checked contract end to end. This asymmetry is the clearest single build-effort argument for **OPUS-007**'s recommended cut.

## 9. Simplifications considered but rejected because value would be lost

- **Requirement map** (§10.3, §13.2, §20.4) — looks like formalization overhead (a 1–12-entry structured array, private, never rendered) but Norwegian state-sector hiring genuinely requires comparative assessment against posted qualifications (`05_EVIDENCE` §2.4), and the candidate's own current employer (Oslo universitetssykehus HF, per the candidate snapshot in `02_CANDIDATE_ARCHITECTURE` §4.5) is public-sector — this is not a remote edge case for this user. Kept.
- **Identity/contact in body flow** (`DEC-29`) — considered recommending the cheaper-looking alternative (leave header-only, rely on `GATE-06` testing) and rejected it: testing-only is a recurring cost against every future template change, while the one-time template edit permanently retires the risk class, which matters more given `D-005`'s multi-batch reuse horizon.
- **Two-attempt repair bound** (`DEC-18`) — considered recommending one attempt for maximum simplicity; rejected because the stated rationale is sound and the mechanism is already minimal, cheap and explicitly reversible. (The real issue here is the unstated exhaustive-vs-fail-fast assumption — **OPUS-010** — a clarification, not a complexity cut.)
- **Exception class as first-class manifest state** (§3.4) — considered recommending handling non-conforming jobs entirely off-system with no manifest trace; rejected because the cost is one enum and one reason field, and it protects against a failure mode the corpus repeatedly names as a hard regression signal: an approved job silently disappearing.
- **Static invalidation classes** (§7.5, `DEC-26`) — considered recommending collapsing this to "re-run everything if anything changed"; rejected because the per-class minimum-stale-scope table is a static lookup, not a dependency engine, and avoids wastefully re-running all three semantic stages when only a render asset changed.

### 20% deletion challenge

Ranked by mechanism-surface removed per unit of product value preserved:

1. **Drop `INV-28`'s lossless-coverage requirement** (OPUS-007). Keep the evidence index as a generated, hashed, resolvable address list built on the source files' own existing heading IDs; delete the exhaustive byte-partition proof and its dedicated test fixture. This is the single largest chunk of net-new deterministic engineering in the draft, and nothing downstream consumes the property it uniquely buys.
2. **Delete the two Step-3 hooks** (OPUS-012) — the strategy-serialization seam and the advisory-artifact slot. Both are addable later at zero prior cost; pre-declaring them only adds spec weight and one internal contradiction.
3. **Un-collapse `DEC-01`**: bring back `letter_required` + `application: null` (OPUS-001). This adds one field but removes four downstream branches of wasted work per affected job (writing, finalizing, two renders, eight-point verification ×2) — a net shrink in mechanism-and-effort surface even though schema surface grows slightly.
4. **Fix, don't build**: reword §19.1's grep-the-schemas claim or narrow `exception_reason` (OPUS-005), and state the strategy's word-budget/cardinality-minimum resolution (OPUS-003). Both are documentation/parameter fixes, not new infrastructure, and both remove self-inflicted risk the draft would otherwise only discover empirically after a real batch.

Nothing on this list requires building anything new; each is a deletion, a parameter change, or a one-sentence clarification.
