# P0.9_CRITIQUE_GEMINI_FLASH_BLINDSPOTS_AMBIGUITY.md

## 1. Executive verdict

The draft P0.Opus architecture package (`Normative Specification`, `Decision Record`, and `Implementation Contract`) is a significant step toward an executable P0.9 baseline. It successfully prunes legacy P0.7/P0.8 sprawl, removes unneeded portal/channel complexity from the core, ratifies the three-stage Selective Quality topology, and establishes a clear separation between mechanical validation and semantic judgment.

However, a fresh Codex implementation agent or maintainer following these documents as written **would encounter critical lifecycle deadlocks, state derivation contradictions, and fallback incompatibilities**. Specifically, the specification:

1. **Creates a state derivation deadlock for failed artifacts:** It mandates that job status (`STRATEGY_FAILED`, etc.) is derived from failure records, while simultaneously forbidding the status engine from reading `history/` and omitting failure records from schemas and root layouts.
2. **Defines an unhandled clash between the invariant 4-document render contract and the `GATE-03` DOCX-only fallback:** A target machine without headless LibreOffice will hard-fail validation and delivery across the entire pipeline without an explicit DOCX-only operational mode.
3. **Leaves RERUN strategy updates in state limbo:** A RERUN updating `strategy.json` will flag downstream artifacts as stale, but because Stage 2 (Draft) is intentionally bypassed during RERUN, the system cannot reach a clean `DELIVERED_READY` state under the static invalidation rules.
4. **Leaves several metadata items without canonical schema homes:** Fields like `requires_source_inspection` and human deliverable edit protections are referenced in operational prose but omitted from formal JSON schemas and deterministic file contracts.

These defects are not fundamental design flaws; they are contractual interface and lifecycle omissions. They can be resolved entirely via a targeted, non-architectural patch set.

## 2. Freeze-blocking contradictions

### `GEM-001`
- **Severity:** P0
- **Type:** Contradiction / Lifecycle
- **Exact draft location(s):** Spec §7.2, §7.3; Contract §3, §4, §5 (`INV-10`)
- **Canonical evidence:** `01_CURRENT_STATE_AUTHORITY_AND_DECISIONS.md` §3.4; `02_P0.9_CANDIDATE_ARCHITECTURE.md` §16, §20.1
- **Plausible wrong interpretation:** The builder reads Spec §7.2 ("`STRATEGY_FAILED`: a failure record is the newest strategy event") and writes a failure record to `history/`, but then implements Contract §3 ("`history/*` ... never read by validators or status derivation"). As a result, when Stage 1 fails, `status.py` ignores `history/`, sees no current `strategy.json`, and reports the job as `PLANNED` instead of `STRATEGY_FAILED`. Alternatively, the builder places an un-schematized `strategy.failure.json` in the job root, causing schema validation to fail on unknown files.
- **Consequence:** The system cannot deterministically distinguish between unstarted jobs (`PLANNED`) and jobs that failed bounded repair (`FAILED`). Queue derivation and partial-success tracking break.
- **Minimal patch:** 
  1. Specify that when a stage fails bounded repair, it writes a canonical, schematized current artifact with `status: "FAILED"` (e.g., `strategy.json` with an explicit failure schema variant or a dedicated `stage_failure.json` current pointer per stage).
  2. Clarify that `status.py` inspects current job directory pointers, not `history/`.
  3. Add a lightweight `failure_record.schema.json` to Contract §4.
- **Confidence:** High

### `GEM-002`
- **Severity:** P1
- **Type:** Contradiction
- **Exact draft location(s):** Spec §3.1 (`CTR-01`), §18.3 (`CTR-11`), §30 (`ACC-17`), §28 (`GATE-03`); Contract §7
- **Canonical evidence:** `01_CURRENT_STATE_AUTHORITY_AND_DECISIONS.md` §3.5 (`D-040/041`); `04_IMPLEMENTATION_BASELINE_AND_BUILD.md` §3.4, §5.3
- **Plausible wrong interpretation:** The builder implements `CTR-01` and `ACC-17` as hard mechanical boundaries that require all four files (`CV.docx`, `CV.pdf`, `LETTER.docx`, `LETTER.pdf`) and mandatory PDF text extraction. When running on a target Windows machine where LibreOffice is absent (`GATE-03` fallback active: "DOCX-only delivery is an acceptable interim"), `finalize.py` and `status.py` crash or mark 100% of jobs `FAILED`.
- **Consequence:** The system cannot operate in the interim DOCX-only mode explicitly permitted by `GATE-03` without failing its own normative acceptance criteria.
- **Minimal patch:** In Spec §3.1, §18.3, and Contract §7, specify that `expected_documents` is governed by `settings.render_mode` (`DOCX_AND_PDF` default, `DOCX_ONLY` fallback). If `DOCX_ONLY` is active, `ACC-17` and `RENDERED` derivation require only the two DOCX files.
- **Confidence:** High

## 3. Lifecycle/state ambiguities

### `GEM-003`
- **Severity:** P1
- **Type:** Lifecycle / Ambiguity
- **Exact draft location(s):** Spec §7.5, §17.3; Decision Record `DEC-20`
- **Canonical evidence:** `02_P0.9_CANDIDATE_ARCHITECTURE.md` §17.2; `08_P081_CONSOLIDATED_PREIMPLEMENTATION_HARDENING.md` §RERUN
- **Plausible wrong interpretation:** A human triggers a `RERUN` for job `J01` and requests an updated strategy. The RERUN session produces a new `strategy.json`, skips Stage 2 (Draft), and directly produces `final_package.json` and `review.json`. When `status.py` runs, it checks static invalidation (§7.5: "Strategy changed -> Draft, final, review, rendered for that job") and flags `draft_package.json` as `STALE_STRATEGY`. The builder implements status derivation such that any stale upstream artifact marks the whole job `STALE`, blocking `DELIVERED_READY`.
- **Consequence:** RERUNs that touch strategy can never achieve a clean delivered state without artificially and redundantly running Stage 2.
- **Minimal patch:** Explicitly state in Spec §7.2 and §7.5 that `final_package.json` produced by a validated `RERUN` supersedes prior draft staleness. If `final_package.json` and `review.json` are newer than `strategy.json`, `draft_package.json` is archived or marked superseded, and the job evaluates to `DELIVERED_*`.
- **Confidence:** High

### `GEM-004`
- **Severity:** P2
- **Type:** Lifecycle / Ambiguity
- **Exact draft location(s):** Spec §6.3, §7.4, §7.6; Contract §2, §5 (`INV-20`)
- **Canonical evidence:** `02_P0.9_CANDIDATE_ARCHITECTURE.md` §5.3, §20.3; `08_P081_CONSOLIDATED_PREIMPLEMENTATION_HARDENING.md` §Freeze
- **Plausible wrong interpretation:** The builder reads `INV-17` / §7.4 ("A frozen manifest is never mutated in place") and assumes `freeze --amend` must create a brand-new run directory (`runs/<run_id_v2>/`), copying all completed job outputs. Another builder reads §7.6 ("`freeze --amend` writes a new manifest version... preserves the prior manifest in history") and overwrites `runs/<run_id>/run_manifest.json` after copying the old one to `runs/<run_id>/history/run_manifest_<ts>.json`.
- **Consequence:** Inconsistent directory structures across implementations; potential duplication of large artifact trees or accidental breakage of immutable hash audits.
- **Minimal patch:** Reconcile §7.4 and §7.6: state that `run_manifest.json` is immutable *during normal stage execution*, but `freeze --amend` performs an atomic replacement of `runs/<run_id>/run_manifest.json` within the same `run_id`, archiving the previous manifest version to `runs/<run_id>/history/run_manifest_v<N>.json`.
- **Confidence:** High

### `GEM-005`
- **Severity:** P2
- **Type:** Observability / Lifecycle
- **Exact draft location(s):** Spec §4 (`INV-11`), §27.3; Contract §5 (`INV-11`), §11
- **Canonical evidence:** `01_CURRENT_STATE_AUTHORITY_AND_DECISIONS.md` §3.6 (`D-034–037`); `02_P0.9_CANDIDATE_ARCHITECTURE.md` §25, §26.3
- **Plausible wrong interpretation:** An operator annotates `runs/<run_id>/queue.md` with human pilot quality scores (1–10) and review minutes as instructed in Spec §27.3. Later, the operator runs `status.py` or `finalize.py`. The script re-generates `queue.md` byte-identically from scratch (`INV-11`), wiping out the human's manual review notes and scores.
- **Consequence:** Loss of pilot calibration data and human time tracking.
- **Minimal patch:** Explicitly state in Contract §11 and Spec §24.4 that `queue.md` is a purely derived, disposable view. Human pilot annotations must be stored in an external file (e.g., `runs/<run_id>/human_pilot_log.csv` or `batch_inventory.csv` operator columns) which is preserved across status re-derivations.
- **Confidence:** High

## 4. Implementer-misread risks

### `GEM-006`
- **Severity:** P1
- **Type:** Implementer-Misread / Validation Gap
- **Exact draft location(s):** Spec §10.3, §11.4, §14.5, §14.6, §21.4; Contract §4
- **Canonical evidence:** `01_CURRENT_STATE_AUTHORITY_AND_DECISIONS.md` §3.2 (`SD-EVID-01`); `02_P0.9_CANDIDATE_ARCHITECTURE.md` §6.3, §13.4
- **Plausible wrong interpretation:** The builder sees that Stage 1 (`strategy.json`) maps evidence refs to specific requirements and bridges, and reads Spec §21.4 ("A facet without at least one supporting evidence_ref is a schema error"). The builder assumes `final_package.json` must also have granular per-bullet or per-paragraph `evidence_refs`. However, Contract §4 defines `used_evidence_refs` as a single flat top-level array `["ID1", "ID2"]`. The builder either:
  1. Rejects valid `final_package.json` files for lacking per-field citations, or
  2. Implements a validator that only checks if strings in `used_evidence_refs` exist in `evidence_index`, without realizing that a model can hallucinate in `profile` while dumping all index IDs into `used_evidence_refs` to pass validation.
- **Consequence:** Either premature mechanical rejection of valid Stage 3 outputs, or false confidence that mechanical validation verifies text attribution.
- **Minimal patch:** 
  1. Explicitly clarify in Contract §4 and Spec §14.6 that in `draft_package.json` and `final_package.json`, `used_evidence_refs` is strictly a flat top-level audit array.
  2. Add an explicit `PROTOCOL` instruction to Stage 3 to ensure every factual claim in the prose is covered by at least one ID in `used_evidence_refs`.
  3. Reiterate in §15.2 that mechanical code verifies set resolvability only.
- **Confidence:** High

### `GEM-007`
- **Severity:** P2
- **Type:** Implementer-Misread / Safety
- **Exact draft location(s):** Spec §24.2; Contract §6.7, §9
- **Canonical evidence:** `01_CURRENT_STATE_AUTHORITY_AND_DECISIONS.md` §3.1 (`D-002`); `04_IMPLEMENTATION_BASELINE_AND_BUILD.md` §6.7
- **Plausible wrong interpretation:** Contract §6.7 and §9 dictate "no accidental overwrite of human-edited final deliverables". The builder assumes `finalize.py` must inspect file modification times or compare DOCX hashes against a snapshot before re-rendering. If a human opened and saved a DOCX to fix a typo, `finalize --job <id> --render-only` detects a modification and refuses to run, or errors out with no way to proceed.
- **Consequence:** The finalizer either silently clobbers human Word edits or deadlocks on human-edited files without a documented force/bypass flag.
- **Minimal patch:** Define the human-edit protocol in Spec §24.2:
  1. Minor text edits should be made in `final_package.json` before running `finalize --render-only`.
  2. If the human edits `CV.docx` or `LETTER.docx` directly, it is considered a post-pipeline submission artifact.
  3. `finalize.py` will overwrite rendered files from `final_package.json` unless an explicit `--no-clobber` flag is passed, or will require `--force` if a hash mismatch is detected.
- **Confidence:** High

### `GEM-008`
- **Severity:** P2
- **Type:** Implementer-Misread / Contract Gap
- **Exact draft location(s):** Spec §10.4 (`DEC-11`)
- **Canonical evidence:** `02_P0.9_CANDIDATE_ARCHITECTURE.md` §9.5
- **Plausible wrong interpretation:** Spec §10.4 mandates: "Total prose across all prose fields: soft target 450–900 words; validator warning above 1200; hard failure above 1600." The builder implements this by running a generic word counter on the entire `strategy.json` file text or all string values. This counts JSON keys, enum names (`BRIDGE_PRIMARY`, `NON_FACTUAL_NON_FINAL`), evidence IDs, and requirement strings, triggering spurious hard failures on concise strategies.
- **Consequence:** Valid, dense Stage 1 strategies fail schema/mechanical validation unexpectedly.
- **Minimal patch:** Enumerate the exact fields included in the strategy word count budget in Contract §4 / Spec §10.4: `employer_decision_problem`, `primary_candidate_identity`, `motivation_bridge`, `cv_direction`, `application_direction`, `writer_notes`, plus prose fields in `requirement_map` and `evidence_plan`. Exclude enum values, IDs, keys, and epistemic constants.
- **Confidence:** High

## 5. Missing edge cases/contracts

### `GEM-009`
- **Severity:** P2
- **Type:** Omission / Schema Gap
- **Exact draft location(s):** Spec §6.4; Contract §4
- **Canonical evidence:** `02_P0.9_CANDIDATE_ARCHITECTURE.md` §3.2, §7.3
- **Plausible wrong interpretation:** Spec §6.4 states that extraction sanity checks at freeze set `requires_source_inspection` on a job. However, `requires_source_inspection` is omitted from the Manifest schema in Spec §6.3 and Contract §4. A builder strictly following the schema validator (which rejects unknown properties) will fail to serialize this flag into `run_manifest.json`, causing the warning to be lost.
- **Consequence:** The downstream model prompt never receives the signal that normalized vacancy text is suspect, leading to hallucinated or misread requirements.
- **Minimal patch:** Add `requires_source_inspection: boolean` (default `false`) to the `jobs[]` object schema in `run_manifest.schema.json` in Contract §4 and Spec §6.3.
- **Confidence:** High

---

### `GEM-010`
- **Severity:** P2
- **Type:** Edge Case / Generator Specification
- **Exact draft location(s):** Spec §20.3 (`INV-28`); Contract §5 (`INV-28`)
- **Canonical evidence:** `04_IMPLEMENTATION_BASELINE_AND_BUILD.md` §1.3; `05_EVIDENCE_CONTEXT_AND_EVALUATION.md` §6.2
- **Plausible wrong interpretation:** `INV-28` requires lossless byte coverage where every byte belongs to exactly one leaf entry. Canonical authority files (`Work_experience.md`, etc.) contain file titles, preambles, and metadata before the first Markdown heading (`#` or `##`). The builder either:
  1. Omits preamble bytes from the index, causing the `INV-28` byte-coverage test fixture to fail, or
  2. Creates inconsistent artificial IDs (e.g., `work_experience#` vs `work_experience#preamble` vs `work_experience#root`), breaking cross-job reference resolution.
- **Consequence:** Deterministic index generation fails its own test assertions, or produces unresolvable evidence IDs for preamble content.
- **Minimal patch:** Specify the canonical heading path for preamble/top-level content in `evidence_index` generator rules: bytes preceding the first heading must be indexed under `heading_path: "ROOT"` and `evidence_id: "<source_file_stem>#root"`.
- **Confidence:** High

### `GEM-011`
- **Severity:** P2
- **Type:** Edge Case / Workflow Recovery
- **Exact draft location(s):** Spec §8.3, §24.1
- **Canonical evidence:** `01_CURRENT_STATE_AUTHORITY_AND_DECISIONS.md` §3.3 (`D-023`); `02_P0.9_CANDIDATE_ARCHITECTURE.md` §3.3
- **Plausible wrong interpretation:** A cluster chat disconnects or exhausts context on job 5 of 8. The operator opens a new continuation chat. The draft states that a continuation chat reconciles against the manifest and disk artifacts. However, neither the Spec nor the Contract specifies what context must be loaded into the continuation chat: does it reload the full cluster history, or start clean with the next uncompleted job?
- **Consequence:** The operator might paste previous job outputs into the chat, causing context bloat and prompt token exhaustion, or fail to re-establish stage instructions.
- **Minimal patch:** Explicitly state the continuation chat protocol in Spec §8.3: A continuation chat loads the Stage Instruction, the cluster ID, and begins directly at the first job in the cluster sequence whose current artifact for that stage is missing or `FAILED`. It loads no prior completed job artifacts.
- **Confidence:** High

## 6. Material context loss or overconfidence

### `GEM-012`
- **Severity:** P2
- **Type:** Overconfidence / Scope creep
- **Exact draft location(s):** Spec §13.3 (`INV-25`), §21.3
- **Canonical evidence:** `01_CURRENT_STATE_AUTHORITY_AND_DECISIONS.md` §4; `02_P0.9_CANDIDATE_ARCHITECTURE.md` §12, §15.2
- **Plausible wrong interpretation:** Spec §21.3 allows a lexical scan on employer-facing fields for personality typology terms (MBTI/DISC/Enneagram/RIASEC). Spec §13.3 lists forbidden stock phrases (*brenner for, spennende reise*, etc.) but states this is a model prompt instruction, not a code gate (`INV-25`). However, because both are lexical checks, an overzealous implementer combines them into a single Python regex blacklist in `finalize.py`.
- **Consequence:** False-positive mechanical validation failures on legitimate Norwegian phrases (e.g., an applicant describing a hospital's *spennende reise* in digitization), violating `INV-06`.
- **Minimal patch:** Add an explicit test fixture in Tier 1 (`ACC-09`/`ACC-18`) asserting that a package containing a stock phrase like *brenner for* passes mechanical validation, while confirming that only typology jargon and private leakage tokens fail.
- **Confidence:** High

## 7. Findings investigated and rejected

1. **Detached portal workflow violates P0.8 intent:**
   - *Investigation:* P0.8 had portal generation in core; the draft detaches it (`DEC-02`).
   - *Verdict:* **Rejected.** User decisions `D-011` and `D-012` explicitly granted permission to simplify the core to an invariant CV + letter and detach portals. The draft appropriately leveraged this permission.

2. **JSON Strategy (`DEC-09`) violates the Markdown normative baseline:**
   - *Investigation:* P0.8.0 normatively specified `strategy.md`.
   - *Verdict:* **Rejected.** `RQ-04` explicitly reopened strategy serialization for Step 1 freeze. The draft provides sound rationale (uniform JSON parsers, mechanical reference checking) and maintains reversibility via `EXP-04` and generated `strategy.view.md`.

3. **Personality default OFF contradicts P0.9 brainstorm:**
   - *Investigation:* Early P0.9 brainstorms explored rich personality injection.
   - *Verdict:* **Rejected.** `D-031` locked personality as optional and off-safe. Default OFF for the first batch is a prudent experimental baseline to avoid confounding `Q_happy` calibration.

4. **Absence of Vector DB / GraphRAG is an architectural flaw:**
   - *Investigation:* Evaluated whether direct authority lookup scales.
   - *Verdict:* **Rejected.** Universal retrieval platform is an explicit non-goal (`NON_GOALS`, `01_CURRENT_STATE_AUTHORITY_AND_DECISIONS.md` §4). At 1 candidate and ~40 jobs, direct file navigation + deterministic indexing is strictly superior in cost and simplicity.

## Concluding answer

**Could a fresh Codex implementation agent plausibly build the wrong system while believing it conformed?**

**YES — ONLY IN THESE AREAS:**
1. **Failure State Tracking:** Implementing status derivation that reads `history/` (violating `INV-10`/Contract §3) or leaving failed jobs in `PLANNED` state due to lack of a current failure representation (`GEM-001`).
2. **Headless Converter Fallback:** Building a rigid 4-document verification engine that hard-fails the entire pipeline when `GATE-03` interim DOCX-only mode is activated (`GEM-002`).
3. **RERUN Staleness Deadlock:** Marking RERUN-reconstructed packages as permanently `STALE` because the bypassed Stage 2 draft artifact is older than the updated strategy (`GEM-003`).
4. **Evidence Reference Over- or Under-Validation:** Misinterpreting flat `used_evidence_refs` validation as either requiring nonexistent per-bullet schema structures or verifying semantic truth (`GEM-006`).
5. **Human Annotation & Edit Erasure:** Building derived view generators (`queue.md`) and renderers that wipe out human pilot scores and manual Word edits on subsequent runs (`GEM-005`, `GEM-007`).
