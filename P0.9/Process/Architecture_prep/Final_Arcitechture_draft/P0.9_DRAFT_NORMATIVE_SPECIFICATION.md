# Jobbsøk_26 P0.9 — Draft Normative Specification

## 1. Status and scope

### 1.1 What this document is

This is a complete proposed P0.9 architecture for Jobbsøk_26: one candidate, private, local, file-authoritative, manually initiated. It resolves every `STEP1_FREEZE` item in the context package with a proposed decision, and assigns every remaining uncertainty to a verification gate (`GATE-xx`) or an experiment (`EXP-xx`).

It is written to be evaluated without reconstructing project history. Where a rule is inherited rather than invented here, the inheritance is labelled, not hidden.

### 1.2 Authority labels used in this document

| Label | Meaning |
|---|---|
| `[USER]` | Explicit user decision represented in the context package. Not reopened here. |
| `[USER-PERMISSION]` | The user permitted an option without selecting it. This draft selects. |
| `[NORMATIVE]` | Unsuperseded P0.8.0 rule inherited as authority. |
| `[VERIFIED]` | Direct implementation/audit evidence (mainly the P0.7 release). |
| `[RESEARCH]` | External empirical evidence; constrains risk, does not choose policy. |

Any statement in this document marked `[DRAFT-DECISION]` is the author's proposal. It must never be cited downstream as a prior user decision.

### 1.3 Identifier system

- `DEC-xx` — architectural decision made or ratified here (rationale in the Decision and Adoption Record).
- `INV-xx` — invariant that must hold at all times in a conforming implementation.
- `CTR-xx` — artifact or interface contract.
- `ACC-xx` — acceptance/release criterion.
- `GATE-xx` — `STEP2_VERIFY` gate: an empirical question with a safe default posture.
- `EXP-xx` — `STEP3_EXPERIMENT`: a causal question the baseline does not depend on.

Ordinary prose is not identified. Only load-bearing elements carry IDs.

### 1.4 Scope boundaries

In scope: the production architecture from human-approved vacancy to reviewable, renderable, manually submittable package, plus its state, contracts, failure semantics, verification obligations and evaluation design.

Out of scope: repository module layout, class and function names, library selection without architectural reason, prompt wording, and any parameter this document explicitly assigns to `GATE-xx` or `EXP-xx`.

### 1.5 Supersession

If adopted, this specification supersedes the P0.9 candidate architecture in the context package and every P0.8.0/P0.8.1 rule it explicitly addresses. P0.8.1 mechanisms not adopted here are **not** inherited: an unadopted hardening is not a contract. Historical rationale remains available; historical contracts do not.

## 2. Objective and optimization hierarchy

### 2.1 Product objective

`[USER]` Maximize the quality distribution of the useful majority, not uniformity:

```text
Q_happy = (median(package_quality) + mean(top_80_percent(package_quality))) / 2
```

Practical target: roughly **30 strong packages from about 40**, with the weak tail cheaply identified and selectively rerun, separately handled, or dropped.

`Q_happy` is an evaluation function computed by the human after the fact. `INV-01` No runtime component computes, stores or acts on a package quality score.

### 2.2 Optimization order

`[USER]` Among options that satisfy the hard constraints:

1. final package quality / expected interview value;
2. low human effort;
3. fast and simple implementation;
4. model cost;
5. reversibility / optionality.

Secondary tie-breaker (older, still useful): human effort > human complexity > model complexity > model effort.

### 2.3 Hard constraints

`[USER]` These are not tradeable against any position in §2.2:

- factual truth and interview-defensibility of every material claim;
- correct candidate identity and attribution;
- employer usability of the delivered artefacts;
- human authority over final approval and every irreversible action.

### 2.4 What the objective forbids

The optimization order is a design test, applied throughout this document:

- a mechanism that raises tail uniformity while costing strong-package quality is rejected;
- a mechanism that costs human minutes per package to protect against a rare mechanical defect is rejected;
- a mechanism whose only benefit is future optionality is rejected (reversibility ranks last);
- an abstraction justified by a hypothetical second candidate, second language or second product is rejected (`D-005`: one candidate, many batches).

## 3. Product contract and non-goals

### 3.1 Core product — `DEC-01`

`[DRAFT-DECISION]` (resolves `RQ-01a`, exercising `[USER-PERMISSION] D-011`)

**The P0.9 core product is an invariant pair: one tailored CV and one tailored application letter, in `nb-NO`, produced for every core job without conditional branching.**

There is no `letter_required` branch, no CV-only branch and no portal branch in the core. Every core job produces both documents in both DOCX and PDF. If a specific employer does not want the letter, the human does not submit it; the marginal cost of an unused letter is far below the cost of a conditional product surface that contaminates intake, schema, validation, rendering and review.

`CTR-01` Core deliverable set per core job:

```text
final CV        : DOCX + PDF
final letter    : DOCX + PDF
final package   : validated JSON (semantic source of both documents)
review          : validated JSON (status + reasons)
```

### 3.2 Portal and form answers — `DEC-02`

`[DRAFT-DECISION]` (resolves `RQ-01b`, exercising `[USER-PERMISSION] D-012`)

**Portal/form answers are detached from the core.** No portal field, portal schema, portal limit, portal status or channel matrix exists in any core artifact or validator. Portal answering is a downstream, human-initiated assist that runs *after* a final package exists (§19). It is not required for release (`ACC` set excludes it).

Consequence, applied aggressively: every P0.8.1 portal hardening mechanism — canonical channel matrix, portal question identity/uniqueness, portal limit validation, portal-state coherence, portal delivery classes — is **deleted**, not reimplemented and bypassed. The P0.7 duplicate-portal-ID defect is thereby not fixed but eliminated.

### 3.3 Language — `DEC-04`

`[DRAFT-DECISION]` (resolves `RQ-02`, exercising `[USER-PERMISSION] D-013`)

**Core v1 is `nb-NO` only.** `language` is a schema constant, not a variable. Prompts, writing standards, templates and validators assume Bokmål. A non-Norwegian vacancy is not a core job.

### 3.4 Exception class — `DEC-03`

`[DRAFT-DECISION]` Any approved vacancy that the invariant core cannot serve is marked `EXCEPTION` at intake with a reason, and is:

- recorded in the run manifest (so it cannot be silently lost);
- excluded from the core expected set (so it cannot make the run look failed);
- excluded from core validation, rendering and status derivation;
- handled by the human, optionally with an ad-hoc model chat, outside the pipeline.

Recognised exception reasons: `LANGUAGE_NON_NB`, `NO_DOCUMENT_UPLOAD` (portal-only structured entry), `STRUCTURED_CV_ONLY`, `SOURCE_UNREADABLE`, `OTHER` (free text required).

`INV-02` An exception job never blocks, delays or invalidates a core job, and never appears in core quality metrics.

### 3.5 Non-goals (regression firewall)

Inherited and re-asserted. These stay out of P0.9 unless a **named observed failure** in a real batch demonstrates material value:

API/model-call orchestration as normal workflow; multi-agent debate or subagents; vector DB, embeddings, GraphRAG, semantic cache; role/archetype memory; automatic model routing; LLM-as-judge stage or numeric fit gate; automatic retries or hidden repair loops; best-of-N packages; default employer research; automatic job search, employer contact, profile mutation or submission; database/event-sourced runtime; automatic dependency engine; generalized claim-graph platform; settings compiler; global cheap-model relevance filter; mandatory personality or Luna; typography auto-fit; persistent LibreOffice daemon; n-gram/similarity hard gate; semantic truth validator in code; universal handling of rare channels, languages or candidate types; per-job copies of candidate authorities; `_DONE` markers or heading/substring completion signals.

Two additions from this draft: **no portal machinery in core** (§3.2) and **no language branch in core** (§3.3).

## 4. Core principles and invariants

Every invariant is typed by how it is enforced, so that no requirement exists without an enforcement or verification path.

Control types: `BOUNDARY` = mechanically enforced by deterministic code; `PROTOCOL` = instructed model behavior, observable but not provable; `ADVISORY` = optional influence; `HUMAN_GATE` = a person decides.

| ID | Invariant | Type | Enforcement / verification |
|---|---|---|---|
| `INV-01` | No runtime component emits or consumes a numeric package quality/confidence score. Human pilot scoring (§27) is external measurement, not a runtime signal, and never feeds back into a stage. | `BOUNDARY` | Schemas forbid such fields; test asserts rejection. |
| `INV-02` | One job is the transaction. A failed or weak job cannot block, mutate or invalidate another job. | `BOUNDARY` | Partial-success test: one poisoned job, others finalize and their outputs hash-unchanged. |
| `INV-03` | Candidate factual authority is exactly the three authority files; the vacancy is authority for employer facts. Nothing downstream raises a claim ceiling. | `BOUNDARY` (immutability) + `HUMAN_GATE` (claim judgment) | Hash check at freeze and at every deterministic command; mutation fixture must fail. |
| `INV-04` | Strategy and draft are hypotheses. Strategic authority migrates downstream and ends at the human. | `PROTOCOL` + schema constants | `artifact_role`/`authority`/`elasticity` constants required in `strategy.json`; Stage-3 elasticity clause in prompt; observable via `material_strategy_change`. |
| `INV-05` | The final writer is `ELASTIC` within immutable truth ceilings. No contract, schema or upstream artifact may restrict what it may reconstruct. | `PROTOCOL` | Spec conformance review: no rule anywhere may require the final package to agree with the strategy. |
| `INV-06` | Models own semantic judgment; deterministic code owns mechanically provable contracts. Code never asserts factual truth, naturalness, relevance or persuasion. | `BOUNDARY` | Validator inventory review (§15.5): every check must be classifiable as mechanical. |
| `INV-07` | Source escape is unconditional. No index, view, summary, strategy, personality artifact or preparation pass may become a permission boundary or the only path to evidence. | `PROTOCOL` + `BOUNDARY` (read access) | Prompts grant it explicitly; index is lossless (§20.3); read access to authorities is never removed. |
| `INV-08` | Deterministic code never invokes a model. There are no automatic retries and no hidden repair loops. | `BOUNDARY` | No network/model client in the runtime; dependency and import test. |
| `INV-09` | No automatic submission, employer contact, profile mutation or other external irreversible action exists in the system. | `BOUNDARY` | No network egress in tooling; no submission capability implemented; test asserts absence. |
| `INV-10` | Completion is derived from validated canonical artifacts. No filename, marker file, heading or human-readable string constitutes completion. | `BOUNDARY` | Status derivation reads artifacts + validation results only; `_DONE`-style fixture must not affect status. |
| `INV-11` | One authoritative representation per fact and per state. Every other view is generated and regenerable. | `BOUNDARY` | Deleting all derived views and regenerating must reproduce them byte-identically. |
| `INV-12` | Optional features are off-safe. The baseline is fully correct with personality off, no context preparation and no experiment hooks active. | `BOUNDARY` | Full pilot test run with all optional flags off and optional files absent. |
| `INV-13` | Control plane and data plane are separate. Data-plane content may inform reasoning; it may never change instructions, permissions, authority, run identity, validation policy or the submission boundary. | `BOUNDARY` + `PROTOCOL` | Injection fixtures in vacancy text; write-root enforcement. |
| `INV-14` | Employer-facing output contains no internal artifacts: no evidence IDs, job/run IDs, source paths, private notes, control tokens or placeholders. | `BOUNDARY` | Leakage scan on rendered DOCX/PDF text; adversarial fixture. |
| `INV-15` | `READY / CHECK / RERUN` is a prediction of remaining repair scope, never a quality grade, and is never immutable — human review may change it. | `PROTOCOL` + `HUMAN_GATE` | Review schema carries reasons and actions, no score; calibration is `EXP-06`. |
| `INV-16` | No rendered output is complete until independently verified. Process exit status alone never proves success. | `BOUNDARY` | Per-document verification test with a forced partial-conversion fixture. |
| `INV-17` | Deterministic commands are idempotent and atomic: temporary write then promote; a failed replacement never destroys a previously valid output. | `BOUNDARY` | Interrupted-write fixture; repeated-command hash test. |
| `INV-18` | Every requirement in this specification is typed `BOUNDARY`, `PROTOCOL`, `ADVISORY` or `HUMAN_GATE`, and tests target the correct type. | Review | A prompt containing an instruction is never accepted as evidence that the instruction held. |

Further invariants (`INV-19`…`INV-29`) are declared at the point where their subject is specified, and carry the same force as those above: `INV-19` claim ceilings (§5.2); `INV-20` manifest content (§6.3); `INV-21` structural invariants (§7.1); `INV-22` cross-job isolation (§8.4); `INV-23` bridge cardinality (§10.3); `INV-24` employment replacement (§12.3); `INV-25` no code-owned prose judgment (§13.3); `INV-26` run status versus delivered work (§16); `INV-27` no residual content controls (§18.1); `INV-28` index lossless coverage (§20.3); `INV-29` evidence-loop separation (§26).

### 4.1 Design rules applied throughout

1. **Delete before hardening.** A hardening mechanism is adopted only if the surface it protects survives §3.
2. **Minimal authoritative core, rich derived views.** Reporting is cheap; authoritative mutable state is expensive.
3. **Structural strictness buys semantic freedom.** Exact identity, addresses and expected sets exist so the final writer can be aggressive without risking leakage or untraceable claims.
4. **Asymmetric loss in context design.** False exclusion of evidence is far worse than false inclusion; every context mechanism is additive and advisory.
5. **Measure before automating.** Human spot-checks precede detectors; target-machine tests precede document-engine work.

## 5. Factual and strategic authority

### 5.1 Factual authority ladder — `INV-03`

```text
1. Work_experience.md, Education.md, Other_high_value_information.md   (candidate facts)
2. Original vacancy artifact                                            (employer facts)
3. CV_BASELINE.md                     — derived chronology/rendering; never raises a ceiling
4. evidence_index                     — addresses only; no relevance, no claims
5. strategy / draft / final / review  — model artifacts; never candidate facts
6. personality, writing standards, preparation output — interpretive/advisory only
```

`[USER]` The three authority files are **immutable for the duration of a run**. Their SHA-256 hashes are recorded at freeze and re-checked by every deterministic command. Source maintenance happens between runs, under human approval, followed by a new freeze.

`[NORMATIVE]` The vacancy is authority for employer, role, requirements, deadline, reference and stated channel facts — and simultaneously **untrusted data** (§23). Normalized vacancy text is a derived convenience view and never replaces the original.

### 5.2 Claim ceilings

`[USER]` The system may select the strongest accurate identity, use functional equivalence, translate sector experience, foreground scope and consequence, and formulate future contribution. It may not invent or silently upgrade: formal title, dates, degree, institution, measured result, metric, personnel responsibility, mandate, lifecycle stage (pilot vs production), ownership, or authorship of team/AI-assisted work.

`INV-19` A claim ceiling can only be lowered by downstream stages, never raised. Where a source marks a caveat, lifecycle or attribution boundary, that marking travels with the evidence reference and must be respected by every stage.

### 5.3 Strategic authority

```text
Stage 1 strategy   = STRATEGY_HYPOTHESIS      (non-factual, non-final, elastic)
Stage 2 draft      = REALIZED_DRAFT           (may make bounded writing corrections)
Stage 3 final      = CURRENT_SEMANTIC_PACKAGE (may reconstruct strategy entirely)
Human              = FINAL AUTHORITY          (factual, semantic, submission)
```

`INV-05` No mechanism may require the final package to conform to the strategy. Validators compare the final package against **facts, schema and identity**, never against upstream semantic intent.

### 5.4 Epistemic typing of artifacts

Every artifact carries a visible epistemic type. This is the cheapest defense against authority leakage.

| Type | Artifacts |
|---|---|
| `FACTUAL_AUTHORITY` | three authority files, original vacancy |
| `DERIVED_LOSSLESS_VIEW` | `CV_BASELINE.md`, `evidence_index`, normalized vacancy text, `job_context` |
| `CONTROL` | `run_manifest`, settings, stage instructions, schemas, template map |
| `STRATEGY_HYPOTHESIS` | `strategy.json` |
| `REALIZED_DRAFT` | `draft_package.json` |
| `CURRENT_SEMANTIC_PACKAGE` | `final_package.json` |
| `OPERATOR_TRIAGE` | `review.json`, derived status and queue |
| `INTERPRETIVE_CONTEXT` | personality artifacts (when enabled) |
| `ADVISORY_PROJECTION` | any Step-3 preparation output (absent from baseline) |

## 6. Vacancy intake, batch organization and freeze

### 6.1 Human batch authority — `CTR-02`

The human compiles one operator-editable table, one row per approved vacancy. Format is an implementation choice (CSV is the obvious one); the **fields** are frozen:

```text
job_id            stable, human-assignable, unique, filesystem-safe
employer          exact legal/known employer name as used by the employer
title             exact advertised title
unit              optional
reference         optional employer reference number
deadline          ISO date or empty
vacancy_path      path to the original vacancy artifact
cluster_id        human-assigned
sequence          human-assigned order within cluster
priority          human sort key only (see DEC-13)
core_or_exception CORE | EXCEPTION
exception_reason  required iff EXCEPTION
notes             free text for the human; never read by any stage
```

Deleted relative to earlier candidates: `language` (constant, `DEC-04`), `letter_required` (constant true, `DEC-01`), `platform`, `channel`, `portal_required` and any channel matrix (`DEC-02`). Channel facts the human needs at submission time live in `notes`, which no validator, stage or metric consumes.

### 6.2 Clustering, order and priority — `DEC-12`, `DEC-13`

`[DRAFT-DECISION]` (resolves `RQ-05`)

- **Human-assigned clusters and sequence.** There is no model-generated cluster plan, no `cluster_plan.json`, no plan schema and no plan/execution reconciliation. The human already selects the opportunity set; asking a model to re-plan it adds a stage, a state object and an anchoring risk for no identified consumer.
- **Priority A/B prediction and differentiated model treatment are deleted.** A predicted priority label is confounded with quality, has no reliable consumer, and would silently change treatment across jobs that must be comparable in the pilot. `priority` survives **only** as a sort key for the human review queue and for production order.
- Starting control: roughly **five clusters × eight jobs**, normal range 6–10 (`[NORMATIVE]`). Size is empirical (`EXP-01`), not architectural: cluster membership changes nothing about a job's contracts, artifacts or validity.

Clustering guidance (`ADVISORY`): group where shared decision context genuinely helps; separate near-duplicate vacancies; avoid placing one identity archetype first in a cluster; every job remains an independent transaction.

### 6.3 Freeze — `CTR-03` `run_manifest.json`

`freeze` is the only command that creates a run. It is a `BOUNDARY`: after it succeeds, the run's expectations cannot change without an explicit amendment (§7.6).

The manifest records, for the run:

```text
run_id, created_at, spec_version, schema_versions, settings_snapshot
authority_files[]    : path, size, sha256
cv_baseline          : path, version, sha256
evidence_index       : path, sha256, generator_version
templates[]          : path, sha256; template_map path + sha256
stage_instructions[] : path, sha256
jobs[] :
    job_id, employer, title, unit, reference, deadline
    cluster_id, sequence, priority
    class: CORE | EXCEPTION, exception_reason
    vacancy: original_path, sha256, normalized_path, normalized_sha256
    document_date            (see DEC-22)
expected_core_jobs[] : job_ids, derived from jobs[] where class=CORE
```

`INV-20` The manifest stores facts, identities and hashes. It stores no semantic conclusion, no status, no progress and no copy of authority content.

Freeze fails loudly, with no partial run created, if: a `job_id` is duplicated or unsafe; a vacancy path is missing, unreadable, oversized, of an unsupported type, or resolves outside the allowed roots; an authority file or template is missing; `core_or_exception` is `EXCEPTION` without a reason; or the expected core set is empty.

### 6.4 Vacancy preservation and extraction sanity

The original vacancy artifact is copied byte-identically into the run and hashed. A normalized plain-text view is generated for convenience and marked `DERIVED_LOSSLESS_VIEW`.

Deterministic extraction sanity checks run at freeze (`BOUNDARY`): non-empty text; a minimum plausible character count; no unreplaced encoding artifacts beyond a threshold; presence of the employer or title string somewhere in the text. Failure is a **freeze warning per job**, not a hard failure, and it sets `requires_source_inspection` on that job, which the stage prompts surface: the model must read the original artifact rather than trust the normalization.

### 6.5 Pre-freeze inventory gate — `DEC-05`, `GATE-07`

`[DRAFT-DECISION]` The core boundary in §3 is chosen on the expectation that non-conforming vacancies are a small minority. The package does not contain the first-batch inventory, and this draft does not invent one.

`GATE-07` **Inventory gate (human, before the first production freeze):** produce one row per real vacancy and count the `EXCEPTION` rows.

- Default posture: proceed with the invariant core.
- Re-adjudication trigger: if `EXCEPTION` exceeds **20% of approved jobs**, or if more than **two** exception jobs share the same reason, the product boundary is re-opened by the human before the batch — the correct response is a deliberate decision, never a silent generalization of the core.
- If the trigger fires and the shared reason is `NO_DOCUMENT_UPLOAD` or `STRUCTURED_CV_ONLY`, the pre-approved remedy is to promote the downstream portal assist (§19) into a supported, still non-core workflow — not to add portal state to core schemas.

## 7. Canonical state and artifact lifecycle

### 7.1 Runtime shape — `DEC-06`

`[DRAFT-DECISION]` (resolves `RQ-03`, exercising `[USER-PERMISSION] D-019`)

**Job-centric runtime with one frozen run manifest and fully derived status.** The stage-centric P0.8/P0.8.1 tree, `progress.json`, `context_snapshot.json`, stage directories and physical stage progression are rejected: they encode the same freeze and completion facts in several places, and progression by directory movement was the mechanism behind P0.7's completion theatre.

Indicative layout (names are not architecture; the invariants are):

```text
authorities/            three authority files + CV_BASELINE.md          [immutable in run]
policy/                 settings, writing standard, stage instructions  [control plane]
templates/              CV master, application master, template_map
schemas/                one schema per canonical artifact
generated/              evidence_index                                  [regenerable]
runs/<run_id>/
    batch_inventory.*                                                   [operator input]
    run_manifest.json                                                   [frozen authority]
    status.json  queue.md                                               [derived, regenerable]
    jobs/<job_id>/
        source/           original + normalized vacancy
        job_context.json  [derived]
        strategy.json     [current]
        draft_package.json[current]
        final_package.json[current]
        review.json       [current]
        rendered/         CV.docx CV.pdf LETTER.docx LETTER.pdf render_report.json
        history/          superseded and failed artifacts, timestamped
```

`INV-21` Structural invariants, independent of naming:

1. exactly one frozen run authority per run;
2. exactly one *current* artifact per (job, stage);
3. the job directory is the transaction and history boundary;
4. all status, queues and reports are derived and regenerable;
5. no per-job copy of candidate authority content;
6. the expected set comes from the manifest, never from directory listing (`DEC-08`);
7. write boundaries are explicit: model stages may write only inside `runs/<run_id>/jobs/<job_id>/`.

### 7.2 Derived job state — `DEC-07`

`[DRAFT-DECISION]` No status file is authoritative. `status.json` and `queue.md` are computed on demand from: manifest expectations, presence of current artifacts, their validation results, hash comparison against the manifest, and the `status` field inside `review.json`.

Derived states per core job:

| State | Derivation |
|---|---|
| `PLANNED` | expected, no current `strategy.json` |
| `STRATEGY_OK` / `STRATEGY_FAILED` | current strategy validates / a failure record is the newest strategy event |
| `DRAFT_OK` / `DRAFT_FAILED` | as above for `draft_package.json` |
| `FINAL_OK` / `FINAL_FAILED` | as above for `final_package.json` + `review.json` |
| `RENDERED` | all four expected documents exist and passed document verification |
| `DELIVERED_READY` / `DELIVERED_CHECK` / `DELIVERED_RERUN` | `RENDERED` and `review.status` is `READY` / `CHECK` / `RERUN` |
| `STALE_<class>` | an input hash no longer matches the manifest (§7.5) |
| `EXCEPTION` | `class = EXCEPTION` in the manifest |

`INV-10` A `FAILED` state is produced only by a failed validation or a failed render verification, never by a missing marker or an unparsed heading.

### 7.3 Current versus history

Writing a new current artifact moves the previous one into `history/` with a timestamp and the reason (`RERUN`, `REPAIR_EXHAUSTED`, `MANUAL_REPLACE`). History is append-only and never read by validators or status derivation — it exists for audit and for the human.

### 7.4 Idempotency and atomicity — `INV-17`

- Deterministic commands are safe to re-run; unchanged inputs reproduce byte-identical deterministic outputs (`GATE-10` covers filesystem behavior).
- Rendering and any multi-file write use a temporary path plus atomic promotion.
- A failed replacement leaves the previously valid outputs in place and reports the failure.
- A frozen manifest is never mutated in place.

### 7.5 Invalidation — `DEC-26`

`[DRAFT-DECISION]` Static invalidation classes, reported by the `status` command. No dependency engine, no automatic re-execution.

| Class | Trigger | Minimum stale scope |
|---|---|---|
| `SOURCE_TRUTH` | authority file or `CV_BASELINE` hash changed | strategy, draft, final, review, rendered — all affected jobs |
| `VACANCY` | vacancy hash changed for a job | that job, all stages |
| `STRATEGY_POLICY` | Stage-1 instruction or strategy schema changed | strategy and everything downstream |
| `WRITER_POLICY` | Stage-2 instruction, writing standard, or draft schema changed | draft, final, review, rendered |
| `FINAL_POLICY` | Stage-3 instruction, final/review schema changed | final, review, rendered |
| `RENDER_ASSET` | template, template map, or render settings changed | rendered artifacts only |
| `INDEX` | evidence index hash changed | reference resolvability revalidation only |
| `SETTINGS_OPTIONAL` | personality toggle or other optional-feature setting changed | only artifacts produced while it was active; factual sources unaffected |

Stale is reported, visible, and blocks nothing automatically. The human decides whether a stale job is re-run or accepted.

### 7.6 Amendment

A frozen run is amended, never edited: `freeze --amend` writes a new manifest version with an explicit changelog (jobs added, jobs marked exception, hashes updated) and preserves the prior manifest in history. Existing valid job artifacts survive an amendment unless their own inputs changed.

## 8. Stage topology and model-role requirements

### 8.1 Ratified topology — `DEC-19`

`[NORMATIVE]` ratified without change:

```text
Stage 1  Sol-class    Decision Architecture         -> strategy.json
Stage 2  Terra-class  Native Package Writer         -> draft_package.json
Stage 3  Sol-class    Elastic Final Writer + Review -> final_package.json + review.json
```

No fourth standard semantic stage. No judge stage, no verifier stage, no separate portal stage, no cluster-planning stage. The package contains no evidence that a fourth stage improves package quality, and each additional standard stage costs a chat per cluster, a contract, a validator, a state and an anchoring surface.

`RERUN` (§17.3) is a targeted repeat of Stage-3-class work for one job, not a standard stage.

### 8.2 Model roles, not model names — `DEC-31`

Model names, effort labels, prices and context limits are volatile environment configuration, not architecture. The architecture fixes **role requirements**; `SETTINGS` maps roles to concrete models at build and batch time, re-verified by `GATE-08`.

| Role | Requirement | Current control |
|---|---|---|
| `SOL_CLASS` | strongest available non-linear reasoning + strong native Norwegian; used where a wrong decision is expensive (Stage 1, Stage 3, RERUN) | Sol Max / equivalent, high effort |
| `TERRA_CLASS` | strongest cost-effective long-form native Norwegian writing | Terra Max / equivalent |
| `AUX_CLASS` | cheap auxiliary, optional, never in the baseline path | Luna / equivalent |

If only one capable model is available at batch time, Stage 2 may use `SOL_CLASS`. The reverse — Stage 1 or Stage 3 on a weaker model — is a deliberate quality reduction and must be recorded in the run notes.

### 8.3 Execution model

`[USER]` Semantic stages are manually initiated chats. There is no orchestrator.

- One chat per (cluster, stage). Jobs are processed sequentially inside the chat, one job fully persisted and validated before the next begins (`D-023`).
- No routine between-job human confirmation.
- A continuation chat (interrupted session, context exhaustion) begins by reconciling against the manifest and the current artifacts on disk — never by trusting a remembered pointer.
- Nominal prompt budget for ~40 jobs: 15 cluster-stage chats + selective RERUNs + exception handling, inside the 20–25 envelope (`D-026`).

### 8.4 Per-job stage loop

```text
load job inputs (manifest identity + vacancy + authorities/index + stage inputs)
  -> produce the stage artifact
  -> run the deterministic validator for that artifact
  -> if invalid: bounded repair (DEC-18), revalidate
  -> persist as current on success, or write a failure record and continue
  -> next job
```

`INV-22` No stage may carry job-specific content from one job into another. Shared context inside a cluster chat is limited to the stage instruction, policy and candidate sources — all job-invariant. Cross-job leakage is a hard defect (`ACC`).

## 9. Stage 1 — Decision Architecture

### 9.1 Question

> Which truthful candidate identity, evidence architecture, employer-decision argument and writing direction gives *this* vacancy the strongest expected interview case?

Stage 1 is a decision stage. It does not draft the employer-facing package, does not score the job, does not rank jobs against each other and cannot veto an approved job.

### 9.2 Inputs

Manifest identity for the job; original + normalized vacancy; the three authority files; `evidence_index`; writing/persuasion standards (for direction only); the personality profile **only if enabled** (§21); `job_context` if the implementation generates one.

Explicitly not inputs: other jobs' artifacts, prior batches, model memory, historical packages.

### 9.3 Read-order protocol (`PROTOCOL`)

1. Vacancy and identity first; form a provisional employer decision problem and requirement structure **before** looking at candidate evidence.
2. Then candidate evidence, via the index and directly in the sources.
3. Then, if enabled, personality — after the factual picture exists.
4. Then produce the strategy.

This is a debiasing protocol, not a boundary. It reduces the tendency to fit the vacancy to a favourite candidate story. It is not testable as a guarantee and must never be described as one.

### 9.4 Obligations

Stage 1 must: identify the employer's actual decision problem and likely selection logic; choose one primary truthful candidate identity and name the identity it deliberately avoids; state an explicit CV headline hypothesis; map each material stated requirement to candidate evidence, adjacency, gap or unknown; select the two strongest complementary evidence bridges plus bounded support; anticipate the likeliest objections with truthful reframes; specify a concrete motivation bridge; allocate content between CV and letter; give the writer explicit direction *and* explicit "avoid" guidance; and record a counterfactual reserve whenever a materially different truthful route is plausible.

Stage 1 must not: invent facts; exceed a source claim ceiling; produce a fit probability or score; draft the full letter; or forbid later source escape.

## 10. Strategy contract — `CTR-05`

### 10.1 Serialization — `DEC-09`

`[DRAFT-DECISION]` (resolves `RQ-04`, supersedes the P0.8 `strategy.md` control)

**Canonical strategy is `strategy.json`. A human-readable `strategy.view.md` is generated deterministically from it, marked `GENERATED — DO NOT EDIT`, and is read by no model stage.**

Reasoning, in the order of §2.2:

- *Quality:* the load-bearing risk in the strategy interface is not prose quality, it is silent drift in evidence references, missing decision surfaces, and a headline hypothesis that never reaches the writer. Those are exactly the parts that structure protects.
- *Human effort:* the human never reads the canonical form; the generated view is better than raw Markdown because it can be ordered for review.
- *Implementation speed:* draft, final and review are already JSON with JSON Schema. Markdown would add a second, bespoke, brittle parsing discipline for one artifact. One parser family is materially cheaper to build and test.
- *Reversibility:* the semantic contract (§10.3) is frozen independently of serialization, so a reversal to Markdown changes one schema and one prompt, not the architecture (`EXP-04`).

`[RESEARCH]` A manual chat response is **not** schema-guaranteed merely because the prompt asked for JSON. Therefore the JSON choice is inseparable from `DEC-18`: local validation before completion, with bounded repair.

Rejected: Markdown-plus-JSON dual authoring (two independently authored canonical representations); YAML front matter duplicating decisions already in the body.

### 10.2 Mandatory epistemic constants — `DEC-10`

Every `strategy.json` carries, as schema constants:

```json
{"artifact_role": "STRATEGY_HYPOTHESIS",
 "authority": "NON_FACTUAL_NON_FINAL",
 "elasticity": "ELASTIC",
 "final_writer_may_reconstruct": true}
```

`INV-04` Schema validity of a strategy proves structure only. It never makes the strategy factually or strategically authoritative, and no downstream prompt may instruct a stage to "comply with" the strategy as a contract.

### 10.3 Frozen semantic contract

Field names are implementation detail; the **surfaces** below are the contract. Optional surfaces are *omitted* when not applicable — never filled with placeholder prose.

| Surface | Cardinality | Notes |
|---|---|---|
| job identity (`run_id`, `job_id`, `employer`, `title`) | required | must equal the manifest exactly |
| epistemic constants | required | §10.2 |
| employer decision problem + likely selection logic | required | prose |
| decision tests the employer will apply | 1–5 | short items |
| primary candidate identity + `avoid_identity` | required | prose |
| headline hypothesis | required | short string; feeds `CTR-06` |
| requirement map | 1–12 entries | `{requirement, class: MINIMUM\|DESIRED\|TASK\|CONTEXT, relation: SUPPORTED\|ADJACENT\|GAP\|NOT_MATERIAL\|UNKNOWN, evidence_refs[], note?}` |
| evidence plan | 1–10 entries | `{evidence_ref, role: BRIDGE_PRIMARY\|BRIDGE_SECONDARY\|SUPPORT, claim_ceiling?, why}` |
| objections and truthful reframes | 0–3 | |
| motivation bridge | required | prose, vacancy-specific |
| CV direction | required | emphasis, employment IDs to foreground, avoid list |
| application direction | required | backbone, 2–3 proof arcs, one interview hook, avoid list |
| counterfactual reserve | 0–1 | `{alternative_identity, when_to_switch}` |
| gaps and risks | 0–5 | |
| personality facets | 0–3 | only when personality is enabled (§21) |
| writer notes | optional | bounded free text |

`INV-23` At most 2 entries may carry `BRIDGE_PRIMARY` and at most 3 `BRIDGE_SECONDARY`. Unequal evidence must not be handed to the writer as equally weighted.

### 10.4 Density budget — `DEC-11`

`[DRAFT-DECISION]` Total prose across all prose fields: **soft target 450–900 words; validator warning above 1200; hard failure above 1600.** No minimum on any field. Per-field hard caps exist for the short fields (headline ≤ 140 characters).

Rationale: the earlier 900–1400 word control was set when the strategy was a prose document that had to carry its own structure. A structured artifact carries structure in the schema, so the same decision density needs fewer words, and a shorter strategy anchors the downstream writer less (`[RESEARCH]` anchoring). Word counting is deterministic, so this is a real `BOUNDARY`, not an aspiration.

### 10.5 Mechanical validation of the strategy

Schema validity; identity equality with the manifest; epistemic constants present and correct; every `evidence_ref` resolves in the frozen index; cardinality and word budget; `employment_id` references (in CV direction) exist in the baseline; no field contains a URL or a path outside the run; no numeric score field present.

Not validated, because code cannot: whether the identity is the best one, whether the evidence is the strongest, whether the reframes are honest, whether the motivation is credible.

## 11. Stage 2 — Native Package Writer

### 11.1 Role

Stage 2 realizes the strategy as a complete native Bokmål package: CV dynamic zones plus the full application letter. It owns prose, voice, rhythm, CV/letter complementarity and first editorial self-correction. It is neither a template filler nor a judge.

### 11.2 Inputs

Manifest identity; original + normalized vacancy; `strategy.json`; writing and persuasion standards; `evidence_index` and the authority files (full read access — `INV-07`); the CV baseline contract (employment IDs and chronology); distilled personality guidance **only** as carried inside the strategy when enabled. No raw personality profile. No preparation artifact in the baseline.

### 11.3 Bounded writer correction

Stage 2 follows the strategy strongly but not mechanically. Where an instruction is contradictory, unwriteable, or would require an unsupported claim, Stage 2 makes the smallest correction that produces a truthful, coherent package and records a short `writer_delta` (free text, ≤ 80 words). The delta is a note, not a competing strategy object, and nothing downstream is required to honor it.

If following the strategy would require exceeding a claim ceiling, Stage 2 **must** deviate and must say so in the delta. Truth outranks the strategy without exception.

### 11.4 Output — `CTR-06` `draft_package.json`

```text
schema_version, contract_version, source_stage = "STAGE2_DRAFT"
run_id, job_id, employer, title       (identity echo, must equal manifest)
baseline_version
used_evidence_refs[]                  (index IDs actually used)
cv: { headline,
      profile,
      key_competencies[4..8],
      employment_overrides[0..4]: { employment_id, bullets[1..5] } }
application: { opening, body[1..5], closing }
writer_delta: string | null
```

The draft carries **only** dynamic content and provenance. It never restates employer names, titles, dates, education or other baseline-owned scaffolding — that is the baseline's job, and duplicating it would create a second chronology authority.

### 11.5 Completion

Stage 2 completes for a job only when `draft_package.json` validates. Otherwise the bounded repair protocol applies, then an explicit failure record, then the next job.

## 12. CV contract — `CTR-07`

### 12.1 Ownership split — `DEC-23`

`[NORMATIVE]` + `[USER-PERMISSION] D-014`, adopted as the frozen v1 surface:

| Baseline-owned (model may not change) | Model-authored dynamic zones |
|---|---|
| employer names, formal titles, employment periods, education chronology and degrees, languages, static sections, employment IDs, section order | headline, profile, key competencies (selection, order, wording), employment bullet sets for up to four employments |

This yields substantial vacancy-specific positioning while making it structurally impossible for a model to rewrite the candidate's chronology.

### 12.2 Headline

`[NORMATIVE]` The explicit headline is a first-class field from strategy through render. It expresses the chosen identity, must be supportable by the authority files, must not imply seniority, formal role or mandate beyond evidence, and should align with — not copy — the advertised title. It must be consistent with the profile and the letter backbone (a `PROTOCOL` check by Stage 3, not a code check).

### 12.3 Employment override semantics

`INV-24` When an `employment_id` appears in `employment_overrides`, its `bullets` array is a **full replacement** of that employment's rendered bullets. Explicitly forbidden: appending to hidden baseline bullets; positional merge; mixed old/new sets; an empty array meaning "use defaults" (an empty array is a schema error — omit the override instead).

The model may not add or remove employment identities, alter periods or titles, or reorder the chronology.

### 12.4 CV doctrine (`PROTOCOL`)

Foreground the evidence most diagnostic for this employer's decision; compact action/contribution/consequence phrasing; make functional leadership visible without implying formal personnel authority; separate personal from team contribution accurately; preserve lifecycle distinctions (pilot, development, production, proxy); no keyword dumping or generic competence lists; keep readable density.

### 12.5 Page behavior — `DEC-24`

`[NORMATIVE]` Sparse CV may be one page; normal and dense CV are typically two. More than two pages produces a `CHECK` review issue, not automatic content deletion. Hard failure only when an explicit external limit is breached or the document is unusable (clipped, empty, unopenable). No hidden typography auto-fit. Sparse, normal and dense fixtures are mandatory render evidence (`GATE-05`).

## 13. Application contract — `CTR-08`

### 13.1 Shape

`opening` + 1–5 `body` paragraphs + `closing`, generated directly in Bokmål. The letter is a decision argument, not a prose CV and not a requirement checklist.

Normal argument order (`ADVISORY`, not a template): the employer's actual problem and the relevant candidate route; one primary identity backbone; two or three evidence-rich proof arcs; the bridge from past evidence to future usefulness here; motivation expressed through problem/work fit; at least one concrete, evidence-grounded interview hook; honest treatment of one material gap or objection where useful; a calm, concrete closing.

Content allocation heuristic (`ADVISORY`, not a quota): roughly 70–85% of meaningful content serves the top one or two employer pain points and the two strongest bridges; 15–30% serves motivation, framing and closing. Unequal evidence does not get equal space.

### 13.2 Public-sector coverage discipline

`[RESEARCH]` Norwegian state hiring assesses candidates against advertised qualification requirements. The architectural consequence is **internal coverage discipline**, discharged by the strategy's requirement map (§10.3), not by checklist prose. A decisive stated requirement must not be silently dropped because another theme reads better; the letter may nevertheless cover requirements through a single strong backbone. The requirement map is private and never rendered.

### 13.3 Language doctrine (`PROTOCOL`)

Ordinary Norwegian word order and precise action verbs; work, responsibility, scope, judgment and consequence in place of self-ranking adjectives; `jeg` for supported personal contribution, `vi` for collective delivery; no American corporate hype, no translation artifacts, no cliché enthusiasm; preserve a plausible individual voice.

Stock phrases to remove unless the surrounding evidence makes them unusually precise: *brenner for, lidenskapelig opptatt av, unik mulighet, spennende reise, fremoverlent, resultatorientert, dynamisk, synergieffekter, game changer, revolusjonerende, sømløst, banebrytende, utnytte kraften i, jeg er overbevist om at,* generic *i skjæringspunktet mellom*.

`INV-25` This list is a writing instruction to the semantic stages, never a code gate. No deterministic validator may fail a package on a stylistic, idiomatic or persuasive judgment about wording — a code-owned prose blacklist is an `INV-06` violation and produces false positives on legitimately precise usage.

The boundary is *closed token set with no legitimate use*, not *string matching*. Two lexical scans are therefore permitted and are not exceptions to this rule: the private-marker and placeholder leakage scan (§15.2), where any hit is a defect by construction, and the typology-vocabulary scan on employer-facing fields (§21.3), where the token set is closed and no legitimate employer-facing use exists. Any proposed third lexical check must meet the same test.

### 13.4 Length

Soft editorial target: roughly one page. Length is never enforced by deleting decision-relevant content. Hard limits exist only when an employer imposes one, which — with portal detached — reaches the system as a human instruction at submission time, not as core state.

## 14. Stage 3 — Elastic Final Writer and Selective Review

### 14.1 Role

Stage 3 is the last semantic quality stage and the triage point. It has two obligations: produce the strongest truth-safe final package, and predict the remaining human repair scope. It is not an independent judge, and its review output is not a quality grade.

### 14.2 Read order (`PROTOCOL`)

1. Vacancy and identity first; form a fresh provisional view.
2. Candidate evidence via index and sources.
3. Only then the strategy and the draft.
4. Source-escape freely at any point.
5. Personality only if enabled and relevant.
6. Write the final package; synchronize evidence refs; write the review; validate; repair if needed; persist.

Reading the draft after forming an independent view is a debiasing protocol. It is not proof of independence and must not be described as such.

### 14.3 Elastic authority — `INV-05`

`[USER]` Stage 3 **may**: change the headline and the primary identity; replace the evidence selection; adopt the counterfactual reserve or a route neither upstream stage considered; change employment emphasis and rewrite every bullet; rewrite the profile, the competency set and the entire letter; change argument sequence and CV/letter allocation; suppress all personality-conditioned framing; and recover evidence the earlier stages omitted.

Stage 3 **may not**: invent support; exceed a claim ceiling; mutate an authority file; ignore an employer hard constraint; change baseline-owned chronology; or treat validator success as evidence of semantic truth.

Correction is normal work, not deviation. Nothing in the prompts, schemas or reviews may frame a departure from the strategy as an error to be justified.

### 14.4 Upstream claim repair

If Stage 3 finds an unsupported or inflated claim upstream, it **repairs it in the final package before saving** and sets `upstream_claim_repaired` with a bounded note. Shipping a known unsupported claim with a `CHECK` label is forbidden: `CHECK` is for confirmation and local edits, never for known truth defects.

### 14.5 Final artifacts

`CTR-09` `final_package.json` uses the same semantic shape as the draft (`source_stage = "STAGE3_FINAL"`), so rendering has exactly one source contract. It becomes the current model-authored package authority for the job, subordinate to sources and to human approval.

`CTR-10` `review.json`:

```text
run_id, job_id, source_stage = "STAGE3_FINAL"
status: READY | CHECK | RERUN
reasons[0..3]: { text, recommended_action }
limitations[]?          things the human must know before submitting
material_strategy_change: bool, summary?
upstream_claim_repaired: bool, note?
```

No numeric confidence, no self-awarded score, no more than three reasons — a triage note that needs four reasons is a `RERUN`.

### 14.6 Evidence synchronization — `DEC-25`

`[NORMATIVE-adjacent, P0.8.1 adopted]` `used_evidence_refs` in the final package must describe the evidence actually used **after** reconstruction. Stale Stage-1 references must not survive as audit truth.

The validator proves only that each reference resolves in the frozen index and that the set is non-empty. Whether the evidence supports the wording is a semantic judgment owned by Stage 3 and the human. This limit is stated in the release evidence; no document may claim the reference validator proves factual support.

### 14.7 Diagnostics

Optional, purely observational, never gates: `material_strategy_change` (interpret with final quality — near-zero is ambiguous between excellent strategy and authority inflation), and, only when a preparation experiment is active, references recovered outside the prepared material.

## 15. Validation

### 15.1 Three classes

| Class | Owner | Consequence of failure |
|---|---|---|
| Mechanical (`BOUNDARY`) | deterministic code | artifact invalid; bounded repair; then job-stage failure |
| Semantic policy | models + human | must be repaired before save (Stage 3) or escalated to the human |
| Soft quality | models + human | `CHECK` / `RERUN` / editorial repair |

`INV-06` No mechanical check may be presented as evidence of factual truth, attribution correctness, relevance, naturalness or persuasive strength.

### 15.2 Mechanical checks (complete list of what code enforces)

Structure and identity: schema validity; identity equality with the manifest (`run_id`, `job_id`, `employer`, `title`); expected-set membership; unique IDs; required fields present; unknown fields rejected.

References: every `evidence_ref` resolves in the frozen index; index hash matches the manifest; `employment_id`s exist in the baseline; `used_evidence_refs` non-empty on draft and final.

Bounds: cardinalities (competencies 4–8, bullets 1–5, overrides 0–4, body 1–5, reasons 0–3, facets 0–3); strategy word budget; headline character cap.

Integrity and safety: candidate authority, baseline, template and index hashes unchanged since freeze; all model-written paths inside the job directory; path traversal, symlink and unsupported/oversized inputs rejected; no private markers, internal IDs, source paths or placeholder tokens in employer-facing fields; no numeric score fields.

Merge and render: baseline merge completeness (every rendered employment resolved exactly once); template map keys all filled; no residual content control or placeholder in the output DOCX; expected outputs exist, are non-empty, open, contain expected identity strings, and yield extractable text.

### 15.3 Semantic policy (models and human)

No fabricated or inflated fact; wording supported by the cited evidence; correct personal versus team attribution; honest formal versus functional authority; correct lifecycle representation; gaps not disguised as direct experience; motivation not invented; claim ceilings respected.

### 15.4 Soft quality (models and human)

Employer relevance; single-backbone coherence; evidence selection; native naturalness; persuasion; distinctiveness across the batch; redundancy between CV and letter; page density and visual balance; motivation strength.

### 15.5 Validator conformance rule

`INV-18` Every check implemented in code must appear in §15.2 or be justified as an instance of it in the implementation contract. A check that requires interpreting meaning is out of scope by construction. Reviewers should treat any new code-side "quality" check as a defect.

## 16. `READY` / `CHECK` / `RERUN` / `FAILED`

`[NORMATIVE]` Operator statuses predict remaining repair scope. They are not grades, and human review may change them.

| Status | Meaning | Expected human action |
|---|---|---|
| `READY` | No known material factual, semantic or usability defect. | Skim, fact-check, approve, submit — within the 10–20 minute envelope. |
| `CHECK` | A small number of localized issues or confirmations that do not require rebuilding the backbone: a claim-strength nuance, preference-sensitive wording, one employer detail to confirm, a local layout issue, a small motivation ambiguity. | Bounded edit or confirmation, still inside the envelope. |
| `RERUN` | Strategic reconstruction is cheaper than human editing: wrong identity, weak or mismatched primary evidence, broken backbone, serious genericity or convergence, multi-section rewrite needed, or uncertainty too broad for a bounded check. | Initiate a targeted RERUN chat, or drop the job. |
| `FAILED` | **Deterministic runtime state**, not a judgment: required current artifacts could not be made validator-clean within the bounded repair protocol, or render verification failed. | Inspect the diagnostic, fix the mechanical cause, re-run that stage or the render. |

Derived delivery classes reported by the finalizer: `DELIVERED_READY`, `DELIVERED_CHECK`, `DELIVERED_RERUN`, `FAILED`, `EXCEPTION`.

`INV-26` A nonzero run-level exit status never deletes, hides or invalidates delivered jobs. The finalizer's exit code reports whether the run was complete; the delivered artifacts stand on their own.

Calibration of these statuses against actual human repair time is `EXP-06`, not an architectural assumption.

## 17. Repair, rerun and partial success

### 17.1 Bounded same-session repair — `DEC-18`

`[DRAFT-DECISION]` (resolves `RQ-09`, exercising `[USER-PERMISSION] D-024`)

```text
validator fails
  -> the model reads the deterministic diagnostic (file, field, invariant, expected vs actual)
  -> edits the current artifact in the same chat
  -> re-runs the validator
  -> at most TWO repair attempts per artifact per stage visit
  -> on exhaustion: write a failure record, do NOT mark complete, continue to the next job
```

Rules: repair addresses the reported mechanical defect only — a repair that would change the semantic content beyond the defect must be recorded in the failure record instead; each attempt is visible in the chat; validator code never triggers a model call (`INV-08`); the failed artifact and every diagnostic are preserved in `history/` for the human.

Two attempts, not one, because the common failure classes (a malformed field, a missing required surface, an unresolvable reference, an exceeded cardinality) are usually one-shot fixes, and the second attempt covers a fix that introduces a second, now-visible error. Three or more attempts start to look like semantic churn against a validator.

`GATE-01` This protocol presumes the execution surface can run a local validator and edit files in-session. That is unverified. **Safe posture before verification:** the same two-attempt loop is operator-mediated — the human runs the validator and pastes the diagnostic back into the chat. The architecture is identical either way; only the ergonomics change.

### 17.2 Failure containment — `INV-02`

A stage failure for one job affects only that job. The chat continues with the next job. The finalizer delivers every valid job and reports the failures. No mechanism aggregates job failures into a run failure that withholds good work.

### 17.3 `RERUN` — `DEC-20`

`[P0.8.1 adopted]` A `RERUN` is:

- manually initiated by the human, never automatic;
- one job, one separate `SOL_CLASS` chat;
- supplied with the vacancy, the authorities and index, the current strategy, draft, final and review, and the human's reason;
- permitted full reconstruction within truth — including discarding the strategy entirely;
- required to produce a replacement `final_package.json` and `review.json` that validate before becoming current;
- required to move the superseded versions into `history/`;
- never a standard fourth stage.

A `RERUN` may also revise the strategy in place when the human asks for it; the revised strategy is still `STRATEGY_HYPOTHESIS`.

### 17.4 Deterministic rerender — `DEC-22`

Rendering is deterministic and independently re-runnable: `finalize --job <id> --render-only` after a template, font or converter fix. A rerender must not change any semantic content and must not change the employer-facing **document date**, which is frozen per job in the manifest at freeze time. Changing the date is a semantic amendment, never a side effect of re-running a converter.

### 17.5 Partial batch success

The finalizer enumerates the expected core set from the manifest, processes every job independently, and reports per-job outcomes. Requirements: an already-valid job is never rebuilt or mutated by a run that fails elsewhere; a failed replacement never destroys a prior valid output; the review queue distinguishes "not produced" from "produced and failed" from "produced and stale".

### 17.6 Exception jobs

Listed in the manifest and in the queue, excluded from core processing and metrics, handled by the human (§3.4). No exception job ever enters `Q_happy`.

## 18. Rendering and document finalization

### 18.1 Evidence posture

`[VERIFIED]` The P0.7 masters are more favourable than generic "avoid content controls" advice implies: the CV master has 17 plain, non-data-bound content controls, no body tables, text boxes or drawings, a linear body flow, and name/"CV" in the header; the application master has 7 control instances over 6 tags, two tables, no drawings, and contact information in the header. The P0.7 finalizer filled the controls, unwrapped them, and failed if any `w:sdt` remained; controlled fixture DOCX/PDF rendering passed.

Consequence: **inspect and adapt, do not discard, and do not blindly reuse.** Target-Windows headless behavior, current fonts, and parser behavior remain unverified (`GATE-02`…`GATE-06`).

`INV-27` No data-bound content control, and no unresolved control of any kind, may exist in a delivered document. Unknown controls in a master fail preflight rather than being ignored.

### 18.2 Critical identity in body flow — `DEC-29`

`[DRAFT-DECISION]` Candidate name and contact details must appear at least once in **normal body text flow** in both documents. The header may repeat them for layout.

This is a cheap template change that deletes a whole class of risk (header content invisible to a parser) instead of testing for it and reacting. `GATE-06` then verifies extraction rather than gating the design on it.

### 18.3 Finalization sequence — `CTR-11`

```text
for each expected core job:
  1. validate current final_package.json and review.json
  2. merge baseline + dynamic CV zones (full-array employment replacement)
  3. fill the CV and application masters via the single canonical template map
  4. unwrap/remove all transient controls; assert no w:sdt and no placeholder remains
  5. validate DOCX structure
  6. write all outputs to a temporary per-job transaction path
  7. convert required PDFs under isolated converter state
  8. verify EACH document independently (exists, non-empty, opens, expected identity
     strings present, no placeholders, no private markers, text extractable)
  9. atomically promote the job transaction
 10. on any failure: leave prior valid outputs untouched, record the diagnostic, continue
```

`CTR-12` There is exactly one canonical package→template map. Code and documentation may not maintain competing mappings; the map is hashed in the manifest.

### 18.4 Converter policy — `DEC-21`

Architecture invariant: **the job is the render transaction; every document is independently verified** (`INV-16`).

Implementation posture, pending `GATE-04`: one isolated converter invocation **per document**, isolated user profile, absolute quoted paths, captured exit code and stderr, explicit expected-file checks. A single invocation for both documents is permitted only after a target-machine smoke test proves partial-failure semantics are observable. No persistent converter daemon.

### 18.5 Parseability posture

Conservative structure, verified empirically, never redesigned from folklore: logical reading order; normal text for critical content; no essential fact only inside a decorative object; selectable and extractable PDF text; standard fonts present on the render machine; identity and contact in body flow (`DEC-29`). Where a real target channel is known, an actual upload/preview test outranks any generic rule.

## 19. Portal and channel boundary

### 19.1 Core boundary

`DEC-02`. Restated as a testable rule: **no core schema, validator, state object, status, metric or release criterion mentions portals, channels, platforms, questions or field limits.** A reviewer can verify this by grepping the schemas.

Deleted with the surface: channel matrix, portal answer arrays, portal question identity and uniqueness, portal limit validation, portal-driven readiness, portal delivery classes, `letter_required`, `platform`, `portal_required`.

### 19.2 Downstream portal assist (optional, non-core) — `CTR-13`

When a real form requires free-text answers, the human runs a separate, manually initiated chat **after** the final package exists. Contract, kept deliberately thin:

```text
IN : exact question text, type, required flag, exact char/word limit (human-captured)
     the vacancy, the approved final package, the authorities/index, an optional human note
OUT: one answer per question
     direct answer first, then at most one or two of the strongest relevant proofs
     inside the stated limit
     wording consistent with the approved package and within claim ceilings
     no miniature application pasted into every field
```

The human copies the answers into the portal and submits. No state is written into the run. If the human wants the answers stored, they go in the job directory as an inert file that nothing validates.

Building tooling for this is **not** a release requirement. It is promoted to a supported workflow only if `GATE-07` shows portal-heavy jobs are common (§6.5) — and even then it stays out of core.

### 19.3 Attachments and credentials

Vitnemål, transcripts, attester and references are human-held files, requested per vacancy and often later in the process. They are never generated, transformed, renamed or submitted by the system. The queue may show a human-authored attachment note; that is all.

## 20. Context and evidence architecture

### 20.1 Baseline context system

Deliberately small: the three authority files; the original and normalized vacancy; stable policy files; the frozen identity; the deterministic evidence index; a derived per-job context view; and unconditional source escape. No vector store, no graph, no model-generated global summary, no relevance filter.

### 20.2 Deterministic evidence index in core — `DEC-14`

`[DRAFT-DECISION]` (resolves `RQ-06`)

**The evidence index is baseline core, not a Step-3 enhancement.** The justification is not retrieval quality — that remains unproven (`EXP-05`) — but enforcement:

- `DEC-25` requires final evidence references to be synchronized and validated. Without stable addresses, reference "validation" degrades to substring matching against prose, which is exactly the class of check that produced P0.7's completion theatre.
- The same coordinate system serves Stage-1 evidence planning, Stage-2/3 source escape, final provenance, audit, and any Step-3 experiment. One generated artifact serves five consumers.
- Cost is one generator plus one schema, and it is disposable: delete it and regenerate.

If a reviewer removes the index, they must also remove mechanical reference validation, and the provenance contract becomes advisory. That trade should be made consciously, not by omission.

### 20.3 Index and reference contract — `DEC-15`, `CTR-14`

Generated from the three authority files (plus `CV_BASELINE.md` for employment IDs). Per entry:

```text
evidence_id          stable, derived from source file + heading path (or the source's own
                     explicit ID where the source defines one, e.g. a project or claim ID)
source_file
heading_path
char_range or stable anchor
section_hash
approx_size
explicit_lifecycle_label?        only when the source states it
explicit_claim_ceiling_marker?   only when the source states it
```

`INV-28` **Lossless coverage.** Every byte of every indexed source belongs to exactly one leaf entry. Consequence: any evidence a model uses always has an address, so "no suitable reference exists" is never a valid excuse for an unreferenced claim.

The index must not: rank or score evidence for a vacancy; summarize; mark anything irrelevant; infer a lifecycle or ceiling the source does not state; become a manually maintained file; require a database; or restrict access to the sources.

It is generated at freeze, hashed into the manifest, and regenerated deterministically. If regeneration produces a different hash, affected jobs are `STALE_INDEX` and references are revalidated.

### 20.4 Requirement map

Held inside the strategy (§10.3), private, never rendered. It exists to prevent a decisive stated requirement from being dropped for rhetorical convenience, and to serve public-sector qualification logic. It is not a checklist for the letter.

### 20.5 Job context view — `CTR-04`

An optional derived `job_context.json` may assemble identity, source paths, the requirement structure, active settings and current stage inputs into one convenience object. It is `DERIVED_LOSSLESS_VIEW`, regenerable, subordinate to the manifest and the sources, and carries an explicit non-authority marker. Its absence must not break any stage.

### 20.6 Source escape — `INV-07`

Every stage may open any authority file at any time, for any reason. Nothing may be framed to a model as "the evidence you may use". Where a preparation experiment is active, models are told explicitly that the prepared material is advisory and incomplete.

`[RESEARCH]` False exclusion is the dominant context-preparation risk: a missed source atom can remove the best argument before the strongest model sees it, while a false inclusion merely costs attention. Every context mechanism in this architecture is therefore additive.

## 21. Personality

### 21.1 Locked boundary

`[USER]` If personality exists in the runtime it is optional and controlled through settings, and the pipeline must be fully correct with it off (`INV-12`).

Personality may guide evidence search and selection, identity framing, authentic motivation, misread prevention, tone and candidate specificity. It may **not** create achievements, responsibilities, skills, results or history; raise a claim ceiling; insert typology labels into employer-facing text; diagnose the candidate; override vacancy or candidate evidence; force a trait into every package; or become a ranking criterion.

### 21.2 Production default — `DEC-16`

`[DRAFT-DECISION]` **Default OFF for the first batch.**

This is a proposal, not a user decision, and it is explicitly interim. Reasons: the first batch must establish a clean product baseline (`Q_happy` has never been measured with real models); personality is the single largest untested semantic variable; and an OFF default costs nothing that a later toggle cannot recover. `EXP-02` decides the standing default.

### 21.3 Minimal runtime interface

When enabled:

1. Stage 1 reads the profile **after** forming the factual and vacancy picture.
2. Stage 1 may select **0–3 facets**. Zero is a valid, unremarkable outcome.
3. Each selected facet records: facet reference, the desired recruiter interpretation, the misread risk, the prevention rule, supporting `evidence_refs`, and an expression ceiling.
4. Facets live inside `strategy.json`. **The full profile never leaves Stage 1.**
5. Stage 2 receives only the distilled facet guidance carried in the strategy.
6. Stage 3 may suppress, replace or ignore every personality-conditioned choice (`INV-05`).
7. Employer-facing text uses ordinary work language. No MBTI/DISC/Enneagram/RIASEC vocabulary, ever — this is a `BOUNDARY`: a small, high-precision token scan on employer-facing fields, and one of the few lexical checks justified because the token set is closed and unambiguous.

The specific 20-facet ID vocabulary in the source material may be used as a reference vocabulary if the profile file defines it. The architecture requires only that a facet reference be stable and resolvable; it does not mandate a particular ID set or count beyond the 0–3 cap.

### 21.4 What personality is not

It is interpretive context (`INTERPRETIVE_CONTEXT`), never candidate factual authority, never a fourth authority file, and never an input to any deterministic decision. A facet without at least one supporting `evidence_ref` is a schema error: personality may shape how evidenced facts are framed, never what is claimed.

## 22. Optional preparation layer (Luna-class)

### 22.1 Status — `DEC-17`

`[DRAFT-DECISION]` (resolves `RQ-08` at architecture level) **Absent from the baseline.** No preparation pass exists in the frozen architecture, no artifact is defined for it in core, and no stage may depend on one. It is a Step-3 experiment (`EXP-03`).

`[RESEARCH]` The auxiliary model is much cheaper and materially weaker at long context in the cited benchmark. Cheapness is not value. Anchoring and summary distortion are the primary risks, and false exclusion is the dominant failure mode.

### 22.2 Contract if tested

Job-local or small-context only, never a global corpus pass; advisory and source-linked; forbidden to draft employer-facing prose, to exclude evidence, to establish facts or ceilings, or to review packages; trivially ignorable by `SOL_CLASS`; fail-open (missing or invalid preparation never blocks Stage 1); attributed in the run record.

The only meaningful comparison is:

```text
Control  : index + direct-source navigation -> Sol
Treatment: index + direct-source navigation + advisory preparation -> Sol
```

Never "preparation versus no context". Measure final package quality and evidence recall, not the elegance of the preparation output.

### 22.3 Activation rule

Activate only if the deterministic control shows a measured attention or retrieval problem, the pass can be bounded cheaply, a paired test shows material quality or effort gain with no decisive omissions, and the prompt count stays inside the 20–25 envelope.

## 23. Security and trust boundary

### 23.1 Control plane / data plane — `DEC-27`, `INV-13`

```text
CONTROL PLANE : this specification; stage instructions; settings; run manifest;
                schemas and validator policy; authority-file definitions;
                write permissions; the submission boundary
DATA PLANE    : vacancies and normalized extracts; candidate and personality content;
                strategy, draft, final, review; operator notes; any preparation output
```

Data-plane content may inform reasoning. It may never change instructions, permissions, source authority, run identity, expected jobs, validation policy or the submission boundary. Vacancy text that contains instruction-like content is employer content, not a command — stage prompts say so explicitly.

### 23.2 Deterministic safety

Resolve every path under allowed roots and reject traversal; handle symlinks and reparse points deliberately; enforce file type and size limits; preserve and re-check source hashes; never execute macros or embedded objects; grant model stages write access only to the current job directory; no network access in any deterministic command; human approval for every external action.

### 23.3 Prompt injection

`[RESEARCH]` Prompt injection is not solvable by lexical scanning. The controls are structural: instruction/data separation, least privilege, no external action capability, and a human gate on everything irreversible. A regex scan may raise an advisory flag; **no release document may claim prompt injection is solved or prevented.**

### 23.4 Privacy

Candidate material is personal data. Minimize what is uploaded to any model surface to what the stage needs; keep personal data out of logs and reports; verify the retention and training posture of the selected account and surface before production (`GATE-08`). Retention terms are volatile and are not architecture.

## 24. Human workflow

### 24.1 The loop

```text
1. select and approve vacancies; fill the batch inventory (clusters, order, priority,
   core/exception)
2. run `freeze`                      -> manifest, index, job scaffolding
3. Stage 1 chat per cluster          -> strategies (validated per job)
4. Stage 2 chat per cluster          -> drafts (validated per job)
5. Stage 3 chat per cluster          -> finals + reviews (validated per job)
6. run `finalize`                    -> merge, render, verify, derive queue
7. work the queue: READY -> skim and submit; CHECK -> bounded fix; RERUN -> targeted chat
8. capture portal answers downstream where a form requires them
9. submit manually; log time and a 1–10 quality score for calibration
```

### 24.2 The human owns

Vacancy selection and approval; maintenance of the authority files between runs; clusters, order and priority; final factual and semantic approval; claim-strength judgment; portal capture; **submission**; quality scoring; and rerun/drop/exception decisions.

### 24.3 The human must not have to

Synchronize state files; confirm each job between generations; re-enter candidate facts; read intermediate reasoning; hunt for missing expected jobs; or rescue every weak package. A workflow change that adds routine per-job human confirmation is a regression against `D-007`/`D-009`.

### 24.4 Review queue

Derived, grouped by action (`RERUN`, `CHECK`, `FAILED`, `READY`, `EXCEPTION`, `STALE`), sorted inside each group by deadline then human priority. Each row: job identity, status, up to three reasons with recommended actions, output paths, and any stale flag. No score, no ranking of jobs against each other.

Each is a decision in this document or an explicitly assigned gate/experiment. If a gate result forces a change, it is recorded as an amendment (§31), not absorbed into code.

## 26. Engineering tests

Tier 1 — before any semantic pilot. Each item must produce actual output, not merely import cleanly.

1. Freeze: source hashes recorded; a mutated authority file fails every subsequent command.
2. Identity: duplicate `job_id`, unsafe path, traversal, symlink, oversized and unsupported inputs all fail loudly at freeze.
3. Expected set: the finalizer enumerates from the manifest; a job whose directory was deleted is reported missing, not silently absent.
4. Schema validation: valid and adversarial-invalid fixtures for strategy, draft, final and review, each with a precise diagnostic (file, field, invariant, expected vs actual).
5. Reference resolution: a fabricated `evidence_ref` fails; a valid one resolves; a changed index hash marks the job stale.
6. Cross-job leakage: a fixture where job B's employer string appears in job A's package fails identity validation.
7. Employment replacement: exact before/after arrays; an override replaces, never appends; an empty bullet array is rejected; an unknown `employment_id` fails.
8. Final reference synchronization: change the evidence in a Stage-3 fixture and prove the final references change with it.
9. Leakage scans: private markers, source IDs, paths and placeholder tokens in employer-facing fields are rejected; a legitimate near-miss string is not.
10. Partial success: one poisoned job; all other jobs finalize and their output hashes are unchanged.
11. Targeted rerender: one job rebuilt; unrelated output hashes unchanged; document date unchanged.
12. Template fill: actual masters filled, controls unwrapped, assertion that no `w:sdt` and no placeholder remains.
13. Target-machine render smoke: DOCX and PDF produced and independently verified on the real Windows machine.
14. Injection and control plane: a vacancy containing instruction-like text does not change permissions, expectations or validation; write attempts outside the job directory fail.
15. Optional-feature absence: full pipeline green with personality off and every optional file deleted.

Tier 2 — before the first full batch: malformed model outputs and the bounded repair loop; sparse/normal/dense rendering; long Windows paths and Norwegian characters; interrupted and partial writes; repeated/idempotent commands; invalidation reporting for each class in §7.5; cluster position logging; queue and delivery classification.

Tier 3 — polish: richer reporting; optional feature toggles; performance tuning against measured bottlenecks only.

`INV-29` Engineering test success is **never** cited as evidence of semantic package quality. The three evidence loops stay separate (§27).

## 27. Product pilot

### 27.1 Three separate evidence loops

1. **Engineering conformance** — §26. Contracts, identity, state, merge, rendering, security, partial success. Failure here invalidates any product comparison, because the outputs cannot be trusted.
2. **Product-quality baseline** — real vacancies, real semantic models, all optional features off. This is the only source of quality evidence.
3. **Optional-feature experiments** — §29. One material variable at a time, run only after loop 2 exists.

`[USER]` Historical applications and interview-conversion rates are **not** comparable baselines. No document may claim P0.9 uplift against them. The first batch establishes the baseline.

### 27.2 Pre-production sequence

Freeze the architecture → complete the vacancy inventory (`GATE-07`) → template and converter preflight (`GATE-02`…`GATE-06`) → one-job deterministic vertical slice with synthetic artifacts → two real jobs live through all three stages and rendering → one representative cluster pilot → production batch.

### 27.3 Pilot measurement (one cluster, ~8 jobs)

Per job: human 1–10 overall quality; submit-ready yes/no; factual corrections needed; total human minutes through submission; review status and the repair scope actually required; `material_strategy_change`; position in the cluster; rerun needed and its result; notable convergence or context failures.

Per run: counts and shares of `READY`/`CHECK`/`RERUN`/`FAILED`; truth and attribution violations (target zero, and a hard guardrail rather than an average); median and distribution of human minutes per submitted package; packages submitted versus dropped; mechanical completion rate; quality by cluster position (descriptive only at this n); model cost logged where it actually arises — per model, surface, effort and chat — with the allocation method stated rather than a fabricated per-job credit split.

For `n=8`, report the raw ordered scores, the median, the mean of all, the mean of the top 6, and a sensitivity value at the top 7. State the `Q_happy` definition explicitly. Do not imply statistical precision; `[USER]` week-later self-rating repeatability is around 7/10, so single-pair conclusions are not reliable.

### 27.4 Quality rubric

Truth and defensibility (hard guardrail, never averaged away); employer specificity ("would this survive noun replacement?"); backbone and positioning; evidence selection; CV quality; letter quality and complementarity; natural Bokmål; usability for the actual channel; human minutes.

### 27.5 Calibration questions

Are weak packages labelled `READY`? Are `CHECK` items actually local? Are `RERUN` items genuinely un-fixable by bounded editing? How many strong packages are over-escalated (`ReviewLoad`)? What is the real human time per status? `TailRecall20` — how often the triage catches the human-judged weak tail — is self-triage calibration, never independent QA recall, and is meaningless without `ReviewLoad` beside it.

## 30. Release and conformance criteria

A conforming P0.9 implementation satisfies all of the following. Each is verifiable; none is a matter of opinion.

**Architecture**

- `ACC-01` Every core artifact schema is free of portal, channel, platform and language variables (`DEC-01`…`DEC-04`).
- `ACC-02` Exactly one frozen run authority exists; no second object encodes freeze, expectation or completion state (`INV-11`, `INV-21`).
- `ACC-03` Every artifact carries an explicit epistemic type, and the strategy carries its non-authority constants (§5.4, §10.2).
- `ACC-04` No rule anywhere requires the final package to agree with the strategy (`INV-05`).
- `ACC-05` The full baseline runs correctly with every optional feature off and every optional file deleted (`INV-12`).

**Intake and freeze**

- `ACC-06` Unique, safe job IDs; original vacancy preserved and hashed; every approved job represented exactly once as `CORE` or `EXCEPTION`; cluster, sequence, priority and document date frozen; authority, baseline, template, schema and index versions hashed; unsafe or unreadable input fails loudly with no partial run.

**Semantic artifacts**

- `ACC-07` Identity equality with the manifest across strategy, draft, final and review.
- `ACC-08` All four artifact types validate against their schemas, with precise diagnostics on failure.
- `ACC-09` Every evidence reference resolves in the frozen index; final references are synchronized to the final package (`DEC-25`).
- `ACC-10` Dynamic CV content appears only in permitted zones; employment overrides fully replace; unknown employment IDs fail.
- `ACC-11` Review carries a status, at most three reasons with actions, and no numeric score (`INV-01`).

**Runtime**

- `ACC-12` Continuation reconciles against the manifest and disk, never a remembered pointer.
- `ACC-13` A failed job cannot erase, mutate or block a good job; delivered outputs survive a nonzero run status (`INV-02`, `INV-26`).
- `ACC-14` Targeted rerun and targeted rerender work without touching unrelated outputs, and rerender never changes the document date (`DEC-22`).
- `ACC-15` Stale inputs are reported by class; nothing re-executes automatically (`DEC-26`).
- `ACC-16` No deterministic command makes a model call or a network request (`INV-08`, `INV-09`).

**Rendering**

- `ACC-17` All four documents per job exist, open, contain no placeholder or residual control, contain no private marker, and yield extractable text; identity and contact appear in body flow; sparse, normal and dense fixtures are visually inspected; prior valid outputs are protected from a failed replacement (`INV-16`, `INV-17`, `DEC-29`).

**Security**

- `ACC-18` Traversal, symlink, oversized and unsupported inputs are rejected; model write access is confined to the job directory; instruction-like vacancy text changes nothing in the control plane; no release document claims prompt injection is prevented (`INV-13`, §23.3).

**Product pilot** (separate from all of the above)

- `ACC-19` On one representative real cluster: packages are materially vacancy-specific; truth or attribution violations are absent or rare and corrected; Stage 3 demonstrably reconstructs weak upstream work at least once; median human handling time is broadly compatible with 10–20 minutes per submitted package; statuses roughly match the repair scope actually required; no severe early/late degradation or cross-job convergence; the weak tail is identifiable without degrading the strong majority.
- `ACC-20` The engineering results in `ACC-01`…`ACC-18` are never cited as evidence for `ACC-19` (`INV-29`).

No single number substitutes for judgment on `ACC-19`.

## 31. Change control

### 31.1 Amending this specification

Changes are recorded, never absorbed. An amendment states: the affected `DEC`/`INV`/`CTR`/`GATE` IDs; what triggered it (gate result, pilot evidence, user decision); the new rule; and what becomes stale. Amendments are appended with a date and reason; superseded text is struck, not deleted.

### 31.2 Who may change what

| Change | Owner |
|---|---|
| Product boundary, authority model, stage topology, statuses, human boundary | The user, explicitly |
| A `DEC` marked `[DRAFT-DECISION]` | Adjudication after review; then the user |
| A gate posture, after that gate's test result | The builder, recorded as an amendment |
| An `EXP` outcome that changes a default | The user, on the evidence |
| Module layout, names, libraries, internal abstractions | The builder, freely (§25.2) |

### 31.3 Regression signals

Treat any of the following as evidence that P0.9 is regressing toward the failure modes this architecture was designed to remove:

state objects growing faster than distinct decisions; a validator beginning to judge persuasion; the final writer defending the strategy instead of improving the package; a weak job blocking strong jobs; a generated summary becoming the only route to source evidence; an optional feature becoming necessary for baseline correctness; portal or channel exceptions reappearing in core schemas; generic document folklore overriding actual master inspection, or the reverse; the repository preserving P0.7/P0.8 shapes for compatibility; prompt, test or schema counts presented as quality evidence; any autonomous submission or external action; an `OPEN` item disappearing without a decision record, a gate or an experiment.

### 31.4 Stopping rule

Architecture work stops — and the build starts — when the load-bearing product, state and serialization choices are made, target rendering has a safe implementation path, every reversible quality enhancer is optional, every remaining empirical question has a named owner and metric, and no further experiment is likely to change a costly structural decision before the current deadlines.

By the author's assessment this document meets that bar. What remains is verification, not design.
