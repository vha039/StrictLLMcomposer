# Jobbsøk_26 P0.9 — Draft Implementation and Verification Contract

Subordinate to `P0.9_DRAFT_NORMATIVE_SPECIFICATION.md`. It introduces no architecture. Where this document and the specification appear to disagree, the specification governs and the disagreement is a defect in this document.

Audience: the Step-2 builder (Codex or equivalent) and the reviewer checking that the build satisfies the architecture.

---

## 1. Step-2 build objective

Produce a fresh, local, Python-first repository that turns a human-approved vacancy batch into validated, rendered, reviewable CV + letter packages, and that can **demonstrate** — with actual output, on the actual target Windows machine, using the actual candidate authorities and Word masters — that every invariant in the specification holds.

The build is finished when a human can run the documented commands from approved vacancies to a reviewable queue without understanding P0.7 or P0.8 internals, and when every item in §12 has evidence attached.

Not in scope for Step 2: improving package quality, choosing product policy, running the semantic pilot, or building anything on the `STEP3_EXPERIMENT` queue.

## 2. Required runtime surfaces

| Surface | Purpose | Notes |
|---|---|---|
| `authorities/` | three candidate authority files + `CV_BASELINE.md` | Copied byte-identically. Read-only to every model stage. Hash-checked by every command. |
| `policy/` | settings, writing/persuasion standards, three stage instructions, RERUN instruction, personality profile (optional) | Control plane. Never written by a stage. |
| `templates/` | CV master, application master, canonical template map | One map only (`CTR-12`), hashed into the manifest. |
| `schemas/` | one schema per canonical artifact | manifest, strategy, draft, final, review, evidence index. |
| `generated/` | evidence index | Regenerable, disposable, hashed at freeze. |
| `runs/<run_id>/` | batch inventory, manifest, derived status/queue, per-job directories | The only location any model stage may write, and only inside its own job directory. |

Command surface (`DEC-28`) — five task-oriented operations, however they are grouped:

```text
freeze     inventory -> manifest + index + job scaffolding   (also: --amend)
validate   one artifact / one job / a whole run
finalize   merge, fill, render, verify, promote, reconcile   (--job, --render-only)
status     derived state, stale classes, review queue
preflight  template map, control inventory, converter and font smoke
```

Every command: exits nonzero on failure; prints a diagnostic naming file, field and violated invariant; is safe to re-run; makes no network request; and invokes no model.

## 4. Required contracts and schemas

Six schemas. Every one rejects unknown top-level and nested fields, and none contains a numeric quality or confidence field.

1. **Manifest** — run identity, spec/schema versions, settings snapshot, authority/baseline/template/index/instruction hashes, per-job identity, cluster/sequence/priority, class and exception reason, vacancy paths and hashes, frozen `document_date`, and the derived `expected_core_jobs` list.
2. **Evidence index** — `evidence_id`, source file, heading path, char range or stable anchor, section hash, approximate size, and optional source-stated lifecycle or claim-ceiling markers. Nothing else. No score, no rank, no relevance, no inferred label.
3. **Strategy** — the §10.3 surfaces, with mandatory constants `artifact_role = STRATEGY_HYPOTHESIS`, `authority = NON_FACTUAL_NON_FINAL`, `elasticity = ELASTIC`, `final_writer_may_reconstruct = true`; cardinality caps (requirements ≤12, evidence plan ≤10, ≤2 `BRIDGE_PRIMARY`, ≤3 `BRIDGE_SECONDARY`, objections ≤3, proof arcs ≤3, facets ≤3); headline ≤140 characters; prose word budget (warn >1200, fail >1600).
4. **Draft package** — identity echo, `baseline_version`, `used_evidence_refs` (non-empty), `cv` (headline, profile, 4–8 competencies, 0–4 employment overrides with 1–5 bullets each), `application` (opening, 1–5 body paragraphs, closing), optional `writer_delta` ≤80 words. No portal field, no language field, no letter-required field, no static chronology.
5. **Final package** — identical shape, `source_stage = STAGE3_FINAL`.
6. **Review** — status enum `READY|CHECK|RERUN`, 0–3 reasons each with a recommended action, optional limitations, `material_strategy_change` (+summary), `upstream_claim_repaired` (+note).

## 5. Architectural invariants Codex must enforce

| Spec ID | Requirement | Expected implementation surface | Verification evidence |
|---|---|---|---|
| `INV-01` | No numeric quality or confidence anywhere | Schemas reject such fields; no scoring code | Fixture with a `score` field is rejected by every artifact schema |
| `INV-02` | Job is the transaction; one failure cannot affect another job | Per-job try/except boundary in `finalize`; per-job temp dir | Poisoned-job run: other jobs' output hashes unchanged, exit nonzero, deliverables intact |
| `INV-03` | Authority files immutable in a run | Hash check at the start of every command; read-only handling | Mutate one authority file: every command fails with a named diagnostic |
| `INV-04`/`INV-05` | Strategy is a hypothesis; nothing constrains the final writer to it | Schema constants; absence of any final-vs-strategy comparison in code | Code search shows no comparison of final content against strategy content; prompt review shows no compliance requirement |
| `INV-06` | Code enforces only mechanical contracts | Validator inventory maps 1:1 to spec §15.2 | Reviewer checklist: each implemented check maps to a listed mechanical check |
| `INV-07` | Source escape unconditional | Read access to `authorities/` from every stage; index is lossless | Coverage assertion in the index generator; prompts grant escape explicitly |
| `INV-08`/`INV-09` | No model calls, no network, no external action | No HTTP or model client dependency in the runtime package | Dependency audit + a test that fails if a network client is importable from the runtime |
| `INV-10` | Completion derived from validated artifacts | `status` reads manifest + artifacts + validation results only | Planting a `_DONE`-style file changes nothing in `status.json` |
| `INV-11` | One authoritative representation; views regenerable | Derived views written only by `status`/`finalize` | Delete `status.json` and `queue.md`, regenerate, compare byte-for-byte |
| `INV-13` | Control/data plane separation | Write-root enforcement; instructions never sourced from data-plane files | Vacancy fixture containing instruction-like text changes no permission, expectation or validation outcome |
| `INV-14` | No internal artifacts in employer-facing output | Leakage scan over rendered text and over employer-facing JSON fields | Adversarial fixture with an evidence ID and a path in the profile is rejected; a legitimate near-miss string is not |
| `INV-16` | No output complete without independent verification | Per-document verification function in `finalize` | Forced partial-conversion fixture: job marked failed, prior outputs retained |
| `INV-17` | Idempotent, atomic | Temp dir + atomic promotion; deterministic outputs | Interrupted-write fixture; repeated command produces identical hashes |
| `INV-24` | Employment overrides fully replace | Merge function replaces the bullet array wholesale | Before/after array test; empty array rejected; unknown ID rejected |
| `INV-28` | Index lossless coverage | Generator asserts every byte belongs to exactly one leaf entry | Coverage assertion failure fixture (a source with content before the first heading) |
| `DEC-08` | Expected set from the manifest only | `finalize`/`status` enumerate from `expected_core_jobs` | Delete a job directory: reported missing, not silently absent |
| `DEC-22` | Frozen document date | Date read from the manifest at render time | Rerender twice on different days: identical rendered date and identical PDF text |
| `DEC-25` | Final refs synchronized and resolvable | Reference resolution against the frozen index | Change evidence in a Stage-3 fixture: final refs change; a fabricated ref fails |

## 7. Rendering verification obligations

Before any job is marked rendered, for **each** of the four documents independently:

1. the expected file exists at the expected path and is non-empty;
2. it opens with an ordinary reader/parser;
3. no `w:sdt`, placeholder token or template marker remains (DOCX);
4. expected identity strings (candidate name, employer, title, headline) are present;
5. no private marker, evidence ID, internal path or run/job ID is present;
6. PDF text is extractable and selectable;
7. the converter's exit code and stderr were captured and are recorded in `render_report.json`.

Preflight (`preflight`) additionally proves, once per environment and after any template change: the converter runs headless with an isolated profile and absolute quoted paths (`GATE-03`); fonts are present and `æ`/`ø`/`å` render correctly (`GATE-05`); sparse, normal and dense fixtures render with acceptable page counts and no clipping, and are visually inspected by a human; extracted text preserves logical reading order and contains identity and contact from body flow (`GATE-06`).

Default converter posture is one isolated invocation per document (`DEC-21`). A single invocation for both is permitted only after `GATE-04` evidence is recorded in the build report.

## 8. Security and provenance requirements

- Resolve every path under allowed roots; reject traversal; handle symlinks and reparse points deliberately; enforce type and size limits at freeze.
- Model stages may write only inside `runs/<run_id>/jobs/<job_id>/`. Attempted writes elsewhere fail.
- Authority, baseline, template, index and instruction hashes are checked at the start of every command; a mismatch is reported as a stale class, never silently accepted.
- Never execute macros or embedded objects in an input document.
- No network access in any deterministic command; no submission, contact or profile-mutation capability exists in the codebase.
- Adversarial fixtures required: a vacancy containing instruction-like text; a vacancy containing a path traversal string; an oversized file; an unsupported type; a symlinked vacancy; an artifact attempting to write outside its job directory.
- Logs and reports carry no unnecessary personal data. No build document may claim prompt injection is prevented.

---

## 9. Partial success and targeted operation

Required, each with a demonstration:

- one job completes fully while another fails, with the successful job's outputs byte-unchanged;
- a failed job remains visibly failed, with its invalid artifact and diagnostics in `history/`;
- `validate`, `finalize` and `--render-only` all accept a single `job_id`;
- a pure rerender preserves semantic content and the frozen document date;
- a RERUN replaces `final_package.json` and `review.json` only after both validate, moving the superseded pair to history;
- a failed replacement never destroys a prior valid output;
- the derived queue distinguishes *not produced*, *produced and failed*, *produced and stale*, and *delivered*;
- a nonzero run-level exit code leaves every delivered job intact.

## 11. Hooks required for Step-3 experiments

Cheap, inert, and off by default. None may be load-bearing.

- **Settings toggle** for personality, read once at freeze and recorded in the manifest settings snapshot (`EXP-02`).
- **Position logging**: the cluster and sequence of each job are already in the manifest; `status` exposes them so quality can later be plotted by position (`EXP-01`).
- **Strategy serialization seam**: the strategy is read through one function and validated by one schema, so a Markdown variant can be added without touching Stage-2/3 code paths (`EXP-04`).
- **Optional advisory artifact slot**: a job directory may contain an inert file that no validator, status derivation or stage requires; nothing in the baseline reads it (`EXP-03`).
- **Diagnostic fields**: `material_strategy_change` and `upstream_claim_repaired` are already in the review schema; `status` aggregates them for reporting (`EXP-06`).
- **Human measurement**: the queue provides a per-job row the human can annotate with score and minutes. A spreadsheet is sufficient; no measurement subsystem is to be built.

## 12. Definition of done

The repository is ready for the first semantic pilot when **all** of the following have attached evidence:

1. Every Tier-1 engineering test in specification §26 passes, producing actual output, on the target machine.
2. The blocking gates in §10 are closed, with results recorded.
3. `ACC-01`…`ACC-18` are demonstrated. `ACC-19`/`ACC-20` are pilot criteria and are explicitly *not* claimed by the build.
4. One complete operator run — approved vacancies → freeze → synthetic stage artifacts → validate → finalize → queue — succeeds on the target Windows machine using the real masters.
5. Partial success and targeted repair are demonstrated (§9).
6. Every optional feature is off, and the pipeline is green with all optional files deleted.
7. A build report labels every claim `DESIGNED`, `IMPLEMENTED`, `MECHANICALLY_TESTED` or `PRODUCTION-MODEL_TESTED`. "Implemented" without evidence is not accepted, and no mechanical result is presented as evidence of package quality.
8. No item in specification §25.3 was decided by the builder.

Do not delay the pilot to build deferred infrastructure. Do not call the system production-ready on fixtures alone: real vacancies, real models and human review are the next evidence layer.

## 13. Prohibited silent redesigns

The builder may not, without an explicit amendment: reintroduce portal, channel or language branching into core; add a fourth semantic stage, a judge, a scorer or an automatic router; make deterministic code call a model or the network; add automatic retries beyond the two visible repair attempts; introduce a second authoritative state object; replace derived status with a maintained status file; add a database, vector store, embedding index or graph; add relevance scoring or tiering to the evidence index; make personality or any preparation layer required; add a code-owned prose or phrase gate; add typography auto-fit or a converter daemon; weaken any claim ceiling; add any submission, contact or external-action capability; or change the meaning of `READY`, `CHECK`, `RERUN` or `FAILED`.

If the build genuinely cannot satisfy the specification, the correct action is to stop and report the conflict — not to resolve it in code.
