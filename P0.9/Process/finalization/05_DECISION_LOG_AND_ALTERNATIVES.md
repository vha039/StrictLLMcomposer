## 1. The professional-voice architecture — the largest decision

### 1.1 Options considered

| Option | Placement | Routing | Verdict |
|---|---|---|---|
| **1** | `policy/writing/FORFATTERSTEMME.md` | all three stages, automatically | **CHOSEN** |
| 2 | `context/FORFATTERSTEMME.md`, new `frozen_inputs` key | Stages 1 + 3 only, conditional in `cmd_context` | rejected — see §1.3 |
| 3 | a new section inside `PERSONALITY_PROFILE.md` | needs a routing mechanic to extract it | rejected |
| 4 | inside `WRITING_DOCTRINE.md` | all three stages | rejected |
| 5 | inside `PERSUASION_CALIBRATION.md` | all three stages | rejected |
| 6 | a new semantic Stage 4 or 3.5 | n/a | rejected |
| 7 | dynamic per-vacancy voice generated by Stage 1 | via `strategy.json` | rejected |
| 8 | deterministic humanizer or LLM voice judge | n/a | rejected |

### 1.2 Why Option 1 wins

- **Zero plumbing.** `manifest.py:221` freezes `policy/writing/*.md` by glob; the schema declares an
  unbounded array; `stage_policy_sha256` folds in every writing-policy file; `cmd_context` exposes
  them all. No code, no schema, no manifest change. Grep confirms zero test coupling to the count.
- **Correct category.** Contract §3 defines `policy/` as *"settings, writing/persuasion rules and
  stage instructions (control plane)"*. `PERSUASION_CALIBRATION.md` is already a candidate-owned file
  there (`owner: Vegard Håland`), so a candidate-owned expression rule set has a precedent.
- **Provenance for free.** Frozen and hashed into every manifest, copied into
  `runs/<run>/frozen/policy/writing/`, so any package can be traced to the exact voice file that
  governed it — which is also what makes an A/B against the pilot meaningful.

### 1.3 Why Option 2 loses — and it is not about cost

The obvious objection to Option 1 is that it hands a candidate-specific voice file to Stage 2, whose
own instruction promises it receives only distilled personality guidance. That objection is real and
forced this decision to be rebuilt (R6). But routing it to `context/` is **worse, not merely
costlier**:

`branch.CONTENT_GOVERNING` decides when a child run may rebind an artifact without re-running its
stage. It already declares `("writing_policy",)` content-governing for `strategy`, `draft_package`,
`final_package` **and** `review`. A `context/`-placed voice file would govern Stage 3's content while
being **absent from that table**, so a child-run rebind could silently reuse a `final_package`
produced under a different voice file. That trades an integrity property for a routing preference.

Adding a new `CONTENT_GOVERNING` key as well would then require: a `manifest.schema.json` property
(the object is `additionalProperties: false`), a `manifest.py` change, a `cmd_context` conditional, a
`branch.py` entry and new tests — five files to reach a worse integrity position than the zero-file
option.

### 1.4 Why Options 3–8 lose

- **3 — a section inside `PERSONALITY_PROFILE.md`.** Spec §10.2 and Contract §12 forbid passing the
  full profile downstream; extracting one section needs a routing mechanic, which is Option 2's cost
  without Option 2's precision. The profile is also explicitly `not_intended_for: Direct
  employer-facing insertion`, whereas a voice file is *about* employer-facing expression.
- **4 — inside `WRITING_DOCTRINE.md`.** Cheapest of all, and conceptually wrong: universal Norwegian
  application doctrine and one candidate's expression habits are different sources of truth. A
  candidate rule would silently become universal doctrine and drift would be undetectable.
- **5 — inside `PERSUASION_CALIBRATION.md`.** That file is explicitly a corrections log — *"Bare
  eksplisitte, gjenbrukbare korreksjoner fra Vegard skal legges til her"*, status `ACTIVE_MINIMAL`.
  Voice is not a corrections log. Same routing as Option 1 with a worse fit.
- **6 — a new stage.** Conceptually clean, operationally expensive: artifact ownership, state, render
  eligibility, recovery, context modes and final authority would all need answers, to do work Stage 3
  already owns. Contract §22 prohibits a fourth stage.
- **7 — dynamic per-vacancy voice.** Voice is candidate-invariant; employer register adaptation
  belongs to the writer and is covered by `§ Stabil forfatter, variabelt register`. Generating it per
  vacancy adds stochastic drift and would make voice disappear when Stage 1 selects zero facets.
- **8 — humanizer or judge.** Contract §22 and Spec §13.4 prohibit a numeric quality judge; the
  objective is generative candidate authorship, not cosmetic anti-AI entropy.

### 1.5 Stage-3-primary versus Stage-2-and-3 conditioning — decided on evidence

`NON_AUTHORITATIVE_CONSIDERATIONS.md` §5 ranks a Stage-2 + Stage-3 design as the strongest
alternative, on the hypothesis that a generic Stage-2 draft would **anchor** Stage 3.

**The pilot refutes the anchoring hypothesis.** Stage 3 replaced both openings, deleted a whole
paragraph from each letter, reordered the evidence, trimmed competencies from 7→6 and 8→6, and
rewrote the framework sentence. It was not anchored; it reconstructed *toward* conventional polish.
Indeed Stage 2's drafts were the **more** plainly written of the two — its openings were candidate-first
(`Jeg søker stillingen som … fordi …`) where Stage 3 substituted consultant forms.

So heavy Stage-2 voice conditioning would spend context on the stage that is not the problem. Stage 2
gets the file as a light prior — it arrives anyway — and Stage 3 carries the ownership. Stage 3 still
formalises the requested anti-anchoring safeguard: before reading upstream prose, it chooses an
independent thesis, opening, evidence order and register from vacancy plus evidence.

### 1.6 Voice-file grounding

Asked and answered: the file is **derived from `PERSONALITY_PROFILE.md` §1 and §6 plus the
anti-patterns reproduced from the pilot output**, and reviewed by Vegard before the first run that
uses it. No corpus of the candidate's professional Norwegian writing exists in the repository, and the
profile is English and describes cognition rather than prose habits.

The pilot-derived section (`§ Mønstre som skal erstattes`) is the highest-confidence part of the file
precisely because it is observational: `Jeg ser frem til muligheten til å utdype …` occurs 4 times
across 2 jobs and 2 stages and survived Stage-3 reconstruction untouched in both. Sample-grounded
refinement remains available as a later revision of the same file.

## 2. Typography decisions

### 2.1 Where typography lives — `prepare_masters`, not a hand edit

| Option | Verdict |
|---|---|
| Declarative table in `prepare_masters.py` | **CHOSEN** |
| One-off hand edit of the DOCX | rejected |
| Typography block in `template_map.json`, applied at render | rejected |
| Edit `styles.xml` only | rejected — provably ineffective |

`styles.xml`-only is not a preference but a factual error: `docxfill._set_paragraph_text` deep-copies
the template run **including `w:rPr`**, so generated CV paragraphs take the master's inline size.
Changing only `styles.xml` would leave the CV almost entirely unchanged. (A prior report asserted the
opposite; `04_…md` §4.1 records the correction.)

A hand edit fails on reproducibility: with no `.git`, an unrecorded binary edit could never be
audited, re-derived or reversed — which is precisely why `prepare_masters` exists. It already repairs
the P0.7 OOXML defects, retargets fonts, removed the forced page break, and verifies the 17/7 control
contract before writing.

`template_map.json` would put presentation logic in the render path and widen a frozen input for no
gain over setting the value once in the master.

### 2.2 Position-keyed, not value-keyed

A value map (`9.0 → 12`) is **not idempotent**: after one run the document contains 10 and 12, and a
second run fires again on the 10s. Keying by SDT tag and text anchor with an absolute target makes
re-running a no-op, which is what lets `prepare_masters --check` remain a standing proof.

### 2.3 Headings at 14, not 12 — and not proportional scaling

Three candidates once the body moves to 12:

- **12 (flatten)** — removes the 1 pt differential that exists today, exactly when the body grows.
  Rejected (R1).
- **Proportional (×1.33 → 13.3)** — 13 is excluded by the user's scale (8, 9, 10, 11, 12, then even),
  and proportional scaling of everything would blow the page budget.
- **14** — even, in scale, gives a 1.17 ratio against body, and preserves the master's existing
  hierarchy mechanism (bold + caps + teal) rather than replacing it. **Chosen**, at a cost of ≈45 pt
  across nine headings, about 6 % of a page.

Employment title lines drop from *equal to* `Heading1` to one tier below (12 against 14). That is a
deliberate improvement: a section label and the record beneath it should not be the same size.

### 2.4 De-bolding: exactly two paragraphs

`CV_RELEVANT_BACHELOR_SUBJECTS` and `CV_OPTIONAL_PREVIOUS_EXPERIENCE`'s content paragraph lose `w:b`
and their `w:color` override. Record lines — employment title, unit, education titles — keep theirs;
their bold navy is correct design. Size alone would not fix ISS-04, because weight is the dominant
signal: bold navy at 10 pt still reads as a title against 12 pt plain body.

### 2.5 Spacing left unchanged, deliberately

The tier scale models to ≈1.5 pages for the CV without touching `w:line` or `w:spacing`. Changing
spacing costs page budget and is not needed. At `w:line="252"` (1.05) a 12 pt Calibri line is tight
but legible. **If** the B0/A1 visual review judges it cramped, a single canonical `w:line` adjustment
is a sanctioned follow-up under A3 — measured, not speculative. This converts a guess into an
observation.

### 2.6 The page-budget decision rule

If the CV renders to 3 pages, the response is editorial compression (A3), **never** a type-size
reduction. `DEC-24` forbids deleting decision-relevant content to satisfy a page rule, so compression
means tightening prose and prioritising competencies, not dropping evidence. `cv_expected_max_pages`
stays at 2 and produces an advisory warning — becoming useful for the first time, since the pilot's
PDF conversion failed and no page count has ever been produced.

## 3. Earned motivation

### 3.1 Non-sufficiency, not a category ban

The deciding evidence is that the two pilot cases are not the same case (`04_…md` §3.1a). Huseierne
quotes the employer's public slogan and attaches motivation to it; Avinor names the operating
environment, which is a causal feature of the work and the basis of the candidate's whole transfer
argument. A categorical rule would have destroyed the second to fix the first.

B2's salience clause is therefore narrow: mission language **does not by itself** establish that
`Arbeidsgiverbyttetesten` is passed. The existing `Begrunnet motivasjon` supplies the discriminator:
is the motivation grounded in the actual work and candidate experience rather than copied employer
value language?

### 3.2 Route the existing section; do not rewrite it

`Begrunnet motivasjon` already anchors motivation in concrete work and explicitly forbids generic
employer praise, copied values, prestige and ungrounded enthusiasm. `Arbeidsgiverbyttetesten` already
says not to repair specificity with slogans, copied values or unfounded employer praise. Coverage is
there; Stage 1 was instructed to consult other sections only, and Stage 3 named two tests but not
`Begrunnet motivasjon`. The change is a named-section pointer at both stages plus the narrow Stage-3
salience clause that mission wording itself is not evidence of a pass.

Rejected: a Stage-3 motivation rubric in English. A five-item Stage-2 gate and a nine-item Stage-3
English rubric were both proposed and both deleted earlier in this project for exactly that reason —
they restate calibrated Norwegian in weaker English and create a second source of truth that drifts.

### 3.3 Motivation stays out of the candidate-voice file

`FORFATTERSTEMME.md` contains no statement about what actually motivates the candidate. Such a
statement would be a candidate fact derived from interpretive personality context, conflicting with
the file's `factual_authority: false` boundary and the three-authority rule. Motivation remains under
the existing doctrine plus actual vacancy/evidence; the voice file governs only how an already
truth-safe argument is expressed.

## 4. Maximum truthful leverage

### 4.1 Semantic rule, not a word list

Rejected: a rule naming `rapportert` and `oppgitt`. It would invite lexical substitution rather than
judgement, would strip the word where the qualification is genuine, and generalises to nothing.

Chosen: one concise speaker-transposition clarification in `TOO_WEAK`. Reader-protecting
qualifications — approximation, observation horizon, lifecycle state, absence of measurement —
survive. A marker that only records that the source file logged the candidate's own statement does
not survive the change of speaker. The general leverage rule is not restated; it already exists.

### 4.2 Fix at the origin as well as the repair point

The trace puts the first occurrence in Stage 1's `evidence_plan[].role`. A Stage-3-only repair duty
would leave the framing that both downstream writers inherit untouched, and would rely on a
downstream stage catching what an upstream stage was never told to avoid.

### 4.3 Do not edit the authority

Explicitly rejected: removing "reports" from `Work_experience.md`. The provenance marker is **true and
useful inside the authority** — it records that the claim rests on self-report rather than
measurement, exactly the kind of distinction the evidence architecture exists to preserve. The fix
teaches the transposition, it does not destroy the source distinction.

### 4.4 No detector

A deterministic hedge detector was rejected: this is a semantic judgement no validator can make, and
`INV-07` with Spec §10.3 forbid failing a package because a string appears.

## 5. Punctuation

| Decision | Alternatives rejected |
|---|---|
| `render.py:179` em dash → **period** | hyphen (reintroduces the prohibited clause-dividing hyphen); colon (acceptable, but a period reads better after a `\|`-separated identity line); restructuring the line (wider than needed) |
| Date-range en dashes → **hyphen** | leaving them: outcome D prohibits the character in employer-facing text and explicitly lists dates and ranges among the hyphen's legitimate uses |
| Unit-name en dashes → **comma** | hyphen: `Direktørens stab - Analyseavdelingen` would itself be a clause-dividing hyphen, prohibited by the same outcome |
| `authority_anchor` values → **left unchanged** | converting them: they are inert, never render, and two are verbatim cross-references to strings in `Work_experience.md` |
| Fix at source (baseline + master) | normalising at render time: hides the source of truth, puts a text transform in the render path, and would break `static_baseline_assertions` unless duplicated there |
| Doctrine subsection for clause hyphens | a validator: outcome D says not to assume one is needed, and `INV-07` forbids failing on a character |
| **No runtime dash warning** | a warning adds machinery without preventing the semantic clause-hyphen defect and invites a second quasi-validator. Known deterministic sources get exact tests; full output is extracted and human-reviewed. |

The output rule is verified at the product boundary by extracting all four A1 and Run B documents and
checking for en/em dash, plus human review for clause punctuation. No runtime warning, normalizer or
failure rule survives the scope gate.

## 7. Verification-design decisions

### 7.1 One projected replay plus an accessible frozen baseline

A run's frozen manifest pins its masters and `render_job` raises `ConfigurationError` on mismatch.
Before any implementation, copy the existing pilot DOCX byte-for-byte into the external snapshot and
verify their SHA-256; copy semantics give the snapshot readable inherited access without altering the
pilot. That is B0. After implementation, one new A1 run projects the same semantic fields through
fresh handoffs and renders with the new masters. A separate old-master run was rejected as pure cost:
it would recreate bytes already preserved in B0.

### 7.2 Semantic-field projection, not artifact copying

Pilot artifacts carry a `binding` pinned to the pilot manifest, strategy and draft hashes, plus a
`finalization` block. `artifacts.MECHANICAL_FIELDS` gives the exact key set to strip. The new run then
stamps its own binding and owns the artifacts with correct currentness.

Stated plainly rather than discovered later: A1 **deliberately re-injects the known semantic defects**
from B0, because holding content constant is the whole point of the typography A/B. A1 is not semantic
acceptance; Run B is.

### 7.3 Run B acceptance tests properties, not surfaces

Rejected (R11): "no mission paragraph", "letters must not share a closing formula or macro-structure".
The first bans a legitimate paragraph; the second rewards difference for its own sake and could make
one letter worse to keep it unlike the other.

Chosen: earned motivation traceable to work/problem/environment/documented motive; truthful leverage
checked **in both directions**; structure judged on the **strategy field**, not the letter's
silhouette — the failure signal is a `structure_guidance` that would read identically for any
employer; voice judged by blind A/B; and a regression guard on the Avinor sentence that was already
good.

### 7.4 Human acceptance is required, not advisory

Mechanical checks cannot answer "is this readable and well balanced" or "does this sound like me".
Both are mandatory outcomes. The B0/A1 visual comparison also discharges `VISUAL_HUMAN` / `ACC-18` on
real content, which is still formally owed.

### 7.5 Pilot log: a RUNBOOK line, not tooling

Automatic pilot-log tooling was previously deliberated and deferred, and a deferred item returns only
on repeated production evidence that also beats the smallest local remedy. One RUNBOOK line placed
where the information is actually in the operator's head **is** the smallest local remedy. The 19
columns already exist. `[paths].pilot_log` stays unwired, per the standing F22 deferral.
